# TLA+ 历次发现：产品确认与裁决清单

日期：2026-11-17。状态：用户已批准本轮讨论的 D 项处理方向；B1—B6 按既定契约认定为缺陷，无须重新裁决。D7 已追加真实上下文链路确认并实施自动接续修复，其他项尚未在本轮修复。

## 当前处理口径

D 编号是追踪索引，不代表十个独立业务决策。D1／D2／D3／D5／D6／D7 属于既定要求的工程落实或补验；D8 的权限与入口、D9 的归档操作，以及 D4／D10 中超出现有保证的承诺，需要按已批准方向细化，但不扩大既有授权、不承诺永久去重。这些后续设计均不构成确定缺陷的修复前置条件。

D7 的自动接续缺陷已确认并修复：普通 trim 会过滤真实 Agent 保存的待核对 system 通知；原接续只通知本次新建项，因此旧未结清事项可从后继模型输入中消失。现在自动接续从事务内全部未结清项重新生成通知，手动免播不变。重启扫描是否唤起仍由 pending／running 等执行事实决定，未把 open 项一律视为自动执行授权。详见 D7。

## 先读结论

从首次试验、第一轮深化，到按五个方向补充验证，初轮确认了 **6 项缺陷（B1—B6）、1 项已修复的历史故障，以及 10 组后续处理事项**。D 项不是十个独立业务决策；深入验证又确认 D7 的自动接续发现缺陷，该部分已修复，B1—B6 尚未修复。 这些问题集中在同一条业务链：用户发送任务、点击停止、对话精简接续，以及故障后恢复；不代表已经检查完项目所有模块。

最需要优先处理的是两件事：**系统不能在尚未可靠保存任务时就把它算作接收完成；用户点击停止后，不能漏取消旧输入，也不能误取消后来新发的输入。** 其次是旧会话退役的执行权、待核对事项的持续发现和处置闭环。

这里的“已确认缺陷”指可重复运行的真实代码路径违背已有要求，不等于已经发生线上用户事故。“业务影响”是这些路径可能带来的后果；未实际复现的丢失、重复工具操作等后果会单独说明。缺陷修复服从已有契约；D 项中只有超出现有保证的业务取舍属于产品决定，工程方法和已定要求不得混入待裁决清单。

### 读懂本文只需要四个概念

- **接收队列（Viewer）**：平台暂存已收到、等待 Agent 接管的输入。
- **会话快照**：磁盘上的会话存档；进程退出后靠它恢复。内存里看得见，不代表重启后找得回。
- **接续／换棒**：上下文过长或用户精简时，把工作交给一个后继会话。线程是同一个，当前负责执行的会话变了；代码称它为 head。
- **待核对项（unresolved）**：平台确实交付过任务，但不能可靠判断旧会话是否已经处理，因此保留原内容，让后继或人明确决定“已处理、放弃、重新发起”。它不是普通待发消息，也不是任务完成证明。

## 一、已确认缺陷：建议确认修复原则，不再把错误行为当成可选设计

### B1．任务还没存好，平台就把它从接收队列中删掉

**用户可能在哪遇到：** 编程小助手、Coder 等线程会话收到任务之后，恰逢会话保存失败。用户可能看到这一轮报错，随后重启应用或会话，发现刚才的要求没有可靠恢复。

**发生了什么：** 输入先进入 Agent 内存，保存会话失败，收尾补存也没有成功。后台轮询却把“内存里已经有这条消息”当成“已经存到磁盘”，向平台确认接管；平台据此把持久队列中的原输入删除。

**业务影响：** 出现“两边都没有可靠保存”的窗口。此后进程崩溃，任务可能漏做，而且不能再从接收队列找回。它不表示每次保存报错都会丢任务。

**确认到哪里：** 模型和真实 Agent、调度器、Viewer 回放都成立，且独立读取队列文件确认已删除、成功快照为零；没有在此回放中实际强杀完整宿主。

**修复要求：** 会话保存失败时应明确显示“任务尚未可靠接管”，原任务保持可恢复。不能因为界面曾显示过消息就宣布接管成功。保存错误后的自动重试、暂停与人工提示，见 D1。

**工程定位／证据：** `scripts/runtime-passive-mailbox.js` 的回执快捷路径；AgentDev `packages/core/src/core/agent.ts` 的保存边界。`specs/tla/receipt-boundary-replay.test.mjs`，严格开关 `REQUIRE_RECEIPT_DURABILITY=1`。依据 ADR-0047 §5、§6.1。

### B2．只记录了“开始处理”，接续就误认为任务已经可靠交给旧会话

**用户可能在哪遇到：** 任务刚开始便保存失败，随后发生自动接续或手动精简／摘要。用户切到后继会话，可能既没看到任务继续，也没收到需要核对的提醒。

**发生了什么：** “本轮开始”事件在会话保存之前发出。接续分类看见事件引用了这条任务，就认定旧会话已消费，不再为它建立待核对项。

**业务影响：** 任务可能从恢复清单中漏掉。B1 是接收队列提前删除，B2 是接续恢复判断错误；它们是两个独立问题，只修其中一个不能代表另一个已解决。

**确认到哪里：** 真实回放中，成功快照为零、模型调用为零、接管确认也为零，但接续结果却把任务判为已消费，待核对项为零。尚未复现完整宿主崩溃后的最终丢失。

**修复要求：** “开始过”只能用于展示进度，不能免除恢复责任。必须有可靠接管证明才从待恢复范围移走；可靠接管也不代表用户目标已经完成。

**工程定位／证据：** AgentDev `agent.ts` 开始事件与保存顺序、`workthread/inbox.ts::classifyRetiredCommands`；Claw `server/thread-control/thread-integration.js`。`succession-evidence-replay.test.mjs`，严格开关 `REQUIRE_EVIDENCE_DURABILITY=1`。依据 ADR-0047 §2、§5。

### B3．用户停止时，已经提交但尚未到接收队列的旧任务可能漏取消

**用户可能在哪遇到：** 对话忙碌、接续中或任务仍在等待投递时，用户点击输入框停止，或在线程菜单点击“停止／中断线程”。

**发生了什么：** 停止操作只取消 Viewer 此刻看得到的输入。某条任务早已进入线程收件箱（Inbox），但尚未到 Viewer，就不在取消集合内，之后仍能投递并被领取。

**业务影响：** 用户以为“刚才排队的都不要了”，旧任务却可能稍后开始。对于改代码、运行命令等任务，这会违背用户撤销意图。

**确认到哪里：** 真实 Inbox、Bridge 和 Viewer 回放确认：先提交、再停止、之后投递的同一条任务仍可领取。未执行它后续的模型或工具动作。

**修复要求：** 保持已有契约：停止截点前、尚未消费的旧输入全部进入取消范围，不以它当时卡在哪一层决定命运。

**用户入口定位：** `public/src/modules/persistent-input.js::interruptAgent`；`ctx-menu-items.js` 的 `thread-interrupt`；Coder 插件 `public/src/plugins/coder/index.js::interrupt`，都请求当前执行会话的中断端点。

**工程证据：** `cancellation-checkpoint-replay.test.mjs`，严格开关 `REQUIRE_GLOBAL_CANCEL_CUTOFF=1`。依据 ADR-0047 §6.2。

### B4．停止请求传得慢时，后来新交的任务反而被一起取消

**用户可能在哪遇到：** 点击停止后又发新指令，或停止与外部任务提交相邻发生；旧执行进程尚未收到中断通知。

**发生了什么：** Viewer 已经确定停止截点，但执行进程稍后收到的仍是无范围的“清空排队任务”。这个清空动作也会扫掉截点后才进入调度器的新输入。

**业务影响：** 用户明确新交的任务被旧停止请求误伤，表现为新要求没执行或被取消。它与 B3 相反：B3 是旧任务漏停，B4 是新任务误停。

**确认到哪里：** 真实 Viewer 中断处理生成通知帧，控制帧延迟后交给真实 CallArbiter，确认截点后的新排队任务被取消。尚未对每种真实输入通道复现完整网络时序。

**修复要求：** 同样保持已有契约：停止只取消截点前的输入，后交任务应保留，待当前步骤安全退出后再执行。

**工程定位／证据：** `server/call-arbiter.js::interruptActive/clearQueued` 及 runtime 中断装配；`cancellation-checkpoint-replay.test.mjs`，同一严格开关。依据 ADR-0047 §6.2。

### B5．手动换棒已经成功，旧执行进程停止失败后仍能领取旧任务

**用户可能在哪遇到：** 调度／管理侧执行手动换头，特别是旧进程退出失败时。不要把它泛化为所有自动接续：自动接续已有先停止、确认保存再读取快照的屏障。

**发生了什么：** 手动换头事务已经提交，平台把不确定任务列为待核对，随后停止旧进程失败，只记告警。旧 Viewer 注册身份仍然自洽，旧进程还能领取这条已经被列入待核对的任务。

**业务影响：** 新会话或人正在核实、甚至决定重发时，旧会话也可能继续做同一件事；有双重处理风险。管理接口仍返回成功，操作者容易误以为交接已彻底完成。

**确认到哪里：** 执行真实手动换头路由、持久事务与 Viewer 领取，注入停止失败后确认旧身份仍能领取；没有让新旧两边实际调用工具，因此不报告为已证实双重改文件。

**修复要求：** 换棒后旧进程不能再取得新的任务执行权。停止失败时，保留已提交的新会话事实，同时明确展示“旧执行尚未隔离”，不能用普通成功掩盖风险。是否允许新会话先做其他工作，见 D5。

**工程定位／证据：** `server/thread-control/thread-routes.js` 手动 head 路由；Viewer 注册与领取。`retirement-recovery-replay.test.mjs`，严格开关 `REQUIRE_RETIRED_RUNTIME_FENCE=1`。它把初轮只有模型／代码依据的风险推进到了真实组件回放证据。

### B6．已经明确放弃的旧任务，下次换棒又变成待核对

**用户可能在哪遇到：** 历史线程中存在旧格式投递记录，调度方已经把该事项明确标为“放弃”，后面又精简接续。原问题会重新出现在恢复清单或自动核对通知中。

**发生了什么：** 某些旧记录没有投递时间。系统每次接续都把它当成“无法归属哪一棒”的任务，却没有先排除已分类并明确处置过的同一任务，于是换一个待核对编号重新开项。

**业务影响：** 操作者反复清理同一旧事项；后继可能再次询问或建议重发。已确认的是待办重开，不是已经发生重复工具执行。影响范围为缺投递时间的兼容旧记录，不能说所有新任务都有此问题。

**确认到哪里：** 用旧格式持久记录作输入，真实换棒、处置 API、第二次换棒均执行；独立存储读取确认同一任务同时拥有已处置记录和新开记录。严格断言因“明确放弃后又重开”失败。

**修复要求：** 明确处置必须对同一原任务持续有效；再次换棒本身不能撤销人的决定。需要重启该任务时，应是另一次有记录的明确决定。

**工程定位／证据：** AgentDev `workthread/inbox.ts::classifyRetiredCommands` 对缺投递时间记录的分类、`core.ts` 待核对生成与处置。`unresolved-lifecycle-replay.test.mjs` 的 legacy 用例，严格开关 `REQUIRE_UNRESOLVED_RESOLUTION_FINALITY=1`。

## 二、后续处理事项：既定要求、实施细节与承诺边界

### D1．保存失败后，用户应该看到“已收到”“待恢复”，还是必须重新发送？

**关联场景：** B1、B2；聊天输入后保存报错、重启恢复。

当前已有“先存好再确认”的技术要求，但它不能自动决定用户看到什么。没有模型调用时可安全地保留并重试，与可能已产生外部效果后要求重发，是不同情形。

**实施需明确：** 是否统一把保存失败表示为“已接收，尚未可靠交给 Agent，等待恢复”；自动尝试到什么条件就转人工处理；不能确定时是否禁止直接提示用户“重新发送”。

**建议：** 平台持有恢复责任，明确提示等待／人工介入；先核实已有执行再重发，避免让用户承担重复操作风险。不用实现层错误直接要求用户猜测任务有没有做。

### D2．点击停止后，撤销的内容如何保留，又如何避免继续影响 Agent？

**已确认行为：** 在“会话已保存、取消先于接管确认”的窗口，当次模型没有运行，但下一条完全无关的请求仍把那条取消文本作为普通用户消息发给模型。

**用户出处与影响：** 输入框停止、线程中断之后继续聊天。用户可能遇到“我刚取消的事，后面又被 Agent 当要求”；回放只证实文本进入后续模型请求，没有证实模型一定照做。

**重要更正：** 首次报告称 ADR 没规定，现核对 ADR-0047 §6.3 已明确：取消残留只能作审计，不能驱动新执行。因此“允许后面继续执行取消任务”不应再列成同等可选方案；未定的是隔离和呈现方式。

**实施需明确：** 历史界面是否保留原文字并标“已取消”；后续模型完全不接收原指令，还是接收明确失效的审计摘要；用户说“继续”时是否必须明确指向这条取消任务才可恢复。

**建议：** 历史可读，指令失效。不要靠删除聊天记录隐藏事实，也不要把已撤销内容继续作为有效要求。

**证据：** `receipt-boundary-replay.test.mjs` 的 cancellation question；ADR-0047 §6.3。

### D3．“停止请求受理”和“全部停妥”应该分别怎样告诉用户？

**已确认行为：** Viewer 返回成功时，线程 Inbox 中某些取消结果还没异步回写；回写也可能失败。Web 输入框已显示“正在停止…等待当前步骤安全退出”，不是立即假装空闲，但当前步骤退出也不能证明所有层的取消都已同步。

**用户出处与影响：** 输入框停止、右键停止、Coder 中断。用户需要知道此时能否离开、是否还有旧任务可能开始、能否提交新任务。

**实施需明确：** 哪个状态才允许显示“已停止”；取消同步失败是否显示“执行已停止，但排队任务取消待确认”；是否需要用户能查看此次停止实际涵盖的任务。

**建议：** 受理、步骤退出、取消完成分别表达；只有后两项均满足，才展示没有保留条件的停止完成。新输入仍按 B4 的截点规则保留。

### D4．去重和“已取消”的记忆，应该保留多久？

**已确认行为：** 接收端只保留有限历史。真实执行 500 次后续消费后，旧任务的接收凭证会被裁掉；一次取消 501 条时，最早的取消凭证可立即被裁掉。此后同编号提交可以重新入队。

**用户出处与影响：** 长期无人值守任务、很久以后重试的外部客户端、大批量取消。用户通常不会直接看到这些凭证；可能感知为迟到的旧请求又被接收。

**现有约定：** ADR 已明确这是有界重试保护，普通 Inbox 不会自动重投 delivered 任务；显式重发本来就使用新编号。本轮没有证明正常业务会在超窗后重提同一旧任务并再次执行，所以不能把容量边界直接当作新 bug。

**两项容易误判的关联事实：** 默认精简保留正文时会丢掉逐条回执，完整保留区则留下回执，纯摘要不带逐条回执。条件回放中，同代旧任务配上无回执上下文确实再次进入模型；但正常接续已经换代，会拒绝旧代输入，不能拼接成正常接续必然重复执行。另一个回放确认：进程身份变了，旧进程的确认请求即使曾成功也会被拒绝，而同任务重新提交仍可在历史窗口内识别为已接收。这样保护身份是必要限制，不应为“所有重试都成功”而放开旧进程权限。

**实施需明确：** 继续接受有限窗口，还是“明确取消”需要比普通消费更长、更强的身份保留；超窗旧请求应拒绝、待核对，还是允许接收。

**建议：** 不承诺无限期业务只执行一次；对明确取消的用户意图，优先防止迟到请求悄悄复活。若保持有界窗口，客户端协议必须承担超窗处置，不能仅靠界面文案弥补。

**证据：** `deep-viewer-replay.test.mjs` 两个历史容量用例；`DEEP-MODELS.md`；ADR-0047 阶段 3。

### D5．换棒与旧会话未停妥之间，是否允许继续工作？

**关联缺陷：** B5。旧执行权未撤销已经是问题；如何收口是产品取舍。

**用户出处与影响：** 手动换头结果、线程接续状态。完全冻结更安全但降低可用性；继续运行新会话可能与旧任务冲突。

**实施需明确：** 旧进程无法确认隔离时，整个线程停在“交接待确认”，还是新会话可以做不涉及旧任务的工作；旧会话迟到的回复／工具结果如何标记，是否进入当前对话。

**建议：** 未隔离前至少冻结与旧任务相关的继续／重发；明显显示交接不完整，不回滚新会话事实，也不悄悄让新旧会话都继续。迟到输出与工具副作用尚需独立验证，不能只靠拒绝旧回执解决。

### D6．接续期间到达很晚的投递结果，可以等到下一次接续才核对吗？

**已确认行为：** Viewer 已接受旧会话的输入，但线程 Inbox 尚未记下成功；此时换棒。分类看见它仍是 pending，就不建立待核对；迟到结果随后把它记成 delivered。现有 G2 用例明确等下一次接续才将它归入待核对。

**用户出处与影响：** Coder 自动接续、手动精简附近发送任务。可能出现“平台记为已投递，但当前会话没继续，也没立即提示核对”的等待期。若没有下一次接续，现有这条兜底触发就不发生。

**实施需明确：** 接受等下一次换棒，还是迟到结果一到就核对；多久无人接管需要向用户／调度者提示。

**建议：** 不依赖“以后还会再精简”。迟到结果应触发对账，无法判断就明确待核对。它是已存在并被测试记录的边界，不是本轮新发现的回归。

**证据：** `test/thread-succession-timing.test.js` 的 G2；`SuccessionWindow.tla`。

### D7．未结清事项必须跨自动接续持续进入后继输入（已修复）

**确认的缺陷：** 真实 Agent 收到待核对通知，通知保存到会话；普通 trim 按既有策略过滤该 system 消息。第二次接续只检查新建未决项，没有为仍未结清的旧项生成通知，后继的真实模型请求不再包含该事项。持久记录仍可查询，但不能满足自动接续不依赖模型主动查询的发现要求。这是恢复链路 bug，不是业务取舍。

**用户出处与影响：** 长任务连续精简接续。旧疑问尚未结清，后继却可能继续其他工作，没有再核对。确认的是该事项从输入中消失，不是已经证明发生了重复部署等外部副作用。

**修复：** 框架换头事务在完成分类后，取全部仍未结清项构造当前后继的通知；通知与换头同笔持久化。返回值 `unresolved` 仍只代表本次新建项，不改变调用方的统计语义。通知标明每项来源会话，不把跨多代遗留都称作“上一棒”。已结清项不带入、同一后继不重复建通知、手动免播不自动启动。

**真实变换边界：** 普通 trim 的遗漏是确定的过滤行为；摘要与 trim＋摘要由可控模型返回遗漏文本，证明恢复不应依赖摘要忠实度，没有测量实际 LLM 遗漏概率。保留 system 的正向对照仍可发现原通知。修复后上述四条路径均在实际后继模型请求中看到未结清项。

**重启边界：** 真实 Viewer dequeue 交出机器通知后、runtime 保存前退出的窗口中，重新构造同数据目录的 Viewer，队列已空；待核对项仍在持久记录。另一路启动扫描回放确认，没有 pending／running 事实时不会仅因 open 项唤起。两者是组件级证据，尚未做完整宿主强杀和启动联测；不能宣布重启链路已闭合，也不能据此一律唤起 idle／failed／waiting_input，因为这些状态可能表示人为暂停或等待输入。当前修复保证再次自动接续会重新带入，但未修同代重启的通知再发现。

**验证与复跑：** `node --test specs/tla/unresolved-discovery-replay.test.mjs specs/tla/unresolved-lifecycle-replay.test.mjs`；真实 integration、Agent、FileSessionStore、官方变换、HandoffSeedFeature 与后继模型请求均执行，Bridge 传输和模型为可控边界，不启动正式服务。框架新增回归在修复前有两项目标失败；修复后 WorkThread 164 项、Claw 最终相关 108 项、类型检查通过。`check-unresolved-lifecycle.mjs` 保留旧行为反例并新增当前自动携带与手动免播对照，共 9 场景匹配。

### D8．普通用户在哪里看待核对项，谁能决定重发或放弃？

**当前可核实入口：** 查询／处置 API 为 `/protoclaw/threads/:threadId/unresolved` 与其 `/:unresolvedId/resolve`；CLI 手动换头响应会列出清单并提示 API 操作。自动路径会把新建清单送入后继输入。

**用户侧缺口：** 检索当前 Web 前端，未找到专门消费此集合的待核对列表、提醒标记和三种处置控件。不能把后台能查询说成普通用户已经有入口。这里是源码核查结论，没有浏览器逐页验收。

**业务影响：** 产品设计要求“由人核对”时，用户可能只能读恢复消息或请开发者调用接口；无人值守调度者也可能不知道还有事项未结清。

**实施需明确：** 清单放在线程详情、消息流还是侧栏提示；Agent 可否自行标“已处理／放弃”，什么情况必须人确认；重发前是否要展示“旧动作可能已发生”的风险。

**建议：** 每条事项可见原要求、来源会话、不确定原因和处置记录；允许 Agent 核实并报告，但对无法撤销的外部动作，缺证据时交人确认，不自动盲目重发。

### D9．归档线程后，还允许安排“解档再做”的任务吗？

**已确认行为：** 归档保留待核对事实并暂停调度，但不是 closed。当前处置 API 允许对归档线程重发，生成 pending 指令；hold 挡住投递。closed 线程则拒绝重发，允许放弃／确认已处理作审计。

**用户出处与影响：** 归档列表、运维／调度方处置 API。用户可能以为归档后只读，却仍有新任务悄悄积存在其下。解档本身不等于要求继续执行，需明确后续动作。

**实施需明确：** 归档后仅允许审计收口，还是允许排好“解档后执行”的任务；解档后自动处理还是必须再点继续。

**建议：** 默认不在归档状态静默安排新执行；若提供“解档后执行”，作为明确动作呈现，与恢复归档本身区分。现有归档不是终态，不能未经裁决简单套用 closed 规则。

**证据：** `unresolved-lifecycle-replay.test.mjs` 的 archive、closed 两个用例；`server/thread-control/thread-lifecycle.js`。

### D10．临时故障结束后，系统承诺自动恢复，还是等人重新触发？

**已核实边界：** 接续身份采纳失败后命令保持 pending；runtime-ready、换头、追加输入或显式投递可触发重试。启动扫描唤起失败只记报告，不在该扫描内自动重试。delivered 记录不当作 pending 重投。模型中的“最终推进”依赖明确恢复和调度前提，不能自动变成产品承诺。

**用户出处与影响：** 服务器重启、执行进程启动失败、短暂通信故障后，任务可能一直排队，直到下一次有触发事件；用户难以分辨“正在自动重试”与“已经等人处理”。没有完整验证所有触发链均会卡住，因此这里登记为恢复承诺待明确，不是又一个确定停滞 bug。

**实施需明确：** 哪些故障自动恢复、哪些转为人工；何时展示待处理与最后失败原因；已投递却不知是否接管的任务由谁对账。

**建议：** 对可安全重试的接收／身份故障自动恢复，并暴露失败状态；对可能已执行的任务先核对，不盲目重发。队列文件损坏／隔离后的恢复、断电持久性另需专项验证，当前未取得足够证据，不列成已确认新 bug。

## 三、历史故障：已经修复，不再列入待修清单

### H1．两个换棒请求竞争时，落败请求把正常竞争误报成接续失败

首次试验顺带发现 G3：一个换棒请求已经成功，另一个迟到请求没有正确作废，反而走失败分支，可能把线程记成接续失败。它是常规回归测试发现，不应算作 TLC 独有发现。

当前 Claw 已有 `a8fd4e84` 修复，将失去提交前提的请求归为幂等作废；本轮完整时序文件与相关回归通过。旧导出和首份报告保留了当时失败，不代表当前仍坏。它保护的用户体验是：并发请求不应把已成功交接的线程重新弄成失败状态。

## 四、建议你如何确认

建议先确认产品底线，再安排修法，不必先审阅 TLA 语法或选内部字段：

1. **可靠接管：** 没有可靠存档，不算交给 Agent；“已接管”与“已完成”分开。对应 B1、B2、D1。
2. **停止范围：** 停止前的未消费输入取消，停止后的新输入保留；历史可读但撤销指令不能再当有效要求。对应 B3、B4、D2、D3。
3. **交接隔离：** 旧执行未隔离就明确标交接不完整，不允许同一任务由两棒同时接手。对应 B5、D5、D6。
4. **恢复责任：** 未结清事项持续可见、跨代可发现；明确处置不会因换棒自动撤销。对应 B6、D7、D8。
5. **长期与人为暂停：** 去重窗口、归档后重发、自动恢复边界分别决定，不能用一句“最终会恢复”概括。对应 D4、D9、D10。

以上处理方向已获批准；工程实现须服从已有契约，不把明确错误重新交由产品选择。D7 自动接续修复已验证，B1—B6 与其他后续事项仍按各自状态推进。
