# ADR-0046: 插件管理产品体系（三级装配与配置三层）

日期：2026-11-08
状态：Accepted（概念模型全量对齐；实现按落地顺序推进）
关联：[ADR-0045](0045-external-plugin-package-and-workspace-assembly.md)（本 ADR 修订其决策 5 的 scope 语义）、[产品蓝图](../plans/2026-11-08-plugin-management-product-blueprint.md)、[实施计划](../plans/2026-11-08-external-plugin-package-ui-binding.md)

## 背景

ADR-0045 落地了外部插件包机制：单 tgz 三面（工具/UI/数据）、Claw 层仓库导入、
工作空间装配分离，并以 agentero 出仓完成端到端验证。机制可用之后，产品定义层
的缺口在实测中集中暴露：

1. **面板可见性上下文未定义**。agentero 面板声明 global scope 后在所有界面出现
   ——包括未装配它的工作空间、甚至无 runtime 激活的工作空间首页。右栏到底
   "跟什么绑定"没有答案。
2. **插件配置无产品级入口**。vault 路径这类参数借住在 Feature 配置的四层作用域
   编辑器里，语义错位（vault 属于数据面/UI 面的属性，却挂在"某身份的 Feature
   参数"层级下）；插件卡片上没有"设置"动作；面板自身的呈现偏好（每页条数、
   视图模式）则完全无处安放。
3. **多工作空间配置联动无语义**。数据面挂载时取第一个装配身份的合成配置——
   "编程小助手配 vault A、Coder 配 vault B"做不到也说不通；面板在哪个上下文
   该读哪个 vault 未定义。

与此同时，产品面存在多入口概念冲突：商店货架卡片与右侧 Features 面板共用
feature-card 结构（插件与 feature 两个层级视觉不分）、上传 tgz 入口藏在
工作空间设置深处（与"导入是 Claw 级仓库动作"的定位不符）、Agent Studio
自带独立的 Feature 仓库面板（与统一插件仓库概念冲突）。

本 ADR 定义插件管理的产品体系全景：术语、三级装配、配置三层、生命周期、
兼容承诺与过渡策略。机制层契约（manifest v3、资产通道、挂载机制）以
ADR-0045 与实施计划为准，本 ADR 管产品形态"是什么、在哪、归谁"。

## 决策

### 1. 术语与包模型

- **插件（Plugin）** = 一个 tgz 包，是导入、装配、处置的唯一单位；内部至多
  三个面：**工具面**（agent 调用的能力，即 feature）、**UI 面**（右栏面板）、
  **数据面**（给面板供数的服务路由）。
- **feature** 降为插件工具面的组成单元，只在运行时视图（右侧 Features 面板）
  呈现，不再是用户操作的宏观单位。
- **builtin 官方可选插件**（playwright-shell、lsp 等）并入统一处置语义：三态
  （装配/禁用/卸载）与分级（全局/工作空间）与 tgz 插件完全一致；差异仅三点
  ——无包坐标、不可删除、随宿主升级。插件页卡片以来源徽章区分。

理由：用户操作心智只保留"插件"一个宏观单位。builtin 与 tgz 插件的差异是
分发事实，不是处置语义——两套开关心智的成本高于统一的小妥协。

### 2. 三级装配体系（本 ADR 核心）

**装配层级 = 可见性层级**：

| 级别 | 装配动作 | 面板可见范围 |
|---|---|---|
| 全局级 | 全局设置中安装 | 所有界面（含任何工作空间首页） |
| 工作空间级 | 各工作空间插件页安装 | 该工作空间内界面（含其首页） |
| 对话级 | 创建对话时声明 | 仅打开对应对话/runtime 时右栏显示 |

- **修订 ADR-0045 决策 5**：manifest 的 `ui.panels[].scope` 降级为**装配建议**
  ——作者标注"这个面板适合装到哪一级"（如跨空间工具建议装全局），实际可见性
  由用户装配层级决定。scope=global 不再意味着"随导入即可用、处处可见"。
- **对话级装配 = 会话参数**：与 `cwd` 同等地位，不进配置树；分支、精简、接续
  继承源会话的插件集（与线程化会话身份语义，ADR-0032，保持一致）。

理由与备选：对话级装配曾考虑按对话寻址的配置层文件（配置树第三种粒度），
被否决——配置树是静态分层的，对话是动态实体，把装配声明挂进配置树会让两套
生命周期（配置层文件 vs 会话快照）互相纠缠；会话参数继承会话身份的既有语义，
无新增规则。

### 3. 配置三层体系

| 层 | 例子 | 用户入口 | 存储 | 声明方 |
|---|---|---|---|---|
| **插件参数** | vault 路径、功能开关 | 工作空间设置 → 插件「设置」 | 配置树四层（global/workspace/project/directory） | 作者（manifest settings，JSON Schema properties 形态） |
| **面板偏好** | 每页条数、视图切换 | 面板本体上的设置控件 | 服务端 KV，键 = 工作空间 × panelId | 作者（面板内自绘控件） |
| **呈现配置** | 面板显隐、右栏排序 | 右栏自定义弹窗 | 服务端，随工作空间 | 宿主 |

三条设计规则：

- **分层与否按"是否需要跨空间统一治理"划分**。插件参数分层（全局默认 →
  空间覆盖 → 工具面独有的项目/目录层）；面板偏好与呈现配置**纯空间级、不分层**
  ——每个空间从零开始，无全局默认。偏好和布局是空间的私事，参数需要跨空间
  统一治理。
- **按面寻址**。工具面读全四层（会话有目录上下文）；数据面读 global + 装配层，
  面板请求由宿主注入当前视图的工作空间标识、数据面按请求上下文合成——
  "编程小助手的面板读 vault A、Coder 的面板读 vault B"由此定义；UI 面只读，
  经数据面接口取合成值，不开第三条写通道。
- **panelPrefs 契约**。claw-host 协议扩展 `host.panelPrefs.get()/set()`，宿主
  负责存储、多空间隔离、跨设备一致；面板作者只管渲染设置控件和读写 API。
  与呈现配置共用服务端基础设施，同期实现。

作者分界约定：影响多面或服务端行为的进 manifest settings；只影响本面板怎么
画的进 panelPrefs。三层各自的消费端不可互换——插件参数驱动行为（改了内容变），
面板偏好驱动长相（高频轻调整，就地配），呈现配置驱动布局（跨面板统一管）。
三个问题三个去处，按使用频率分布入口：低频重决策在设置深处、中频轻调整在
使用现场、布局管理在布局现场。

理由与备选：曾考虑把面板偏好也声明进 manifest settings（DSH 模式——所有配置
统一 settings 页），被否决：DSH 是单机单用户应用没有分层需求；Claw 多工作
空间、多设备浏览器访问，"每页条数"这类高频偏好若藏进工作空间设置深处，
用户会放弃配置。面板上就地配置符合"在哪用在哪配"的直觉。

### 4. 工作空间持有清单

一个工作空间在插件体系里持有四样数据，构成其自主处置面：

| 数据 | 内容 | 特点 |
|---|---|---|
| 装配清单（$mount） | 挂了哪些插件、什么版本 | 空间自主处置的锚点 |
| 空间层参数覆盖 | 配置树 workspace 层的插件参数值 | 插件参数分层体系的空间层 |
| 面板偏好 | 每面板一份 KV | 纯空间级 |
| 呈现配置 | 面板显隐排序 | 纯空间级 |

插件包本体与多版本仓库由 Claw 层持有。装配、参数、偏好、呈现是不同的树，
但装配声明与插件参数共用配置树文件（$mount 是配置树里的特殊键）——不另立存储。

### 5. 版本与处置

- **版本策略：钉精确版**。装配声明写精确版本；升级走插件详情页显式"升级到 X"
  动作（导入新版 → 仓库多版本并存 → 装配改指新版）。不支持 range 自动跟随。
  理由：第三方代码自动升级违背 digest 纪律的保守性；手动升级路径已足够轻。
- **处置三态**：装配 / 禁用（声明与配置全保留、三面整体下线、随时启用回来）/
  卸载（声明置 null、配置留在层文件、三面退场）。仓库删除 tgz 前置检查无任何
  层级装配引用。处置单位始终是插件包，不做面级拆开。
- **生效边界**：UI 面与数据面即时；工具面随该工作空间 runtime 下次启动
  （新开会话即得）。与既有装配边界语义一致，不引入热挂载。

### 6. 兼容承诺

ClawHost 面板协议面（declare / ensurePlugin / mountBody / panelPrefs 等宿主
注入接口）随 agentdev **minor** 版本冻结；破坏性变更升 major，且保留一个
major 版本的兼容垫片。第三方作者依据 `engines.agentdev` 声明兼容范围。

理由：第三方插件生态的可信度建立在宿主协议稳定上。此前该承诺一直悬空
（实施计划开放问题 4），本 ADR 将其落为正式决策——panelPrefs 契约加入后
一并冻结，冻结范围即 claw-host 的宿主注入面。

### 7. 通用原则

纯产品体验的小细节、不涉及本质决策的，一律先按**保守方向**实现——后加能力
成本低（如给版本策略补 range 跟随是微小工程），先收紧不会错。此原则适用于
本体系后续所有实现决策，避免在细节上过度设计。

### 8. 过渡与愿景

- **Agent Studio 过渡形态**：数据源统一到同一插件仓库 catalog，保留开发语境
  专用浏览视图（包结构、验证账本、运行记录——消费端不关心这些），不成为
  第二装配入口（制造端不装配，装配只发生在消费端）；视觉对齐插件卡片语言。
  长期重做为**插件产出端**：产出完整插件（不止 feature），这是 Studio 的
  演进方向，本 ADR 只锚定方向、不定义其契约。
- **插件定义整个工作空间**（一个插件声明并提供完整 APP 型工作空间，DSH 表层
  组合包的形态）列入愿景、不进 manifest v3 契约；待第一个真实需求出现再升 v4。
  理由：现有 APP（memo、agent-studio）都是深度宿主耦合的，插件化工作空间的
  成本收益当前看不清，预留空契约比晚加契约便宜。

## 后果

- **可见性合成逻辑重写**：`composePanelDeclarations` 从"按作者 scope"改为
  "按装配层级合成 when"；全局级装配入口（全局设置插件区）为前置依赖。
- **配置入口与契约新增**：插件设置弹窗（复用三态编辑器组件）、panelPrefs
  宿主契约、呈现配置从 localStorage 迁服务端（随工作空间持久化 + 一次性迁移）。
- **数据面挂载语义变更**：从"取第一个装配身份的合成值"改为"按请求上下文
  合成"，面板请求携带工作空间标识由宿主注入（插件作者无感）。
- **builtin 开关升级**：独立开关形态升级为三态 + 分级，原开关行为兼容映射为
  已装配/未装配两态。
- **ADR-0045 的 manifest v3 契约不变**（三面声明、digest 纪律、导入流程）；
  `scope` 字段按本 ADR 第 2 条重新解释为装配建议。
- 对话级装配引入会话参数位（创建对话时声明插件集），消费会话创建流程与
  分支/接续的继承路径。

## 落地顺序

1. 插件卡片「设置」入口 + 设置弹窗（复用三态编辑器，先解决配置入口层级痛点）
2. 全局装配入口 + 可见性按装配层级合成（三级体系主体，含 scope 语义调整）
3. 数据面请求上下文（多空间配置联动）
4. 呈现配置迁移 + panelPrefs 契约（同款基础设施，一起做）
5. 禁用语义、资产懒解出自愈、卡片视觉分层、术语收口

各步实现细节与验收见[实施计划](../plans/2026-11-08-external-plugin-package-ui-binding.md)
与[产品蓝图](../plans/2026-11-08-plugin-management-product-blueprint.md)。
