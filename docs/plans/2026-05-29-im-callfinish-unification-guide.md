# 执行手册 4：IM 回复机制切换到 CallFinish

> 适用对象：熟悉 QQ / 微信门户代理与 IM 工作空间语义的 agent
> 优先级：中高
> 前置条件：第 3 份文档完成，系统已存在统一完成事件或等价接口
> 目标：让 QQ / 微信从“onCall 直接回调回复”切换到“订阅 callfinish 统一出结果”

---

## 这份文档的根目标

你要解决的是这个产品语义问题：

> 哪怕一次调用不是从 IM 端输入的，只要该 runtime 或门户代理绑定了 IM，IM 也应该能看到结果。

当前障碍在于：

- IM 更像调用入口的一部分
- 回复动作和某次 `onCall()` 的直接调用栈绑得太紧

所以你要把 IM 改造成：

**输入来源之一 + 结果订阅出口之一**

而不是：

**谁触发 onCall，谁自己当场回调回复**

---

## 允许修改的文件

主要关注：

- [prebuilt-agents/official/qqbot/agent.js](D:/code/AgentDevClaw/prebuilt-agents/official/qqbot/agent.js)
- 和 QQ / 微信门户工作空间配置有关的 `server.js` 区域

可能需要配合第 3 份文档留下的事件接口。

尽量不要改：

- `node_modules/agentdev/**`
- `dispatch` 底层恢复逻辑
- Viewer 输入基础逻辑

## 你要建立的新语义

对 IM 而言，一次调用需要拆成两件事：

### 1. 输入来源

如果消息来自 QQ / 微信，它是：

- `source = qq`
- 或 `source = weixin`

### 2. 结果出口

当某个 envelope 完成时，系统根据策略决定是否把结果投递到：

- 原会话
- QQ
- 微信
- 只在失败时通知
- 只推送摘要

也就是说，IM 不再天然等于“输入来源”，它也可能只是“结果出口”。

---

## 建议引入的结果策略

你可以实现一个轻量策略字段，名字自行决定，但语义建议包含：

- `none`
- `session-only`
- `im-mirror`
- `im-primary`
- `notify-on-failure`

最低要求：

- 至少要能表达“把结果同步到 IM”
- 至少要能表达“只在失败时通知 IM”

如果这轮不方便把策略完全暴露到 UI，也没关系；可以先在后端 / runtime 默认策略里保留接口。

---

## 推荐实现步骤

### 第 1 步：确认 callfinish 事件载荷

先与第 3 份文档产物对齐，确认完成事件至少带有：

- `envelopeId`
- `runtimeKey`
- `source`
- `sourceRef`
- `response`
- `error`
- `completed`

如果没有，请在你的提交结果里明确阻塞点，不要私自重新设计一套事件。

### 第 2 步：把 IM 回复从直接 onCall 副作用中拆出来

目标：
- 不再依赖“谁调用了 `onCall()`，谁立刻回复”

你需要识别当前 QQ / 微信回复是在哪里被触发的，然后把回复动作移到 callfinish 订阅侧。

注意：
- 如果当前框架或 feature 内部仍有直接 reply 行为，你要谨慎处理，避免双发。
- 必要时可以先做“非 IM 来源通过 callfinish 补发，IM 原来源仍保持兼容”，但最终提交时要说明是否仍有双轨。

### 第 3 步：建立 IM 结果分发器

你可以新增一个小层，例如：

- `deliverCallResultToIM(...)`
- `dispatchIMCallFinish(...)`

职责：
- 根据 runtime / session / workspace 配置判断发往 QQ 还是微信
- 根据 reply policy 决定是否发送
- 统一格式化结果文本

### 第 4 步：定义默认行为

这一步很重要，因为产品语义需要稳定。

建议默认规则：

1. IM 来源触发的调用：仍然向该 IM 渠道回复结果
2. 非 IM 来源触发的调用：
   - 若 runtime 绑定 IM 门户且策略允许，则同步结果到 IM
   - 否则仅保留在会话中
3. 失败结果可以比成功结果更高优先级地推送

### 第 5 步：控制噪音

不要让 IM 成为刷屏机器。

建议至少做一项：

- 超长响应只发摘要
- 工具细节不全量外发
- 失败时保留更完整信息，成功时偏摘要

---

## 验收标准

完成后至少满足：

1. 一次非 IM 来源的调用，在策略允许时，IM 能看到结果。
2. IM 来源的调用仍然能正常回复。
3. 不出现明显双发。
4. QQ 与微信的回复逻辑尽量共享一套结果出口语义，而不是各自再分叉。

---

## 最低验证场景

你至少要验证：

1. 从 QQ 触发一次调用，确认还能收到回复。
2. 从微信触发一次调用，确认还能收到回复。
3. 从 dispatch 触发一次调用，在 runtime 绑定 IM 的情况下，确认 IM 能看到结果。
4. 失败调用能否按策略推送到 IM。

如果你没有真实 IM 环境，至少把模拟验证路径和缺失点写清楚。

---

## 你不要做的事

1. 不要在这里自己重构 dispatch 状态机。
2. 不要在这里再设计一套新的 runtime queue。
3. 不要在这里改调试器输入框行为。

你的职责是：

**把 IM 从“调用副作用”改造成“统一完成事件的结果出口”。**
