# ADR 0023: 工具调用历史改写——工具自声明生效调用，框架零语义判断

日期：2026-10-07
状态：已接受

## 背景与问题

模型发起工具调用后若不符合工具要求（参数形态不规范、旧名/别名、缺省值未补全），现状的唯一处理路径是"如实返回错误 → 模型读到错误 → 下一轮重新调用"。每循环一次消耗一轮 LLM 调用，且历史里留下一段失败的尝试；对于别名类场景，模型甚至没有"错"可言——它只是用了旧写法。

诉求：工具在执行时自行修正调用（参数规范化、别名映射到正式工具），并把这种修正**写进模型看到的历史**——下一轮模型看到的就是修正后的调用，如同当时就是这么调的。典型场景：

1. **参数自修正**：工具按修正后参数执行成功，历史记修正后参数。
2. **A→B 改名**：模型调了别名/旧名 A，实际按正式工具 B 执行，历史记 B。
3. **A→B+C 展开（跨 feature）**：本 ADR 不裁决，方向记录见"不做清单"。

可行性依据（读代码验证，非推测）：

- 模型看到的历史由框架构造：`Context.getAll()` → `llm.chat()` → provider 适配层纯函数编译（`anthropic.ts` / `openai.ts` / `openai-responses.ts` 把 `toolCalls` 编译为 `tool_use`、tool 消息编译为 `tool_result`）。
- LLM API 对历史唯一硬约束是 `tool_use ↔ tool_result` 按 id 配对完整；id 由框架生成，provider 不校验 id 背后的调用是否真实发生过。保持 id 不变、只改 name/arguments 的改写在 wire 层完全合法。
- 体系内已有同类先例：ADR-0002 确立"历史是变换的产物"（trim/summary 即历史变换）；output-guard 经 ToolResultTransform 截断工具结果；react-loop 的 max_tokens 截断防御为未执行的调用注入"结果"——"模型看到的 ≠ 实际发生的"已是既成事实。

## 决策

### 1. 能力原语：工具执行体声明"实际生效的调用"

`ToolExecResult` 扩展 `effectiveCall?: ToolCall`：id 与原调用一致（配对不变），name / arguments 为实际生效值。框架在结果写入历史时，将 assistant 消息中 id 匹配的 toolCall 替换为 effectiveCall。改写只作用于 toolCalls 与对应结果的配对呈现；assistant 正文与 thinking 块原样保留，框架不做剥离。

### 2. 框架零语义判断（哑改写）

改写是"等价规范化"还是"实质修正"、要不要在结果中解释修改、正文与改写后调用是否语义自洽——全部归工具作者。工具想解释，就在返回内容里自带说明字段；协议上它是普通数据，框架不认识、不校验、不降级。这是 ADR-0007"注册表是哑的"同一哲学的又一次贯彻：权力归作者，责任归作者，框架只做机械替换。

（决策过程注：本条最初方案为"框架分级——等价静默、实质修正强制携带差异说明，说明缺失降级为如实报错"。评审中推翻：语义等价不可自动判定，框架分级终将演化为替作者做判断。哑框架版本由用户裁决定案。）

### 3. 声明制：改写权仅属于工具执行体自身

工具定义显式声明本工具的调用可被改写；改写声明（effectiveCall）只能由该工具执行体在自身执行过程中发出。未声明工具的结果携带 effectiveCall 视为框架错误。不存在第三方 feature 改写他人工具调用的路径——跨工具诉求属于场景 3，另行裁决。

### 4. 改写目标必须在本 agent 工具清单内

effectiveCall.name 必须是当前 agent 已注册的工具，否则视为装配错误。这保证模型认知自洽（它看到的调用名是自己认识的工具），并使改名场景产生训练迁移价值：模型看到自己调过 B，逐渐学会直接调 B。

### 5. 双视图：模型看改写后，用户看真实

- **模型视图**（LLM 输入）：改写后的调用。
- **用户视图**（DebugHub 与 Claw 前端，两条渲染管线同规则）：工具卡片主体显示生效调用（与结果配对，保持叙事连贯），带"已修改"标注，可展开查看原始调用。原始调用快照由框架在改写时自动附加到结果消息的前端展示元数据（display，不注入 LLM）。
- **IM 渠道**：零改动、零感知，转述模型回复原文。

用户是最终审计者：改写 bug（错误修正、静默滥用）必须始终有界面可见路径，这是双视图存在的根本理由。

### 6. 持久化单轨 + 事实层审计

会话快照只存改写后历史——branch / trim / summary / checkpoint 全部下游变换天然一致，不存在"两个真相"。原始调用的完整对照记录于结构化日志（改写事件携带原始与生效值）；无头 JSONL 事件流按写入时刻发射原始调用（先于改写），事实层不被污染。

## 不做清单（显式边界）

- **不做改写语义分级、校验、强制说明、降级报错**——见决策 2。
- **不做别名退役机制**：A 是否继续注册由装配者手动管理；迁移效果（模型是否已学会直接调 B）查结构化日志。
- **不做快照双轨 / tombstone 式改写归档**：留给未来出现真实需要时再加。
- **不做跨工具/跨 feature 改写**（场景 3）：方向已记录——宿主中转的 sub-call 协议（工具执行上下文注入 invokeTool，走完整 ToolExecutor 治理链，含深度上限、环检测、预算共享），与 ADR-0007"共享权威状态与跨 feature 事务上移宿主"的裁决一致。实施前另行 ADR。
- **不做 thinking 剥离**：框架不做"改写时是否剥离 thinking"的选择，正文与 thinking 原样保留；语义自洽性归工具作者。

## 后果

**正面**：失败重试循环消除（一次执行成功替代"报错→重调"整轮）；别名收敛获得训练迁移路径；工具作者获得参数规范化的完全自主权，且无需框架理解任何业务语义。

**代价与风险**：

- 框架无法阻止工具作者把实质修正静默化——事实层日志是唯一兜底，审计依赖日志链路完整（无头事件流在写入时刻发射，天然可靠；Debug 日志依赖分级配置）。
- 改写使 provider prompt cache 的前缀失效——影响集中在最近一条 assistant 消息时最小（参数自修正与改名的典型时序正是如此）。
- 双视图意味着前端两条管线（Claw 前端 1420 与 DebugHub 2026）都要实现标注呈现，漏一条则该管线的用户失去审计入口。
- `Context.apply()` 现状只同步主消息数组、不同步 enrichedMessages 与查询索引——该缺陷必须在本能力落地前修复，属实施计划的前置项。
