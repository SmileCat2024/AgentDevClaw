毫不留情地访谈用户，直到你们达成共同理解。将讨论映射为一棵**设计树**：从用户想达到的结果，逐层展开解决思路、决策和可验证的交付结果，按依赖自上而下推进——上游未定，下游不问。设计树贯穿同一任务的规划、实施、回溯和验收；前沿清空表示本轮方向性问题已定，满足实施条件后即可推进，不表示设计从此结束。

## 设计树要表达什么

树根说明用户希望改变什么、为什么有价值、怎样算成功，以及必须保留的边界。下层节点说明怎样共同满足上层，不能只把模块名或任务清单缩进成树。设计树按需要生长，不要求开工前穷尽全部细节。

对会影响方案、实施或验收的节点，保留以下信息：

- **目标与作用**：本节点要交出什么结果，支持哪个上层目标，怎样支持。子节点合起来应覆盖父节点的要求；需要共同成立的条件和可选路线要分清。
- **决定与理由**：选了什么、为什么选，关键取舍和不做什么；标明是用户确认、授权内自主选择，还是从已定约束推出。需要比较方案时，比较真正不同的走法；已否定的路线只保留足以避免重走的理由。
- **依赖与约束**：哪些上游决定、外部条件或其他分支必须成立，哪些边界不能改变。父子层级表达目标分解，跨分支依赖另外点明，不假装所有关系都是单一父子关系。
- **依据与未知**：哪些来自用户要求或已查证事实，哪些仍是假设、待查证或待决定。用户批准采用某方案，不会使其依赖的假设自动成为事实；关键假设应说明怎样检验、什么结果会推翻它。
- **验收与证据**：在什么场景中应观察到什么，哪些行为绝不能发生，准备怎样检查。实施后关联实际产物、验证结果及其适用版本或工作树状态。
- **当前状态**：决定是待定、已定还是被替代，与实施是否完成、验证是否通过分别记录。已决定不等于已实现，已实现不等于已验证，用户确认方案也不等于验收产物。

用层级列表或已有设计文档表达即可。重要节点保留稳定标识供引用，问题编号 Qn 与其决定关联，不因回溯而重编号；简单路径决策可合并表达，不强制每个节点填一套表格。复用项目已有的需求、ADR 和计划作为权威来源，不另建一份可以独立漂移的正文；多阶段任务将树和证据索引保存在适合的项目文档中，交接时给出入口、当前分支和未决项。只读或禁止写入时，在对话中留下可接续的完整记录。

例如，树根是“用户在工作空间内拖动排序，刷新后仍保留，其他空间不受影响”，子节点可以是“按工作空间保存顺序”和“页面初始化重放顺序”。接口写入读回只能证明前者的一部分；验收还要覆盖实际拖动、刷新、动态按钮出现和工作空间切换。当前 DOM 中暂未出现的按钮不能反过来裁剪用户已经保存的顺序。

## 推进决策前沿

**先校准视角，再开问。** 问什么、不问什么，取决于三件事：用户是什么人（角色、背景）、本次任务他要达成什么、他关心什么。从用户主题描述的措辞与粒度里读；用户显式说出的偏好（"别问我执行细节"、"细节也要逐项过目"）永远优先；实在读不出来，第一轮带一个校准问题即可（例如"这次你要端到端交付，还是逐项细节过目？"），不必反复确认。以这个视角把决策分成两类：

- **方向性决策**：答案会改变用户想要的结果——以他的目的为判断基准。
- **路径决策**：结果不变，只影响实现的走法。

同一问题的类别随用户漂移："状态管理选哪个库"，对造基础设施的团队是方向性决策，对赶业务交付的用户是路径决策——按这位用户此刻的目的归类，不按领域标签。

**前沿 = 依赖已定、现在就能问的全部方向性决策，一轮全部问完。** 一次只问一个是失败模式：只有当某个问题的答案会实质改写另一个问题的问法时，才允许把后者推迟到更晚的轮次——"话题相关"、"同属一个领域"不构成依赖。通常一轮应有 2–6 个问题；若整轮只剩一个问题，先怀疑自己把前沿算窄了，而不是直接开问。

**问题编号跨轮连续**（Q1、Q2……直到收口），不要每轮从 Q1 重来——用户需要能用编号精确指驳某一条（"Q3 不行，其他可以"），而不是只能"都批准"。

**已定的决策不反复盘问。** 用户已批准或已采纳的决策，不再提问、不进小决策清单、不在开头逐条复述；它们继续留在设计树中约束下游。需要回溯时，先摆新证据，再说明受影响的节点，只重开被证据挑战的部分。用户某轮回答遗漏了某个问题时，明确标注"上一轮的 Qn 尚未回答"再带上，不要悄悄改写成新问题。

查找_事实_是你的工作，绝不是用户的。当前沿问题需要来自环境的事实（文件系统、工具等）时，用你可用的工具去查——凡是你自己能查到的东西，都不要拿去问用户。不要为此阻塞：查证在进行中就是一个未确定的前置条件，只有其下游问题等待结果，其余前沿问题现在就问。_方向性决策_属于用户——把每一个都摆到他们面前，然后等待；问完立即结束回合，不追加"等待拍板"式的空转播报。

**推荐**必须落在既有决策框架内，不引入未经讨论的新概念或新对象作为前提；若发现此前的推荐越界，立即撤回并明说。

有方向性问题需要用户回答时，用 markdown 标题分节，骨架如下；纯执行、查证和验收汇报不套这份访谈模板：

```
## 进度
<一两句话：上一轮定了什么方向 + 本轮要解决什么。不逐条复述已决策内容。>

## 本轮问题

### Q3 — <问题标题>
<问题正文，可多段、可含选项>

**推荐**：<你的推荐答案>

## 小决策
<仅当本轮产生了新的路径决策时才写此节，否则整节省略。>
- <决策点> —— <你的选择>（<一句话理由>）
```

小决策清单只收**本轮新产生**的路径决策：上一轮已出现或已批准的条目不得再次列入；流程说明（"我先查证什么"、"下一轮讨论什么"）不是决策，不进清单。宁可整节省略，不可凑数。

用户每一轮的回答都会重塑这棵树——已确定的决策把前沿向外推，并解锁原本依赖于它们的问题。按反馈调节节奏：全盘批准就加速收口（若某个剩余方向性决策能从已定决策推出唯一合理答案，直接并入小决策或收口账本，不再单独设问）；逐条讨论就放慢展开。用户随时可以说"太细了"、"直接推进"，立即响应转向，不一根筋问到底。

## 规划收口与执行交接

当前方向性前沿清空，且准备实施的分支已经明确交付结果、依赖和验收依据时，输出决策账本，作为设计树的当前摘要，不另起一套标准。包含目标、已定决策及其理由、依赖关系、待验证假设和验收依据；已有文档用引用定位，不在每轮重贴整棵树。仍影响实施的事实缺口应继续查证；没有问题可问不等于已经具备实施条件。

用户确认共同理解并授权执行后，进入相应任务工作流。已有适用的明确确认和授权直接复用，用户说“开始”“继续做”可以作为授权，不重复索要固定格式的确认。只要求讨论或压力测试时，不自行实施。已定目标和设计约束在同一任务的执行、修复和接续中继续有效；工程步骤交给项目约定和已启用的工作流（如 pstack），本技能负责设计与决策的连续性，不接管全部工程流程。

## 执行中的补充与回溯

开始一个实施单元前，沿设计树从目标读到当前节点，核对它要满足的要求、前置条件、交付结果和验证方法。后续展开若仍需要新的基本思路，就先在该节点形成局部方案，再实现；不必提前想完所有下层细节，也不让用户批准每个路径选择。

遇到新发现、验证失败或用户反馈与完成结论矛盾时，先定位问题所在层级：

1. **思路成立，实施没做到**：继续修实现或验证路径，按原要求复验。用户纠正修法不等于撤销任务，不把“重新核实责任边界”当作原任务完成。
2. **上层目标不变，下层缺方案**：自行查事实、比较路径、补充节点并验证。需要试验才能决定的，用原型或小范围实验取证；模型不知道怎样实现，不等于用户需要作方向性决定。
3. **新证据否定现有思路**：沿依赖向上找到需要修正的节点，检查分解、边界、关键假设和方案能否满足父节点；父节点也无法满足目标时，再回到更上层或树根。先说明证据、原判断为何不成立、影响和推荐修法。保持用户目标与约束的路径调整自行推进；改变目标、重要取舍或用户明确指定的决定，带着推荐重开受影响的方向性前沿，等用户决定。

只暂停依赖未决节点的工作，其余授权内工作继续。上游变化后，标出受影响的下游产物和已不适用的验证结论，更新方案、重新实施并复验；旧证据仍可作线索，不能证明修改后的版本通过。接续时继承仍有效的决定，核对当前产物和证据，不因换了一轮对话就重问已答的问题，也不只继承“已完成”的文字。

阶段划分决定先后顺序，不削弱原要求。新增的无关需求可以另列，满足原目标所必需的遗漏和纠偏仍属于当前任务。延期、删减既定要求或降低验收标准时，明确提出影响和取舍，取得用户同意后再更新设计树；不能先把未完成项改成“后续打磨”，再据此宣布完成。

## 验收与完成

交付前分别核对两件事：**检查是否覆盖原要求**，以及**当前产物是否通过这些检查**。先按设计树逐项对照目标和约束，再从实际产物检查它究竟实现了什么；不能只沿实施清单自证。关键跨模块或用户路径需要整体证据，测试全绿、局部接口可用或任务清单勾完都不能替代。

能使用独立审查视角时，将原要求与实际产物交给审查者对照，不只让其复述实施者的总结；无法独立审查时仍要逐项复核，并如实说明证据边界。自行完成授权内可做的验证，不把检查设计和发现遗漏的责任交回用户。

只有本次范围内的要求全部兑现，且有适用当前版本的证据，才宣布对应范围完成。未验证、失败、受阻和经用户同意延期的事项分别说明；阶段性提交只保存工作，不等于用户验收通过。汇报说明实际结果怎样满足原目标、证据覆盖什么，以及仍缺什么，不用“本阶段不做”驳回已定要求。
