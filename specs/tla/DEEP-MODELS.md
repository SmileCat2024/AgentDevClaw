# 回执与接续协议的深化检查

## 运行与定位

```bash
node specs/tla/check-deep-models.mjs
node --test specs/tla/deep-viewer-replay.test.mjs
```

Java、工具版本和依赖构建要求同 [README](README.md)。基准为 Claw `b5507f7e` / AgentDev `47a8c5f7`。生产代码未修改。驱动器生成每个场景的配置，并将模型副本、完整输出和提交身份保存到 `artifacts/deep-*/`。四份 `ReceiptBoundaryDeep-*.cfg` 是可直接交给 TLC 的独立配置；完整检查矩阵以驱动器内的场景声明为准。

驱动器退出 0 表示所有预期通过、预期安全反例、预期活性反例均按声明得到结果。它不表示所有业务性质通过。解析错误、超时、不完整状态赋值与意外性质失败均使驱动器失败。每个场景单 worker、固定 seed/fingerprint、1GB 堆、60 秒上限。

## 两个模型为什么分开

`ReceiptBoundaryDeep.tla` 描述一个 Viewer agent/session 槽位及其消费客户端：持久队列、内存 Context、最后成功快照、租约所属 runtime/head 代际、有界消费和取消历史、取消截点、响应丢失、一次重启、一次身份替换、一次迟到重投。

Viewer 的消费确认不等于直接把 WorkThread Inbox 标为 consumed。`SuccessionWindow.tla` 单独描述 Inbox 与两个 head runtime：投递开始捕获目标 → Viewer 接受 → Inbox 记录结果，允许交接、hold、关闭插入其间。pending 命令投递时才绑定当时 head，而不是入箱时绑定旧代。

这种分解保留两个持久化域的不同语义，但不构成两个模型自动组合后的整体证明。

## 已运行场景与结论

| 场景 | 性质/假设 | TLC 结果 | 能说明什么 |
|---|---|---|---|
| baseline | 内存捷径 + 一次保存失败 | `AckRequiresSnapshot` 反例 | 原发现 1 在深化模型仍可达；原实现回放已有证据 |
| fencing | 两命令、重启、注册身份替换、响应丢失 | 534 状态完整探索 | 本槽位内旧身份不能修改队列消费结果，FIFO、去向和正常持久化性质保持 |
| fifo-three | 三命令、正常保存 | 493 状态完整探索 | 模型内队首领取与多命令处置没有被两命令范围掩盖 |
| history-eviction | 两命令、历史容量缩为 1 | 重新准入反例 | 有界历史不能提供无限期去重 |
| cancel-history-eviction | 批量取消两命令、容量 1 | 取消项重新准入反例 | 批量取消本身即可裁掉最早的取消凭证 |
| retry-after-identity-change | ack 成功、响应丢失、注册身份替换 | 无条件幂等 ack 性质反例 | 身份 fencing 优先于消费历史命中；幂等不跨任意 runtime 身份 |
| liveness-fair | 三命令、固定身份、一次保存失败/重启/响应丢失，始终重新保存，不走原内存捷径；消费主链弱公平 | 1,213 状态完整探索并检查时序性质 | 在这些前提下队列最终全部消费或取消；不是当前所有运行模式的活性证明 |
| liveness-no-fairness | 不约束调度 | 时序反例，exit 13 | 即使存在可执行动作，也不能从安全性推出系统必定推进 |
| mutation-lease | 模型故意绕过身份 fencing | `NoCrossIdentityAck` 反例 | 对应性质可以发现被模拟移除的身份校验 |
| mutation-fifo | 模型故意改领队尾 | `FifoClaim` 反例 | FIFO 观察点确实有辨别力 |
| succession-safety | 两命令、挡板、hold/close、两代 head | 1,128 状态完整探索 | 门禁后不新启动投递；不禁止门禁前已发起请求继续完成 |
| succession-late-classification | 接收完成与 Inbox 标记之间换 head | 分类空窗反例 | 对应已有 G2 测试，不是新发现；后续显式扫描才可能发现该项 |
| succession-inflight-old-runtime | 换头时旧 runtime 注册仍在 | 旧 runtime 接受反例 | Viewer 本地身份 fencing 不等于立即隔离全局已退役 head；属于更强性质探针 |

这些是有限范围模型检查；没有声称任意命令数、任意历史长度或无限进程恢复均成立。状态数用于核对完成性，不代表验证强度的排名。

## 实现回放与断言来源

`deep-viewer-replay.test.mjs` 在独立临时目录构造真实 ViewerWorker，不启动 HTTP/UDS、不连接生产服务；使用实际提交、领取、ack、注册身份和取消原语。四个用例均执行并通过：

1. 三命令 FIFO；重复领取返回同租约；换 runtime 后旧回执拒绝、新租约可确认；同身份 ack 重试成功。
2. 已消费回执在 runtime 身份变化后仍被拒绝，而同 commandId 重提交返回 consumed。区分请求身份校验与内容去重。
3. 真正运行 500 个后继消费：第 499 个后继消费时旧回执仍命中，第 500 个后继消费后旧回执被裁掉；此时旧 ack 拒绝、旧命令提交重新 queued 并可领取。不是把实际容量偷偷改成 1 来回放。
4. 真正提交 501 条并一次取消：最新与边界内命令仍拒绝，最老取消项重新 queued。取消调用实际原语，不声称验证了 interrupt HTTP/UDS 全链。

其中历史边界用例是观察性实验，不把重新准入认定为正确产品要求。未模拟模型客户端、未执行后续业务副作用，因此不能由重新入队或领取推导“重复业务执行”。Snapshot 自身的回执去重、上游是否会在如此久之后重投、持久化 Inbox 如何限制重投，都需要联合证据。旧身份 ack 拒绝可能是必要安全行为，不能因为无条件幂等探针给出反例就移除 fencing。

## 深化中排除的假反例

首次草稿错误地要求每条命令只能领取一次；TLC 指出了“未保存即崩溃后重领取”合法路径。最终模型不把领取次数当业务执行次数。草稿还有无限增长计数，导致不能完成状态空间探索，已改为有界事件/集合；没有靠截断搜索来声称通过。

原两个问题暂不修复。模型始终区分当前行为、安全契约与更强的语义探针，不通过增添理想化恢复动作使检查变绿。

## 本轮最终核验

13 个深化场景均得到其明确声明的结果；原 4 个基准场景结果保持不变。两份实现回放合并执行 6 个用例、6 通过、0 失败（约 0.83 秒）。另行运行已有真实 Viewer HTTP 的 G2 时序用例，1 通过、0 失败；没有把上轮 G3 的已知失败排除后声称整个文件通过。

本次深化模型日志位于 `artifacts/deep-ttxqx0/`，基准日志位于 `artifacts/run-tn67Rh/`，回放日志为 `artifacts/all-replays.log` 与 `artifacts/g2-replay.log`（均是本机未入 Git 的运行证据）。旧 runtime 在全局换头后仍接受在途请求，仅有模型与注册/投递代码依据；本轮未另建端到端回放，不把它报告成新增已证实产品 bug。

## 剩余盲区与下一步价值

- **传输与租约细节**：当前一个在途客户端，runtime/head 身份代表租约所有权，未显式枚举 lease UUID、多个并发 claim/ack 请求与旧响应重排；需另建多请求网络模型再与回放对照。
- **接续证据一致性**：当前 commit 使用完整当下消费证据；读取在事务外，证据陈旧、缺失、损坏与跨文件快照不是同一原子动作。这里是下一项高价值深入方向。
- **退役与恢复全链**：接续模型保留旧 runtime 接收能力，但未覆盖实际停止进程、迟到模型输出、失败回滚、归档/删除并发、重启后的 registry 重建。不能用当前通过结果证明这些流程。
- **历史裁剪端到端后果**：Viewer 有窗口的事实已确认；是否造成重复执行或取消失效，要把上游请求生命周期、Session 回执恢复/精简与去重组合起来验证。
- **活性假设**：弱公平要求持续可执行的消费主链最终获调度。真实轮询、失败退避、runtime-ready 事件是否满足它尚未验证；身份替换后队首代际不匹配可能合法阻塞，不能靠虚构清队列动作修复模型。
- **存储故障**：未建模文件损坏后隔离重置、rename/fsync 的断电语义、Viewer 保存失败、跨宿主共享目录。仅覆盖 Session 保存失败与进程级 Context 丢失。
- **模型维护**：检查的是手写抽象，无自动代码一致性证明。变更身份/保存/接续协议时需要更新映射并重跑实现回放。模型变异证明性质能发现指定错误，不证明实现不存在其他错误。
