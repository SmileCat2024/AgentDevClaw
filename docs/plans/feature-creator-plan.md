# Feature Creator 产品化方案（对话承载版）

> 状态：方案定稿，待实施
> 前置阅读：[adv-vs-dsh-strategy-2026.md](adv-vs-dsh-strategy-2026.md)（总体战略，本文是其体验层/工作项 B·C 的产品化展开）

## 1. 背景

### 1.1 现状：只是一个简易 demo

当前的 feature creator 由三部分拼成：

- `agentdev-create-feature` 脚手架 CLI（独立 npm bin，生成工程骨架——这部分是好的，保留）
- feature-dev feature（local-features，1628 行）：四态模式（plan/code/debug/package）+ `featuredev_package_to_repository` 打包入库工具
- 开发者自己去翻面向"整个 agent"的调试界面

它不能支撑真正复杂的 feature 开发流程，病根有三：

1. **四态是提示词纪律，agent 靠自觉**。agent 说"进入 debug 态"，但代码可能没保存、挂载可能失败、它自己都不知道——状态活在 agent 记忆里，不在现实里。
2. **开发循环被发布流程绑架**。每次改动要走 build → npm pack → 入库 → rm node_modules + npm install → 重启 agent（丢会话），单轮 30 秒到 2 分钟。这套流程是为正式交付设计的，被错误地摊到了每一次调试迭代上。
3. **没有定向观测**。调试器面向整个 agent。开发 feature X 时作者要的是"X 的钩子为什么没触发、X 的工具结果被谁改了、X 的注册面变没变"——现在只能人肉从全局信息里捞。

### 1.2 与 dsh 的关系

dsh 的"创造模式"（cordis preset）验证了**对话承载开发**是赛道的正确形态：标准编码 agent + cordis_inspect/define/run 工具族 + 420 行 skill 纪律。我们确认沿用对话承载这个共识，但在两个点上做出代差：

1. **dsh 教 agent 守纪律（skill 教义），我们给 agent 事实流**——纪律会漏，事实不会。
2. **dsh 的热插拔为不可信代码设计**（eval 约束 + 审批 + 多轮等待协议 + 无 import/TS，官方自认"probing, not shipping"），我们承认开发场景注入的是本机可信源码——免审批、完整生态、秒级生效。

### 1.3 刻意的取舍记录

**曾考虑并被否决：IDE 式三栏工作台**（左源码树 / 中试运行 / 右时间线）。否决理由：放弃对话承载等于放弃本项目的核心产品形态（人与 agent 在对话里协作），退回传统 IDE 赛道与成熟工具竞争。**对话是唯一承载；平台不做新界面，做 agent 可消费的能力后端。** 现有调试界面保留为"深看模式"（人主动深挖时用），不进开发主流程。

**另一个刻意取舍：不做独立的"开发沙盒界面"**。沙盒 agent 本身要做（试运行隔离是刚需），但它以对话中的一方存在（开发 agent 与之交互），而不是一个需要人操作的独立窗口。

## 2. 目标形态（一句话）

**对话是唯一入口和承载；feature 的写、挂、试、看、验、交付六个环节全部在对话里闭环，由平台事实流驱动 agent 的每一步判断。**

```
写（agent 改源码）→ 挂（热载 2 秒生效）→ 试（沙盒对话）
→ 看（定向时间线卡片）→ 验（一键回归）→ 交付（打包入库）
```

## 3. 发力点一：给 agent 心智的开发流程（事实流状态机）

### 3.1 核心改造

四态从"提示词纪律"升级为**平台事件驱动的状态机，状态回灌 agent 上下文**：

```
真实事件链：源码保存 → 热载成功/失败 → 沙盒试运行 → 回归通过 → 入库
平台回灌：  每次事件把事实注入对话上下文
            （"feature v3 已挂载，工具 4 个，钩子 2 个，上次回归通过"）
```

状态定义（替代 plan/code/debug/package 的四态）：

| 状态 | 进入条件（平台事实，非 agent 声明） |
|---|---|
| draft | 有未热载的源码变更 |
| mounted | 热载成功（工具/钩子注册数回灌） |
| verified | 最近一次回归通过 |
| packaged | tgz 入库，版本号回灌 |

### 3.2 为什么这是代差

- agent 不再需要"记住"自己改了什么、挂没挂上——平台事实说话，"我已经测过了"这类幻觉从机制上消失。
- agent 的每一步建议基于回灌的事实而不是记忆，长会话开发不退化。
- 对比 dsh：它的 skill 用 420 行教 agent"先 inspect 再写码、不要推断 API"——这是把正确性押在模型遵循纪律上；我们把正确性押在"agent 看到的就是现实"上。

### 3.3 事件回灌通道

复用现有 viewer 双向通道的推送机制（push-messages）：热载结果、回归结果、注册面 diff **不是等 agent 来查，是平台主动推到对话里**——失败带报错，成功带卡片。agent 下一轮发言自动看见，零查询成本。

## 4. 发力点二：调试平台基础能力（feature 定向）

现有资产直接复用：debugger 的 query_logs/get_hooks 工具族（支持按 feature 过滤日志/钩子快照——地基现成）、viewer 推送通道、generative-ui 卡片组件族。新增四项 feature 定向能力：

### 4.1 能力清单

| 能力 | 形态 | 干什么 | 地基 |
|---|---|---|---|
| feature 定向查询 | 工具 | 一次调用拉出该 feature 的事件流：工具调用与结果、钩子触发记录（按 Observe/Guard/Transform 分类显示，Guard 显示决策与理由，Transform 显示前后 diff） | query_logs 已支持 feature 过滤；三原语（战略文档工作项 A）落地后分类数据即结构化 |
| 热载执行 | 工具 + 自动触发 | agent 改完代码即挂载，2 秒生效；失败自动回退旧实例并回灌报错 | reloadFeature（战略文档工作项 B） |
| 沙盒管理 | 工具 | 起一个隔离试运行 agent（空白 / 最小工具集 / 克隆某个现成 agent 配置三选一）；沙盒会话随便造，炸了重开，与真实 agent 完全隔离 | 现有 agent 启动机制 |
| 一键回归 | 工具 | 装配四查 + 工具 schema 校验 + 钩子约束测试 + 回滚兼容测试，结果回灌状态机 | 内部测试装置产品化（hook-constraint-verify、feature-rollback-compat 等 28+ 测试文件已有） |

### 4.2 人怎么看

全程在对话里：agent 推送视图卡片（热载 diff 卡、回归结果卡、feature 时间线卡——generative-ui 现成），点开看详情，操作回到对话（"把工具 X 的超时改大点"）。不做独立工作台。

### 4.3 交付环节收敛

package 态从"检查清单纪律"变为：dev 态验证通过后一条命令转正式包，manifest 元数据自动附带最近一次回归结果。开发态与发布态同一份源码、同一个 Feature 类、同一套原语，无断层——对比 dsh 动态模式与正式 composition file 之间的能力断层（官方自认 "a capability belongs in a composition file"）。

## 5. 与 dsh 创造模式对照（对外叙事依据）

| | dsh 创造模式 | ADV feature creator |
|---|---|---|
| 承载 | 对话 | 对话（共识形态） |
| agent 状态来源 | skill 纪律 + 模型自觉遵循 | 平台事实回灌，无幻觉空间 |
| 开发循环 | define → 审批 → 多轮等待 steering | 保存 → 2 秒热载 → 事实自动推送 |
| 能力上限 | 动态插件无 import/TS/JSX | 完整 TS + npm 生态 |
| 失败恢复 | undefine 重来 | init 失败自动回退旧实例 |
| 观测 | inspect-first 全局查询，要 agent 会问 | feature 定向事件流 + 主动推送 |
| 验证 | 无系统化回归 | 一键回归，结果锚定状态机 |
| 试验→交付断层 | 存在（probing vs composition file） | 不存在（同一份源码直达 tgz） |

一句话：**dsh 的 agent 在"遵守开发流程"，ADV 的 agent 在"活在开发现实里"。**

## 6. 分期

| 阶段 | 内容 | 交付判据 |
|---|---|---|
| P0：demo 变可用 | 沙盒 + 热载 + 事实回灌 + feature 定向查询 | 对话中改源码保存 → 2 秒生效 → 会话不丢 → init 失败自动回退 → agent 下轮发言引用挂载事实 |
| P1：可用变可靠 | 一键回归 + 状态机完整（verified 态）+ 打包收敛 | 回归通过/失败直接决定 agent 能否宣布"可交付"；tgz 入库附带回归结果 |
| P2：可靠变协作 | 工作区依赖（feature A 依赖开发中的 feature B，本地目录直联、同时热载）+ 推送卡片打磨 | 双 feature 联调场景跑通 |

依赖关系：P0 依赖战略文档工作项 A（三原语，分类观测数据源）与 B（reloadFeature）；沙盒依赖现有 agent 启动机制，无前置。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 事实回灌注入过多内容挤占上下文 | 回灌走紧凑摘要（一行状态 + 关键数字），详情按需用卡片/工具拉取 |
| 热载后旧模块实例泄漏（cache-busting 每次新实例） | reload 编排内统一 dispose 旧实例钩子/定时器；框架身份判断钉死 feature.name 字符串键 |
| 沙盒 agent 与真实 agent 配置漂移导致"沙盒过了生产炸" | 沙盒第三模式（克隆现成 agent 配置）覆盖主流验证场景；装配预检在两侧同跑 |
| dsh 补上热载体验（cordis-host-runner 演化） | 本文属体验层窗口牌：作用是窗口期钉住"feature 长在对话里"的品类心智，长期防守靠范式层（见战略文档 §3） |
