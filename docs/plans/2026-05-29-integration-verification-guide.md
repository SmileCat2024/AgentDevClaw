## 核查目标

### A. Dispatch 状态机是否收口

重点确认：

1. `__latest__` 不再导致 runtime key 写错
2. `fired` 不会永久悬挂
3. 过期 timer 不会永久 `pending`
4. `on-ready + repeat` 重启后仍工作
5. `on-idle` 至少不会因一次丢 respond 就永久僵死

### B. Runtime 调用入口是否唯一

重点确认：

1. 是否还存在多条活跃的直接 `agent.onCall()` 路径
2. dispatch、常驻输入框、普通输入是否都受同一仲裁器约束
3. 同一个 runtime 同时收到多条输入时是否串行

### C. IM 结果出口是否统一

重点确认：

1. IM 来源还能正常回复
2. 非 IM 来源在策略允许时，IM 能看到结果
3. 不会明显双发

### D. UI 状态是否与底层事实一致

重点确认：

1. pending / fired / completed 显示是否合理
2. 队列气泡是否与真实队列漂移过大
3. runtime running / idle / queued 是否至少大体可信

## 推荐验证步骤

### 第 1 组：单 runtime 串行性验证

场景：

1. 启动一个带 `UserInputFeature` 的 runtime
2. 连续提交两条常驻输入
3. 在第一条尚未完成时再触发一条 dispatch

期待结果：

- 不会并发直接撞进 `onCall()`
- 三条请求会以可观测顺序被串行处理

### 第 2 组：dispatch 恢复验证

场景：

1. 创建 timer 调度
2. 创建 `on-idle`
3. 创建 `on-ready + repeat`
4. 创建 `__latest__` 目标调度
5. 在不同状态下重启 server

期待结果：

- 不出现永久 `fired`
- 不出现永久过期 `pending`
- `on-ready + repeat` 能续上

### 第 3 组：IM 结果验证

场景：

1. 从 IM 触发一次调用
2. 从 dispatch 触发一次调用
3. 让其中一条故意失败

期待结果：

- IM 源调用仍有回复
- 非 IM 源调用在策略允许时能同步到 IM
- 不明显双发

### 第 4 组：回归验证

确认这些旧能力没被破坏：

1. 普通 programming-helper 对话
2. exploration session 运行
3. 调度台创建 / 取消 schedule
4. runtime 自动启动

## 建议补的测试或验证资产

能写自动化就尽量写，优先级建议：

1. dispatch 恢复逻辑的单元或小集成测试

## 你的底线任务

你最终要回答的不是“代码看起来不错”，而是下面这几个问题：

1. 同一个 runtime 现在是否真的只有一个执行入口？
2. `dispatch` 重启后是否真的不会再明显积尸体？
3. IM 是否已经从输入副作用变成结果出口？
4. 现有 UI / 状态展示是否还能被人信任？

如果这四个问题有任何一个你不能给出偏肯定结论，请明确写出来，不要模糊带过。
