# 宿主投递面：永久滞留死锁与投递活性假设边界

日期：2026-11-18。状态：宿主投递滞留缺陷已修复并经构造性复现与 TLA 前后对照验证；宿主投递模型已细化并按 ADR-0047 §4 修正线程宿主/普通会话路由边界；产品决策项为 D11（滞留可见性）及 D12（投递活性承诺边界，生产可达性待验证）。D13/D14 曾由未区分路由域的模型推导，已撤回为生产断言。本文承接 [2026-11-17 裁决清单](2026-11-17-tla-product-decision-register.md)：D10 中“接续身份采纳失败后命令保持 pending”边界已升级为确定缺陷并修复。

## 先读结论

本轮形成三项结果：

1. **滞留死锁已修复**：受控复现（真实生产模块 + 两处故障注入）证明“身份错位 + 触发点耗尽”时，修复前的自愈路径不再触碰该指令；实现加入周期对账与 force 重投，并通过构造性复现和 TLA 前后对照验证。
2. **宿主投递面模型已细化**：`HostDeliveryPlane.tla` 明确表达投递触发点、线程级退避、runtime 生命周期、身份采纳和 ready 信号。模型及场景持续按当前代码与 ADR 校准；首轮细化曾把线程宿主和普通会话的直投合并，后续已更正，不再把该轮 D13/D14 当作生产结论。
3. **保留有依据的边界问题**：无限换头和 runtime 崩溃循环在模型假设下可导致活性失守；滞留期间的用户可见性仍待产品决策。漂移风暴只作为尚待生产验证的模型反例，不视为确定缺陷。

## H2．身份错位 + 触发票耗尽 → 指令永久滞留（已修复）

**用户可能在哪遇到：** 编程小助手 / Coder 线程会话中，恰逢换头后身份采纳失败（adopt-thread-head 失败不回滚换头，server.js 路由注释自认"失败只能靠重启收敛"）。用户发"继续"等指令，提示"已暂存"，之后永远不执行，只能手动接续或重启救活。

**发生了什么：** 换头提交后、runtime 采纳新身份前，宿主注册表条目与 runtime 实际采纳的 head 代际是两个可分离的事实（双真相源）。错位窗口内投递被 viewer fencing 永拒（`runtime_not_accepting_input`，可重试失败——指令保持 pending 且盘上无任何失败痕迹）。而修复前的三个自愈机制看的都是宿主侧"条目在位"同一个事实：`ensureHeadRuntime` 对在位条目直接返回 ok；requeue 扫描对在位条目跳过；delivery-consumer 无自驱动定时器。触发点（gateway 即时投、runtime-ready 补投）烧完投递尝试后，没有任何一方会再碰这条指令。

**确认到哪里：** 三层证据链，全部可复跑：

- **构造性复现**（`test/thread-pending-stall-deadlock-repro.test.js`，真实 `createThreadControl` + 真实框架 `WorkThreadRuntimeBridge`，仅注入"宿主条目在位"与生产同形的 fencing 拒绝错误）：指令保持 pending 且 attempts 不变（解释了为何事后无现场）；退避窗口后模拟新消息触发重试，仍被拒；`ensureHeadRuntime` 回答"一切正常"；pending 老化 120 秒后连跑两轮 `requeueStalledPendingThreads` 零行动；对照用例证明换头（手动接续）立即送达——与用户症状闭环。
- **TLA+ 模型**（`specs/tla/HostDeliveryPlane.tla`）：`fencing-deadlock-pre-fix` 场景死锁态可达（安全形式，无需活性假设）；`liveness-pre-fix` 场景在完整弱公平假设下活性失守（exit 13）——证明这不是调度运气问题，公平性救不了修复前语义；细化轮新增 `allgreen-stall-pre-fix` 场景把 wt-1ab8a75b 的"一切健康但永久静默"窗口也钉成可达（修复前触发面上没有任何 action 对滞留指令负责）。
- **变异验证**：临时回退修复的跳过条件，两条自愈断言立即失败；恢复后重过——断言锚定的是"扫描零行动"行为本身。

**修复：** `thread-succession.js` 的 requeue 对"条目在位 + 滞留超过水位（60s）"增加对账：先 force 重投（`tryDeliver` 新增 force 通道绕过幂等窗口），仍错位则做身份采纳重试（复用换头事务的采纳路径）再复投；janitor 周期自驱动，不依赖外部触发点。修复后 `liveness-post-fix` 场景活性通过（干扰预算有界时：换头 3 + 崩溃 2 + 漂移 2）。

**验证：** 相关测试 116 项全过（delivery-consumer / succession / control / 新复现测试三用例）；原细化版 TLA 15 场景全匹配。后续修正路由域后，TLA 场景矩阵增至 16 项并再次全匹配（最新记录见重跑日志）。与 D10 的关系：D10 登记的"哪些故障自动恢复、哪些转人工"整体仍是产品决策，但其中"身份采纳失败类滞留"已按本轮修复落为自动恢复。

**修复边界（未覆盖）：** 采纳失败本身的根因（为什么 adopt-thread-head 会失败）未查——本轮修的是"失败后不自愈"这一层；采纳失败时的即时重试（而非等 janitor 水位）与用户可见性见 D11。

## D11．滞留期间用户应该看到什么（可见性承诺）

**关联：** H2；2026-11-18 凌晨报告的"已暂存 18~34 秒"现象。

**已确认行为：** 冷启动窗口内"已暂存"提示先于 runtime 就绪出现，属按设计暂存；但同一文案也覆盖了 H2 的永久滞留形态。指令被 fencing 拒绝不落盘任何痕迹（attempt 计数不变、无 lastError），滞留水位告警挂在 delivery-consumer 的 consume 路径上——修复前恰好是没人调用的那条路径。修复后 janitor 有日志，但用户可见面没有变化。

**用户出处与影响：** 线程会话发指令后长时间无响应。用户无法区分"正常暂存（秒级）"、"交接窗口（15s 级）"与"投递反复被拒（需干预）"——正是本轮线上报告误判为卡死的直接原因。

**实施需明确：** "已暂存"是否按滞留时长升级为分级文案（暂存中 → 交接中 → 反复投递失败请检查）；投递失败痕迹要不要持久化（attempt/lastError）并在会话或线程详情暴露；滞留告警的归属从 consume 路径移到 janitor 后，水位与通知渠道是否调整。

**建议：** 文案分级 + 失败痕迹持久化。不承诺永久重试，但让"没发出去"这件事本身可见——H2 修复消除了静默死锁，D11 要消除的是静默等待。

## D12．投递活性的假设边界（即使修复后仍成立的饥饿类）

**模型结果（不是生产故障证明）：** `HostDeliveryPlane.tla` 把投递活性依赖的环境前提显式化。在无界干扰配置下，换头风暴、runtime 崩溃循环、漂移风暴和采纳反复失败均有 TLC 时序反例（exit 13）。这些场景证明抽象模型在相应环境假设下不能保证活性；生产可达性须分别核实。D12 记录的是承诺边界与待核查假设，不等同于已确认的生产饥饿类。

1. **换头尝试持续阻挡对账**：模型允许 begin/abort 无限循环，导致每次 janitor 扫描都撞上挡板；没有挡板最终收敛假设时，pending 不能保证送达。生产接续调度是否可能形成该无限序列，尚未由本次调查证实。
2. **runtime 持续崩溃**：模型允许 starting 后无限次 spawn fail / restart harvest，runtime 无法稳定到达可投递态。生产是否会持续自动重启、是否有熔断与告警，需要按 supervisor 策略另行验证。
3. **绑定漂移风暴**：模型两拍抽象允许 janitor 每次看到 foreign 后只唤醒重绑，并在下一扫描前再次漂移。生产扫描周期为 15 秒，但模型没有约束漂移动作的频率；当前没有证据证明 shared-by-project 生产调度能以该频率反复拉走同一 runtime。因此这是模型反例，不登记为生产饥饿缺陷。

这些反例共同说明：仅有 janitor 弱公平还不足以推出投递最终完成；还需挡板最终开放、runtime 有机会稳定到达 ready、采纳最终成功等环境前提。`adopt-repeat-starve` 也只说明模型在永久采纳失败下失去活性，生产失败是否永久持续尚未验证。

**用户出处与影响：** 本次没有生产复现上述无限干扰序列；可能相关的无人值守场景包括连续接续、runtime 拉起失败与共享 runtime 被借用，但需采集真实日志或建立调度回放后再作判断。它们不能与已复现并修复的 H2 静默死锁混为一谈。

**后续验证方向：** 对接续重试、supervisor 重启和 shared runtime 会话切换分别核实触发频率、退避/熔断条件及可观察状态。若发现生产能持续阻断 janitor 完成对账，再据证据决定是否需要修正两拍收敛或增加滞留告警；当前不为模型假设预先引入产品承诺。

## 模型边界复核：线程宿主与普通会话的路由域

细化模型曾把所有 runtime miss 统一表示为“直投”：当绑定漂移到 foreign 会话时，`offthread-direct-reachable` 于是得到 direct 终态，并据此将 D13/D14 写成生产行为。核对 `server/thread-control/input-gateway.js::_resolveThreadRoute` 与 ADR-0047 §4 后，确认这是模型过度泛化，不是已证实的生产缺陷：

- 线程宿主 APP（如 Coder）的 session 归属查到 WorkThread head 时，输入进 Thread Inbox；查到历史成员时返回 `session_not_head`。现增加的 fail-closed 修复进一步规定：线程宿主 runtime 已存在但归属记录无法解析时返回可重试的 `thread_ownership_unresolved`，不再降级 Viewer 直投。
- 普通非线程 APP 不参与 WorkThread 路由，继续按 Viewer 当前 user-turn 语义直投。此路径不代表线程队列语义，也不能拿来证明线程消息会跨路径超车或落入无关会话。

因此：

1. 原 `direct-overtake-reachable` 反例只证明“若线程宿主在归属缺失时可直投，则可能跨路径超车”；现行契约和修复都排除此路由。线程宿主场景已改为 `thread-host-no-cross-path-direct`，验证绑定漂移下没有 direct 命令；普通会话保留 `plain-session-foreign-direct` 作为独立域对照。wt-1ab8a75b 的历史现象不能仅凭旧模型归因于此路由，仍需按原始运行记录确认其实际输入入口和 runtime 绑定。
2. 原 D14“foreign 绑定时线程输入静默落到其他会话”撤回为生产断言。模型现已把线程宿主 fail-closed 与普通会话直投区分；目前没有证据证明线程宿主用户输入会走到 foreign session。
3. `starve-drift-storm` 仍是模型反例：若绑定在每个 janitor 扫描前持续漂移，唤醒与对账两拍可能永远无法完成。但生产 janitor 每 15 秒调用一次，漂移动作在模型里可任意插入；这不足以证明生产调度允许无限高频漂移或已出现用户可达饥饿。先作为待验证的模型边界，不登记为确定 bug 或产品决策。

**处理结果：** 不以 D13/D14 要求改变产品行为；按 ADR-0047 §4 修复线程宿主归属解析失败时的 fail-open 直投。模型场景保留为“域区分与反例辨别力”测试，不把普通会话直投路径提升成线程 FIFO 或会话落点承诺。

## 方法论注记（试验体系自身，不占裁决编号）

- **活性性质的空转陷阱**：`<> (\A i : cmd[i] # "pending")` 形状的否定式从"Init 无 pending"出发不可满足，TLC 永远报告通过——本轮实测踩过，必须用 leads-to（`pending ~> delivered`）。已审计既有模型：`ReceiptBoundaryDeep` 的 `EventuallyDisposed` 因 Init 队列非空而成立，`UnresolvedLifecycle` 已用 `~>`，均无此问题。
- **弱公平性的 action 重合陷阱（细化轮实测）**：TLA+ 的 action 是状态对谓词，不是产生者身份；效果完全重合的转移也满足该 action。若用户切回操作与 janitor 唤醒分支状态变化相同，`WF(JanitorActs)` 可能被用户操作代偿，而未表达定时器实际经过。模型通过 `sweepTick` 布尔翻转为扫描加入专属状态变化。此修正保证模型中的扫描公平性有独立身份；它本身不证明生产会发生漂移风暴。
- **TLA+ 多行合取按 `/\` 列对齐决定层级**：重构 action 时 THEN/ELSE 关键字或合取项缩进错位，UNCHANGED 会被静默解析进错误分支（TLC 报"successor state not completely specified"）。列对齐是语法结构的一部分，不是排版习惯。
- **哑效果变量必须有界**：定时器计数器用 `Nat` 递增会让状态空间无限，TLC 无法终止；哑效果只需要"变化与否"的区分，布尔翻转足够。
- **TLC 活性只认真实转换环**："无任何 action 使能"的纯停滞对 TLC 活性检查不可见——死锁类必须配可达性不变式（本模型的 `NotDeadlockFencing`）才能进入 TLA 体系。这解释了为什么宿主层死锁此前在所有模型中隐形。终态（全部送达、无 action 使能）经 `-deadlock` 关闭死锁误报后成为合法自环，由活性性质判定。
- **递减计数器消灭精确环**：干扰预算若随每次干扰递减并进入状态，饥饿 lasso 的精确状态环就不存在（TLC 找不到环），且状态空间随预算值线性爆炸（实测 999 预算下安全场景膨胀至 270 万状态）。本模型的解法：`Bound*=FALSE` 时无限干扰且不递减计数器（保留精确环），`TRUE` 时才递减（假设显式化）。
- 工程细节：TLC cfg 不接受负数字面量、常量替换不展开定义。
