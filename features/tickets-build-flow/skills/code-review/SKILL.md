# Code Review — 双轴评审

对 `HEAD` 与用户指定的固定点（fixed point）之间的 diff 做两轴评审：

- **Standards** — 代码是否符合本仓库成文的编码规范？
- **Spec** — 代码是否忠实实现了来源 issue / spec？

两轴各自独立进行，互相看不到对方的推理，避免上下文污染（宿主支持并行子代理时优先并行执行；不支持时也必须作为两次独立检视，先完整做完一轴再做另一轴），最后聚合两份发现。

## 流程

### 1. 锁定固定点

用户说的就是固定点——commit SHA、分支名、tag、`main`、`HEAD~5` 等；没说就问，不要猜。

一次性确定 diff 命令：`git diff <fixed-point>...HEAD`（三点，按 merge-base 比较）；同时记录提交列表 `git log <fixed-point>..HEAD --oneline`。

继续之前确认固定点可解析（`git rev-parse <fixed-point>`）且 diff 非空。坏的 ref 或空 diff 应该在这里失败——而不是在两条并行检视进行到一半时。

### 2. 确定 Spec 来源

按顺序找来源规格：

1. 提交信息中的工单引用（`#123`、`Closes #45`、GitLab `!67`）——若仓库配置了 issue tracker 说明则按其取回。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/`、`.scratch/` 下与分支名或功能名匹配的 spec 文件。
4. 都没有就问用户 spec 在哪；用户确认不存在时，**Spec 轴跳过**并在最终报告注明 "no spec available"——绝不凭代码反推需求。

### 3. 确定 Standards 来源

仓库里任何记录"代码应该怎么写"的文档，如 `CODING_STANDARDS.md`、`CONTRIBUTING.md`。

在仓库文档之上，Standards 轴始终携带下面的 **smell 基线**——一组固定的 Fowler 代码坏味（_Refactoring_ ch.3），即使仓库什么都没写也适用。两条约束：

- **仓库优先。** 成文的仓库规范永远赢；仓库背书了基线会标记的写法时，抑制该 smell。
- **永远是判断题。** 每条 smell 是带标签的启发式（"possible Feature Envy"），从不是硬违规——且与这里的任何规范一样，工具链已强制的内容一律跳过。

每条 smell 按 *是什么* → *怎么修* 阅读；对照 diff 匹配：

- **Mysterious Name（神秘命名）**——函数、变量或类型的名字没有揭示它做什么或装什么。→ 重命名；起不出诚实的名字，说明设计本身混浊。
- **Duplicated Code（重复代码）**——同一逻辑形状出现在本次改动的多个 hunk 或文件里。→ 提取共享形状，两处调用。
- **Feature Envy（依恋情结）**——一个方法伸手进另一个对象数据的次数多于自己的。→ 把方法搬到它依恋的数据上。
- **Data Clumps（数据泥团）**——同样几个字段或参数总是结伴出现（一个想要诞生的类型）。→ 捆成一个类型，传它。
- **Primitive Obsession（基本类型偏执）**——用原始类型或字符串顶替值得拥有自己类型的领域概念。→ 给概念一个自己的小类型。
- **Repeated Switches（重复分支）**——对同一类型的同样 `switch`/`if` 级联在改动里反复出现。→ 用多态，或两张共享的映射表替换。
- **Shotgun Surgery（霰弹式修改）**——一个逻辑变更迫使 diff 里许多文件零散修改。→ 把一起变的聚到一个模块。
- **Divergent Change（发散式变化）**——一个文件或模块因多个不相关原因被修改。→ 拆分，让每个模块只因一个原因变化。
- **Speculative Generality（投机泛化）**——为 spec 没有的需求添加的抽象、参数或钩子。→ 删掉；内联回去，直到出现真实需求。
- **Message Chains（消息链）**——调用方不应依赖的长 `a.b().c().d()` 导航。→ 用第一个对象上的一个方法把这段走位藏起来。
- **Middle Man（中间人）**——一个类或函数大部分只是往后转发。→ 砍掉，直接调用真实目标。
- **Refused Bequest（被拒绝的遗赠）**——子类或实现者忽略/覆盖了大部分继承内容。→ 放弃继承，改用组合。

### 4. 两轴并行检视

**Standards 轴简报**——包含完整 diff 命令与提交列表；找到的规范文档清单 + 上述 smell 基线全文（检视者没有其他途径拿到它）。任务书："逐文件/逐 hunk 汇报—— 抄录文档化规范的地方：引用规范（文件 + 规则原文）； 命中的基线 smell：点名并引用 hunk。区分硬违规与判断题——文档化规范可以是硬违规，基线 smell 永远是判断题，且成文仓库规范覆盖基线。工具链已强制的内容跳过。400 字以内。"

**Spec 轴简报**——包含 diff 命令与提交列表；spec 的路径或取回的内容。任务书："汇报： spec 要求但缺失或不完整的需求； diff 里没被要求的行为（scope creep）； 看起来实现了但实现方式可疑的需求。每条发现引用 spec 原文行。400 字以内。"

spec 缺失时跳过 Spec 轴，并在最终报告中注明。

### 5. 聚合

两份报告分别放在 `## Standards` 与 `## Spec` 标题下，原样或轻度清理呈现。**不合并、不重排**发现——两轴刻意分离（见下文"为什么两轴"）。

结尾一行总结：每轴的发现总数与各轴内部的最严重问题（若有）。不在两轴之间选唯一赢家——那种重排正是分离要阻止的。

## 为什么两轴

一个改动可能通过一轴而挂掉另一轴：

- 代码遵守了每条规范，但实现的是错的东西 → **Standards 过，Spec 挂。**
- 代码精确做了工单要求的事，但破坏了项目约定 → **Spec 过，Standards 挂。**

分开报告，阻止一轴掩盖另一轴。
