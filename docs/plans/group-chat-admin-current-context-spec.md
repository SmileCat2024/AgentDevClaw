# 群聊管理员当前上下文规范

> 状态：当前实现说明（不是未来设计稿）  
> 更新日期：2026-07-13  
> 关联设计：`group-chat-admin-context-injection-design.md`  
> 主要实现：`server/routes/group-chat.js`、`local-features/group-admin/src/bridge.ts`、`local-features/group-admin/src/index.ts`

## 1. 这套上下文要让管理员成为谁

管理员是群聊中的协调者。它面对的不是若干孤立的对话容器，而是一组持续变化的工作线程：用户正在推进哪些工作、每项工作由谁负责、目前做到哪里、此刻是否仍在执行、能否继续派发，以及刚刚发生了什么变化。

管理员用“工作线程”理解一项持续推进的工作。线程的上下文入口可能因 trim、summary、compact 等交接而变化，也可能因 branch 产生并行方向，但日常协调仍围绕线程进行。session 是承载上下文和诊断问题时使用的技术对象，不是默认导航层。

管理员每次醒来依次回答五个问题：

1. 这一次为什么叫我？
2. 当前有哪些工作线程，分别处于什么状态？
3. 刚才有哪些用户消息、Agent 回复或系统事件改变了这些线程？
4. 用户说的是已有工作还是一项新工作？
5. 我应该派发、澄清、中断、公开回复，还是保持静默？

## 2. 一次推理实际由哪几层组成

管理员看到的信息不是一个大字符串，而是按角色和寿命分层：

| 层次 | 消息角色 | 寿命 | 内容 |
|---|---|---|---|
| 系统提示词 | `system` | 整个管理员 session | 身份、工作线程心智、可见性边界、状态语义、决策顺序、工具与结束规则 |
| 本轮环境证据 | `system` | 每次唤醒重新生成 | 当前工作线程、未读群聊增量；新 session 额外包含群基本信息、GROUP.md、群记忆 |
| 特殊状态说明 | `system` | 发生特定事件时 | 自动派发结果、审批通过/拒绝、失败提醒等 |
| 附件内容 | `system` | 触发消息带附件时 | 文件名和内容，超长附件按行截断 |
| 本轮触发 | `user` | 当前 call | 用户直接要求，或一句简短的活动说明 |
| 忙碌期增量 | `system` | 当前 call 的后续 step | 管理员推理期间新到达的线程快照与群聊增量 |
| 工具结果 | `tool` | 当前推理链 | 主动查询的线程详情、消息、Task、诊断信息和操作结果 |

顺序上，系统提示词最先存在；空闲状态收到消息时，Bridge 在 `CallStart` 先加入环境证据和附件，再由 Arbiter 将本轮触发作为用户输入启动 call。因此管理员的阅读顺序是“先知道环境，再处理触发”。

## 3. 永久系统提示词

来源：`prebuilt-agents/official/work-group/.agentdev/prompts/system.md`。

它不罗列某个群的实时数据，而是建立稳定认知：

- 管理员负责理解意图、掌握进展、定位线程、派发要求和必要干预；
- 当前输入由“工作线程、群聊增量、本轮触发”组成；
- 线程分类回答当前执行是否仍在继续，执行状态提供更具体的运行细节；
- 专业 Agent 看不到群聊，只能看到系统路由或管理员派发给它的文本；
- 同一线程保留自己的历史，不同线程不自动共享上下文；
- 运行中或排队中的线程不重复派发；
- 已有目标的增量要求进入原线程，明确的新目标才开始新线程；
- 上下文用量只是观测值，不能据此假定系统已经自动压缩；
- 中断只停止当前执行，不会自动创建线程或 session；
- 审批行为取决于群聊当前响应模式，以工具实际返回为准；
- 管理员的普通模型输出不会自动展示到群聊，公开表达必须调用 `gc_reply`；
- 每轮必须通过派发工具的 `done=true`、`gc_reply(done=true)` 或 `gc_stop` 明确结束。

这段提示采用正向叙述：直接说明管理员所在的世界、能看到什么、要完成什么，不假设它曾经采用过另一套“会话管理”心智。

## 4. 新管理员 session 才注入的背景

`prepareAdminContext(..., isNew=true)` 会依次加入以下内容。它们是静态或半静态背景，不在每轮重复。

### 4.1 群聊基本信息

固定格式：

```text
─── 群聊基本信息 ───
群聊名称：{chat.name 或“(未命名)”}
群聊ID：{chat.id}
创建时间：{zh-CN 本地时间；createdAt 存在时才显示}
当前时间：{zh-CN 本地时间}
```

`创建时间` 是可选行；其他三行始终存在。

### 4.2 GROUP.md 群聊背景

当群目录中存在非空 `GROUP.md` 时：

```text
─── 群聊背景 ───
{GROUP.md 原文}
```

它用于项目背景、长期约定、成员职责和稳定事实。更新后，已有管理员 session 不会自动重新注入；要让新内容成为开场背景，需要重启或轮转管理员 session。动态变化不应写进 GROUP.md。

### 4.3 群记忆

格式：

```text
─── 群聊记录（{近1天|近3天|近1周|全部历史}，共{N}条）───
[MM/DD HH:mm] {发送者}{会话或派发目标标签}：{消息摘要}
[MM/DD HH:mm] {发送者}{会话或派发目标标签}：{消息摘要}
...
```

时间范围来自 `chat.adminMemory.range`，可取 `1d`、`3d`、`1w`、`all`，默认 `3d`。群记忆可带人工批注：

```text
[批注 MM/DD HH:mm] {批注内容}
```

单条消息超过 800 字符时只保留头部，并给出原始长度与 `messageId`，管理员可用 `gc_messages` 获取全文。

新 session 且此前没有管理员水位线时，不再额外生成 catch-up；群记忆承担首次历史背景，避免同一批历史重复出现两次。

## 5. 每次唤醒都会注入的当前工作线程

这是管理员的默认主视口，由服务端在每次 `prepareAdminContext` 时读取最新群聊、线程血缘、Task 快照、运行时和上下文用量后生成。

### 5.1 总体格式

```text
─── 当前工作线程 ───
概览：进行中 {N}；已完成 {N}；已归档 {N}

[进行中 · 运行中] {Agent 显示名} · {线程标题}
  threadRef: {稳定线程引用}
  Task {已处理数}/{总数} 已处理（含 {取消数} 取消）；上下文 {百分比}%；{可派发|不可派发}
  最近：{当前入口的最近一条用户或 assistant 消息}

[已完成 · 空闲可继续] {Agent 显示名} · {线程标题}
  threadRef: {稳定线程引用}
  Task {已处理数}/{总数} 已处理；上下文 {百分比}%；{可派发|不可派发}
  最近：{最近消息}

已归档线程：{N} 条（未展开）
```

如果还没有线程：

```text
─── 当前工作线程 ───
概览：进行中 0；已完成 0；已归档 0
当前还没有工作线程。
```

### 5.2 工作状态

- `进行中`：当前入口正在运行、排队，或派发仍在处理中。
- `已完成`：当前执行已经结束；它不表示所有 Task 都成功，也不等于用户已经验收。
- `已归档`：该线程路径的 head 已归档，不再接收指令。中间节点归档不会影响仍有可用 head 的线程。
- head 缺失但没有明确归档时仍归入`已完成`，并通过“不可派发”等详情表达技术限制，不增加第四个分类。

线程分类与 Task 进度解耦。Task 全部完成但执行尚未结束时，线程仍是“进行中”；Task 未全部成功或包含取消项但执行已经结束时，线程进入“已完成”。取消的 Task 计入“已处理”，同时保留“已取消”结果。

### 5.3 执行状态

- `运行中`：Agent 正在执行。
- `排队中`：已有请求在队列中。
- `空闲可继续`：runtime 存活但当前无 call。
- `未运行可继续`：runtime 未运行，但线程入口仍可接收派发。
- `不可用`：当前入口不能直接派发。

### 5.4 信息量限制

- 默认只展开未归档线程，最多 20 条；
- 已归档线程只注入总数，需追溯时主动调用线程工具；
- 最近消息会压成单行，最多 180 字符；
- 默认线程概览提供 `threadRef`，不提供 head session ID；
- Task 只显示汇总，不默认展开每个 Task；
- 上下文只显示当前入口的使用百分比。

这样管理员一眼看到“事情和状态”，只有在验收、定位分叉或诊断异常时才下钻到 session 与 lineage。

## 6. Catch-up：管理员离开后发生了什么

水位线之后、当前触发上界之前的消息会组成增量块：

```text
─── 你未读的群聊消息（共{N}条）───
[MM/DD HH:mm] 用户：{消息正文}
[MM/DD HH:mm] {Agent 名}[会话：{标题} #{短ID}]：{回复正文}
[MM/DD HH:mm] [系统事件] {事件描述}
```

管理员派发消息使用“派发到”标签，Agent 回写使用“会话”标签。这些标签用于解释消息来源与去向；它们不会改变管理员以线程为主的默认导航。

### 6.1 超长消息

单条消息超过 800 字符：

```text
{截断后的头部}
[已截断，原文 {N} 字符。使用 gc_messages 查看 messageId: {id} 的完整内容]
```

截断会尽量向前寻找换行，且不会退到阈值一半以前。

### 6.2 附件摘要与批注

有附件时，消息行尾附加：

```text
[附件: {name1}, {name2}]
```

有管理员批注时，消息行尾附加：

```text
[批注 MM/DD HH:mm] {批注内容}
```

### 6.3 系统事件

已专门格式化的事件包括：

```text
[系统事件] {Agent} [会话：{标题} #{短ID}] 已开始处理
[系统事件] {Agent} · 工作线程「{标题}」精简历史后已由新上下文接管
[系统事件] {Agent} · 工作线程「{标题}」摘要交接后已由新上下文接管
[系统事件] {Agent} · 工作线程「{标题}」已创建新的并行工作线程
[系统事件] {Agent} · 工作线程「{标题}」Task 完成：{Task 标题}
[系统事件] {Agent} [会话：{标题} #{短ID}] 会话已归档，不再接收新任务
[系统事件] {Agent} [会话：{标题} #{短ID}] 已取消归档，可以继续接收任务
```

生命周期事件优先带 Agent 名和工作标题，避免仅出现“某个编程小助手的会话已精简”而无法定位具体工作。

## 7. 特殊 systemNote

特殊状态说明放在本轮环境证据最前面，与用户输入分离。

### 7.1 系统自动派发成功

```text
─── 自动派发状态 ───
目标：{Agent 名}（{identityRef}）
操作：{已建立新工作「标题」|指令已进入已有工作「标题」}
消息 ID: {messageId}
系统已自动将此消息派发给 {Agent 名}，你不需要重复派发。
```

### 7.2 自动派发可能失败

```text
─── 自动派发状态 ───
目标：{Agent 名}（{identityRef}）
状态：会话启动可能失败，请关注。
消息 ID: {messageId}
```

### 7.3 审批通过并执行

```text
─── 审批通过 · 派发已执行 ───
目标：{Agent 名}（{identityRef}）
操作：{已建立新工作「标题」|指令已进入已有工作「标题」}
原派发消息 ID: {messageId}
```

### 7.4 派发请求被拒绝

```text
─── 派发请求被拒绝 ───
被拒绝的派发目标：{Agent 名}（{identityRef}）
被拒绝的派发内容：{前 300 字符}
原派发消息 ID: {messageId}
```

这些块报告已发生的事实，不再向管理员重复灌输判断规则，也不默认暴露 session ID。

## 8. 附件如何注入

附件不拼进用户正文，而是独立 system 消息：

```text
附件内容：
--- {文件名1} ---
{文件内容1}

--- {文件名2} ---
{文件内容2}
```

每个附件默认最多展示前 50 行。超过时：

```text
... [内容已截断] 共 {总行数} 行，已显示前 50 行，还有 {剩余行数} 行未显示。

完整内容请查看本地文件: {群资源目录下的绝对路径}
```

因此附件名称会在 catch-up 中作为存在性提示，实际内容则在独立 system 块中出现。

## 9. 本轮 user 输入是什么

user 块只表达“为什么这次叫管理员”，避免同时塞入环境快照和历史。

| 触发场景 | user 块 |
|---|---|
| 用户直接 `@管理员` | 用户原始消息正文；当前消息不重复进入 catch-up |
| 执行模式下用户 `@Agent` | `用户 @了 {Agent 名}`；原始正文进入 catch-up |
| 规划模式下系统已自动派发 | `用户 @了 {Agent 名}`，可能带附件名；正文进入 catch-up，自动派发结果进入 systemNote |
| 一般用户消息唤醒管理员 | `用户发送了消息`；正文进入 catch-up |
| Agent 回复唤醒管理员 | `{Agent 名}[会话标签] 回复了`；回复正文进入 catch-up |
| 生命周期或 Task 事件 | 一句结构化事件说明；完整事件也进入 catch-up |
| 审批通过 | `用户批准了 {Agent 名} 的派发请求`；结果进入 systemNote |

对于非直接 `@管理员` 的场景，`textInCatchUp=true`。Bridge 知道触发消息原文已经在 system catch-up 中，因此不会再把简短 user 触发文字拼进忙碌期的 system 增量里造成重复。

## 10. 空闲路径与忙碌路径

### 10.1 管理员空闲

1. 服务端解析或创建管理员 session；
2. `prepareAdminContext` 生成环境证据并推进水位线；
3. 消息进入 Group Chat inbox；
4. Bridge 暂存 `contextText` 和附件；
5. `CallStart` 将它们作为 system 消息加入上下文；
6. Arbiter 使用 `text` 启动新的 user call；
7. 管理员调用工具完成本轮。

### 10.2 管理员正在推理

新消息不会立刻再开一个并发 call，而是进入 `pendingBuffer`。下一个 `StepStart` 时：

- 多条消息按到达顺序合并；
- 各自的 `contextText` 作为新的 system 消息注入；
- 直接 `@管理员` 的原始 `text` 会跟在对应 context 后；
- 已被 catch-up 包含的触发原文不再重复；
- 新附件单独成为另一个 system 消息。

这使管理员在一轮尚未结束时也能感知新的用户消息、Agent 回写和工作状态变化。

## 11. 水位线的当前实现

当前游标是：

```text
chat.lastActiveAt['work-group:admin'] = {触发消息 timestamp}
```

每次 `prepareAdminContext`：

1. 读取上一次时间戳；
2. 选择 `timestamp > lastActiveAt` 的消息；
3. 根据场景决定是否包含当前触发消息；
4. 生成 catch-up；
5. 将水位线推进到当前触发消息时间戳并写回群聊文件。

直接 `@管理员` 时，当前消息作为 user 输入，不进入 catch-up。观察、自动派发和一般活动通知时，当前消息进入 catch-up，user 块只保留触发说明。

### 11.1 已知边界

当前水位线是时间戳，不是严格递增的消息序号或确认游标，因此仍有以下边界：

- 同毫秒消息和乱序到达不具备严格的全序保证；
- 水位线在消息成功进入 inbox 之前已经写回，极端故障下存在“游标已推进、投递未完成”的窗口；
- 没有 per-message ack，不能精确表达“已注入但模型尚未处理”；
- 并发的管理员通知依赖管理员 session 锁和写文件顺序，语义强度仍不等同于事务队列。

这些问题不影响普通单流场景的基本工作线程心智，但在高并发和故障恢复阶段需要升级为 `seq + delivered/ack` 模型。

## 12. 管理员上下文轮转

管理员使用持久 session。每次解析管理员 session 时，系统检查当前 session 的上下文用量。

配置支持两种阈值：

- `tokens`：默认达到 200,000 tokens 时轮转；
- `ratio`：默认达到模型 context length 的 20% 时轮转。

当用量达到阈值：

1. 停止旧管理员 runtime；
2. 记录旧 session ID 到 `adminSessionHistory`；
3. 创建新的管理员 session；
4. 新 session 重新注入群基本信息、GROUP.md、群记忆和当前工作线程。

这里的轮转只针对管理员自身上下文。专业 Agent 工作线程的上下文交接由真实的 trim、summary、compact、branch 生命周期事件描述，不能从“用量达到阈值”直接推断已经发生。

### 12.1 当前总量边界

- 阈值限制的是当前管理员 session，不是管理员历史 session 的总量；
- `adminSessionHistory` 当前没有总体数量上限；
- 选择 `all` 作为群记忆范围时，新 session 的历史输入可能持续增长；
- 新 session 依靠群记忆重建背景，不会自动生成旧管理员 session 的专门交接摘要；
- GROUP.md、群记忆与工作线程概览之间仍可能出现语义重复，需要靠内容职责约束避免。

## 13. 主动查询与派发后的上下文

默认注入只给“足够做第一步判断”的信息。管理员需要下钻时使用工具：

- `gc_thread_overview`：重新读取完整工作线程概览，可按工作状态筛选；
- `gc_thread_detail`：读取一条线程的 Task 明细、最近消息、当前入口和 lineage；
- `gc_messages`：读取被截断的原始群消息；
- `gc_sessions`、`gc_session_tasks`、`gc_session_summary`：session 级追溯或诊断；
- `gc_dispatch_thread`：向已有线程当前入口派发增量；
- `gc_start_thread`：开始明确的新工作；
- `gc_interrupt_thread`：中断指定线程当前执行。

线程概览的可读文本不展示 head session ID。结构化工具结果仍保留 `lineageHeadId`、`sessionId` 等字段，供工具链和诊断使用。

派发成功的可读结果保持简短：

```text
已派发到 {identityRef}，{创建了新工作「标题」|指令已进入「标题」的当前上下文}。
工作线程: {threadRef；可解析时显示}
消息 ID: {messageId}
```

结果对象仍可携带 `sessionId`、`sessionTitle`、`threadRef` 和最新线程结构，但不再把 session ID 或整份“派发后的工作线程概览”重复塞进管理员阅读文本。

## 14. 完整示例

## 15. 当前设计的核心取舍

这套结构刻意把信息分成三种密度：

1. **默认可见**：线程标题、负责人、工作状态、执行状态、Task 汇总、上下文比例、最近消息；足够完成绝大多数协调判断。
2. **按需下钻**：完整 Task、群消息全文、lineage、head session；只在验收、追溯和诊断时读取。
3. **技术保留**：session ID 和原始结构化字段继续存在，保证精确操作与兼容能力，但不占据管理员日常注意力。

管理员因此不是在记住所有信息，而是在保持一个清晰的线程模型：先看每项工作现在怎样，再看刚刚发生了什么，最后只对用户当前要求采取最小而准确的动作。
