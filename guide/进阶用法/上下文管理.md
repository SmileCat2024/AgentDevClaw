# 上下文管理

对话越长，Agent 记得越多，但也越迟钝、越昂贵。这篇文章讲清楚上下文到底是怎么回事，以及两种处理手段——总结与精简——各自适合什么时候用。

## 上下文就是 Agent 的记忆

大模型没有凭空的记忆。它「记得」的一切，就是当前这次对话发给它的全部内容：你发的每条消息、Agent 的每次回复、它读过的文件、执行过的命令和返回的结果。这份随对话不断追加的完整记录，就是**上下文**。

这意味着两件事：

- Agent 每一轮「记得什么」，完全取决于上下文里有什么。上下文足够长、信息足够全，它才能在第十轮还记得你第一轮说过的话。
- 对话每进行一轮，上下文就长一截。它不会自己变短。

## 为什么要管理上下文

**成本与长度成正比。** Agent 的每一轮交互——包括每一次读文件、跑命令的工具调用——都要携带完整上下文发往模型。一次实际任务动辄几十次工具调用，上下文从几万 token 滚到十几万，每一轮的成本都在水涨船高：同样的工作，背着两倍的历史，就花两倍的钱。

**模型有窗口上限。** 每个模型的上下文窗口都有上限。顶到上限后 API 直接报错，会话无法继续——不是变慢，是停止工作。

**太长会降智。** 即使离上限还远，上下文过长也会让模型的表现变差：注意力难以聚焦、忘记早期的约定、对内容的理解开始飘。如果你遇到过 Agent 干着干着「忘了自己在干嘛」，或者重复问你已经说过的事，多半就是上下文太长了。

所以，适时处理上下文不是可选项：既省成本，也直接决定 Agent 的执行质量。

## 两种手段：总结与精简

### 行业常规做法：压缩成摘要

大多数 Agent 工具（Claude Code、Codex 等）的做法是设一个阈值，上下文快满时自动触发压缩：调一次模型，把之前的历史概括成一份摘要，用摘要替换原始对话。

它的问题在于**信息折损**：概括必然丢细节，原始表述被重新改写，而丢掉的细节可能恰恰是后续执行的关键。用过这类工具的人对压缩之后的体验应该不陌生——Agent 开始发飘，忘了之前定下的约定，甚至重新犯一遍已经修过的错。因为对它来说，「历史」已经变成一份失真的二手描述。

### AgentDevClaw 的做法

我们也提供总结，也就是摘要式压缩；但在绝大多数场景下，**精简是更好的选择**。

| | 精简（Trim） | 总结 |
| --- | --- | --- |
| 做什么 | 按轮次裁掉最早的对话，保留最近部分 | 整段历史压缩成一份摘要，对话基于摘要继续 |
| 原始表述 | 逐字保留 | 被重新表述 |
| 适合 | 绝大多数场景 | 信息已收敛的特定场景 |

## 精简为什么通常是更好的选择

**它保留的是对话的骨架，Agent 的身份感知始终一致。** 精简裁掉的是部分轮次，留下的是原样的对话——一问一答的结构、你的语气、Agent 自己的措辞都还在。续接时，Agent 看到的仍然是一场真实的对话，只是变短了：还是同一场工作、同一个身份，它以一贯的风格和自我认知继续。压缩成摘要则是另一回事——历史变成一份转述出来的报告，Agent 从对话的「参与者」变成了「读报告的人」。用过压缩式工具的人多半有过这种体会：压缩之后 Agent 像换了个人，口吻、行事风格、对任务的理解都有漂移，根源就在这里。

**裁掉的是低价值的大头。** 长上下文里占大头的是早期的调查过程：读一段代码、试一个方向、改一行又读一遍——这些中间记录在后续工作里几乎没有参考价值，却实实在在占着空间。精简正好把它们裁掉。

**留住的原文不会被抹平。** 需求往往是在很多轮对话里散着提、慢慢补的。你那些口语化的、随手补充的话里，常常藏着真正的意图——摘要恰恰最容易把这些微妙信息「概括」掉。精简保留原文，Agent 读到的还是你当时说的话。

**Agent 不是无感知地被裁。** 精简发生后，系统会在上下文末尾注入一条注解：Agent 知道此前有内容被裁掉、上一段对话到哪为止，并被提醒先重读关键文件、回顾已有结论再继续。而实际工作中，继续修问题、继续编码本来就需要基于最新的代码状态重读一遍——与其背着过时的编辑记录，不如干净地重读。

**裁掉不等于删除。** 被精简的轮次仍留在原会话里（选择「执行并归档」时归档保留），需要时可以回去翻，也可以用[跨对话记忆](../新功能/v0.2.2preview.md)把历史会话引用回来。

## 什么时候精简：一个典型节奏

设想这样一段工作：你先和 Agent 进行了大量深入的讨论——信息密度很高，需求、结论、约定交错在各轮对话里；随后进入执行阶段，工作拆成了 A、B、C、D 四个环节。A、B 做完，上下文已经很长了。这时候值得想一想：接下来的 C，和 A、B 的关系往往并不深——它对前面内容的依赖大多停留在「知道发生过什么」的层面，并不需要反复回看细节。此时把前面的轮次精简掉，Agent 处理 C 时就是轻装上阵。

判断的思想只有一条：**接下来要做的事，和前面的对话关系有多紧。**

- 关系紧密——比如 C 的实现直接取决于之前的讨论细节——那就**不精简，或者少精简**，把重要的轮次留下来；
- 关系不紧——绝大部分开发性工作都是如此——Agent 只需要知道前面发生过什么，细节靠后续重读文件来回忆即可，此时**放心精简**。

## 总结适合什么时候用

总结的强项是把「过程」收拢成「结论」。当信息已经收敛——你清楚知道在解决什么问题，只是需要一份更紧凑的状态描述——它比一长串杂乱的调用记录更好用。

典型场景：一个难缠的 Bug 修了几版都不对，探索阶段结束了。此时把整段历史总结成「试过哪些方案、哪些还没验证、当前思路是什么」，相当于交给 Agent 一份条理清晰的调试日志，它基于这份日志继续，比在原始调用记录里翻找要高效。

## 一句话判断

- 信息**收住了**，只需要结论——**总结**；
- 信息还要**留着**，只想甩掉早期的包袱——**精简**。

拿不准的时候，选精简。

## 如何操作

在会话列表中右键目标会话（或点「⋯」菜单），选择「精简历史」打开精简面板，点确认即完成。

> [!TIP] 绝大多数情况：直接确认
> 面板打开时已默认勾选全部可精简的轮次，通常无需逐轮查看，直接点确认就是一次干净利落的精简。

想更精细地控制，也可以在面板里手动调整勾选，把仍然重要的轮次留下来：

- **收益**：Agent 的「经验」保存得更完整——后续工作中可以少读一些重复的文件，对细节的理解也更准；
- **代价**：保留得越多，精简后的上下文自然越长。

适合你对这段对话的走向把握得当、清楚哪些内容接下来还会被用到的时候。

面板的界面细节（逐轮列表、占用占比、实时释放统计）与两种执行方式（「仅执行」/「执行并归档原会话」）的完整说明，见[会话与上下文](./会话与上下文.md)。
