# 宿主投递面：永久滞留死锁与投递活性假设边界

日期：2026-11-18。状态：死锁缺陷已修复并验证（构造性复现 + TLA 双重证实）；TLA+ 宿主投递面模型已建立并于当晚大幅细化（8 → 15 场景全匹配，覆盖双投递路径、绑定漂移、ready 信号丢失等此前不可表达的机制）；三项产品决策盲点待用户裁决（D11/D12/D13/D14）。本文是 [2026-11-17 裁决清单](2026-11-17-tla-product-decision-register.md) 的后续：其中 D10 登记的"接续身份采纳失败后命令保持 pending"边界，本轮已升级为确定缺陷并修复。

## 先读结论

本轮完成四件事：

1. **把 2026-11-18 凌晨报告的"永久卡死"从机制推演变成确定性缺陷**：受控复现（真实生产模块 + 两处故障注入）证明"身份错位 + 触发票耗尽"形态下三个自愈机制全部失效、指令永久滞留且盘上无痕；随后修复。
2. **首次把宿主装配层纳入 TLA+ 验证**：新模型 `HostDeliveryPlane.tla` 补上既有模型显式留白的一层（DEEP-MODELS.md 自我声明"真实轮询、失败退避、runtime-ready 事件是否满足公平假设尚未验证"），8 场景矩阵全部匹配预期。
3. **跑模型过程暴露两类新发现**：① 一个确定缺陷（即上述死锁，已修复）；② 两项产品决策盲点——投递活性的完整假设链（无限换头风暴 / 无限崩溃循环可饿死投递，即使修复后），与滞留期间的可见性承诺（"已暂存"文案、失败无痕）。
4. **模型细化轮**：把首版明确留白的机制全部补进模型——直投与线程队列双路径、诚实投递触发面（四个触发点取代票池）、线程级退避（force 失败也置退避、到期无内部重试）、runtime 三态生命周期与绑定漂移、spawn 身份注入开关（ADR-0047 前后）、ready 信号丢失开关（11-16 补偿前后）、采纳反复失败探针。15 场景全匹配，新增两项产品决策盲点（D13 跨路径保序、D14 直投落错会话可见性）与一条新饥饿轴（D12-3 漂移风暴）。

## H2．身份错位 + 触发票耗尽 → 指令永久滞留（已修复）

**用户可能在哪遇到：** 编程小助手 / Coder 线程会话中，恰逢换头后身份采纳失败（adopt-thread-head 失败不回滚换头，server.js 路由注释自认"失败只能靠重启收敛"）。用户发"继续"等指令，提示"已暂存"，之后永远不执行，只能手动接续或重启救活。

**发生了什么：** 换头提交后、runtime 采纳新身份前，宿主注册表条目与 runtime 实际采纳的 head 代际是两个可分离的事实（双真相源）。错位窗口内投递被 viewer fencing 永拒（`runtime_not_accepting_input`，可重试失败——指令保持 pending 且盘上无任何失败痕迹）。而修复前的三个自愈机制看的都是宿主侧"条目在位"同一个事实：`ensureHeadRuntime` 对在位条目直接返回 ok；requeue 扫描对在位条目跳过；delivery-consumer 无自驱动定时器。触发点（gateway 即时投、runtime-ready 补投）烧完投递尝试后，没有任何一方会再碰这条指令。

**确认到哪里：** 三层证据链，全部可复跑：

- **构造性复现**（`test/thread-pending-stall-deadlock-repro.test.js`，真实 `createThreadControl` + 真实框架 `WorkThreadRuntimeBridge`，仅注入"宿主条目在位"与生产同形的 fencing 拒绝错误）：指令保持 pending 且 attempts 不变（解释了为何事后无现场）；退避窗口后模拟新消息触发重试，仍被拒；`ensureHeadRuntime` 回答"一切正常"；pending 老化 120 秒后连跑两轮 `requeueStalledPendingThreads` 零行动；对照用例证明换头（手动接续）立即送达——与用户症状闭环。
- **TLA+ 模型**（`specs/tla/HostDeliveryPlane.tla`）：`fencing-deadlock-pre-fix` 场景死锁态可达（安全形式，无需活性假设）；`liveness-pre-fix` 场景在完整弱公平假设下活性失守（exit 13）——证明这不是调度运气问题，公平性救不了修复前语义；细化轮新增 `allgreen-stall-pre-fix` 场景把 wt-1ab8a75b 的"一切健康但永久静默"窗口也钉成可达（修复前触发面上没有任何 action 对滞留指令负责）。
- **变异验证**：临时回退修复的跳过条件，两条自愈断言立即失败；恢复后重过——断言锚定的是"扫描零行动"行为本身。

**修复：** `thread-succession.js` 的 requeue 对"条目在位 + 滞留超过水位（60s）"增加对账：先 force 重投（`tryDeliver` 新增 force 通道绕过幂等窗口），仍错位则做身份采纳重试（复用换头事务的采纳路径）再复投；janitor 周期自驱动，不依赖外部触发点。修复后 `liveness-post-fix` 场景活性通过（干扰预算有界时：换头 3 + 崩溃 2 + 漂移 2）。

**验证：** 相关测试 116 项全过（delivery-consumer / succession / control / 新复现测试三用例）；TLA 15 场景全匹配。与 D10 的关系：D10 登记的"哪些故障自动恢复、哪些转人工"整体仍是产品决策，但其中"身份采纳失败类滞留"已按本轮修复落为自动恢复。

**修复边界（未覆盖）：** 采纳失败本身的根因（为什么 adopt-thread-head 会失败）未查——本轮修的是"失败后不自愈"这一层；采纳失败时的即时重试（而非等 janitor 水位）与用户可见性见 D11。

## D11．滞留期间用户应该看到什么（可见性承诺）

**关联：** H2；2026-11-18 凌晨报告的"已暂存 18~34 秒"现象。

**已确认行为：** 冷启动窗口内"已暂存"提示先于 runtime 就绪出现，属按设计暂存；但同一文案也覆盖了 H2 的永久滞留形态。指令被 fencing 拒绝不落盘任何痕迹（attempt 计数不变、无 lastError），滞留水位告警挂在 delivery-consumer 的 consume 路径上——修复前恰好是没人调用的那条路径。修复后 janitor 有日志，但用户可见面没有变化。

**用户出处与影响：** 线程会话发指令后长时间无响应。用户无法区分"正常暂存（秒级）"、"交接窗口（15s 级）"与"投递反复被拒（需干预）"——正是本轮线上报告误判为卡死的直接原因。

**实施需明确：** "已暂存"是否按滞留时长升级为分级文案（暂存中 → 交接中 → 反复投递失败请检查）；投递失败痕迹要不要持久化（attempt/lastError）并在会话或线程详情暴露；滞留告警的归属从 consume 路径移到 janitor 后，水位与通知渠道是否调整。

**建议：** 文案分级 + 失败痕迹持久化。不承诺永久重试，但让"没发出去"这件事本身可见——H2 修复消除了静默死锁，D11 要消除的是静默等待。

## D12．投递活性的假设边界（即使修复后仍成立的饥饿类）

**已确认行为（TLA 场景证据）：** `HostDeliveryPlane.tla` 把投递活性的前提显式化为四个假设，其中三个在干扰无限时产生确定饥饿（`starve-handoff-storm` / `starve-crash-loop` / `starve-drift-storm` 场景，exit 13 时序反例）：

1. **换头尝试收敛**：无限换头风暴（begin/abort 永久循环）会饿死一切依赖挡板关闭的对账与投递——**修复后依然成立**。间歇性挡板使弱公平的 janitor 永远"被打断"，每次扫描都撞上交接窗口。生产对应物是接续反复失败重试的风暴场景。
2. **runtime 最终稳定**：无限崩溃循环（拉起即死）饿死投递——janitor 每次唤醒都在 runtime 死亡前无法完成送达。与死锁无关，属另一类。
3. **绑定漂移不快于 janitor 扫描**（细化轮新增）：janitor 对"条目缺位"的处理是两拍收敛——唤醒拍重绑 head，下一拍对账投递。绑定漂移频率高于扫描频率（15s 一拍）时，每次扫描都看到 foreign、永远走唤醒分支，对账拍永不发生；且弱公平性被唤醒分支无限代偿满足（WF 只要求"扫描做了它该做的事"，而每拍它确实做了）。生产对应物是 shared-by-project 的机器速度借用（另一个工作流高频轮转拉走同一 runtime）或用户在会话间高频切换。**修复后依然成立**。
4. 挡板收敛（交接事务最终 commit/abort）与触发点公平（gateway 即时投总会执行）：生产有对应机制，模型作假设声明。

细化轮另有一条探针性质的饥饿轴：`adopt-repeat-starve` 场景（采纳可反复失败时修复后活性仍失守）表明投递活性隐含依赖"身份采纳最终成功或 runtime 重启"。是否真实可达取决于 adopt-thread-head 在生产中的失败形态（本轮未核实），登记为待核实而非确定缺陷。

**用户出处与影响：** 无人值守长任务（Coder 自动接续风暴、runtime 崩溃循环、共享 runtime 被高频借用）。表现为指令长时间滞留——与 H2 症状相同但成因不同，H2 修复不覆盖这三类。

**实施需明确：** 接续失败是否设尝试上限/熔断（当前是否有退避需另行核对生产代码）；崩溃循环检测（连续 N 次拉起即死 → 停止自动重试并告警）是否作为承诺；漂移风暴的缓解方向（janitor 唤醒拍捎带 force 对账把两拍收敛压成一拍、漂移源治理、或滞留升级告警与 D11 联动）；这三类饥饿要不要纳入滞留告警的区分逻辑。

**建议：** 把"接续尝试上限"、"崩溃循环熔断"与"漂移风暴缓解"作为决策项裁决；裁决前至少在告警中区分"交接风暴中"、"runtime 不稳定"与"runtime 被借用"，不给用户虚假的"稍后会自动恢复"预期。

## D13．直投与线程队列的跨路径关系（细化轮新增）

**已确认行为（TLA 场景证据）：** `direct-overtake-reachable` 场景证明跨路径超车可达：更早入箱的指令还在 pending，更晚的用户输入已经直投落在 runtime 当前会话。这正是 wt-1ab8a75b"10:09 新消息秒达而旧 4 条纹丝不动"的形态。队列内 FIFO 无超车在所有场景下恒成立（`QueueFIFO` 不变式，FIFO + retryable-break 的数学后果），但**线程 FIFO 保证不跨路径成立**：直投既不清偿 pending 也不保序。

**机制根源：** 用户输入按注册表事实分流（input-gateway 路由）——runtime 在位且绑定 head 时入箱（受 fencing 保证），否则直投（绕过线程队列，落在 runtime 当前绑定会话）。两条路径互不相通，直投成功后线程侧的滞留指令不会被触发重看。

**用户出处与影响：** 绑定漂移或 head 缺位的窗口内向线程会话发多条消息：先发的入箱滞留，后发的直投秒达（可能还落错会话，见 D14）。用户看到的是"新消息有反应、旧消息石沉大海"。

**实施需明确：** 直投路径要不要捎带检查线程滞留（不能代为清偿——fencing 语义下直投无权投递 head 队列——但可以触发一次 force 对账或提示"线程有 N 条指令滞留"）；或者接受跨路径不保序并在文档里明确"线程顺序保证仅限队列路径"。

**建议：** 直投不捎带清偿（保持 fencing 语义纯净），但直投命中时可异步触发 janitor 提前对账（把 15s 等待压缩掉）；用户提示归 D11 的文案分级一并考虑。

## D14．直投落错会话的可见性（细化轮新增）

**已确认行为（TLA 场景证据）：** `offthread-direct-reachable` 场景证明输入静默落错地方可达：runtime 绑定漂移到无关会话时，用户对着线程 head 会话发言，消息经直投成功落在漂移后的会话（模型终态 "direct"，响亮成功），不经线程队列、不受 fencing、不清偿 pending。同一窗口内若 runtime 绑定的是历史成员会话，用户得到的是响亮的 409 拒收（`session_not_head`）——**同为"runtime 不在 head"，可见性不对称：member 响亮失败，foreign 静默落错**。

**用户出处与影响：** shared-by-project 共享 runtime 被其他项目借用期间（或用户手动切过会话后），向线程会话发的消息实际进了别的会话。用户在线程里等回复，回复出现在无关会话；线程侧无任何痕迹。

**实施需明确：** 直投落点与线程 head 不一致时要不要提示（"消息已发送到会话 X（runtime 当前绑定），线程队列中有 N 条指令待投"）；直投是否应该在绑定漂移时降级为拒收（与 member 路径对齐）或保持尽力投递。

**建议：** 与 member 路径对齐可见性——直投成功但落点不是 head 时至少提示落点；是否升级为拒收属产品取舍，登记裁决。

## 方法论注记（试验体系自身，不占裁决编号）

- **活性性质的空转陷阱**：`<> (\A i : cmd[i] # "pending")` 形状的否定式从"Init 无 pending"出发不可满足，TLC 永远报告通过——本轮实测踩过，必须用 leads-to（`pending ~> delivered`）。已审计既有模型：`ReceiptBoundaryDeep` 的 `EventuallyDisposed` 因 Init 队列非空而成立，`UnresolvedLifecycle` 已用 `~>`，均无此问题。
- **弱公平性的代偿陷阱（细化轮实测）**：TLA+ 的 action 是状态对谓词，不是产生者身份——效果完全重合的转移即算该 action 发生。给"janitor 周期扫描"建模为 WF 时，用户切回操作（重绑 head）与扫描的唤醒分支效果重合，无限漂移/切回环即可代偿满足 WF 而扫描从未真正触发对账。解法是给定时器类 action 携带专属哑效果（`sweepTick` 翻转），任何不带该效果的转移无法代偿。同型问题也出现在析取 WF 上：`WF(Wake ∨ Reconcile)` 只要求之一发生，唤醒分支被外部干扰无限触发即可饿死对账分支——这条已从缺陷候选转正为真实的饥饿形态（D12-3）。
- **TLA+ 多行合取按 `/\` 列对齐决定层级**：重构 action 时 THEN/ELSE 关键字或合取项缩进错位，UNCHANGED 会被静默解析进错误分支（TLC 报"successor state not completely specified"）。列对齐是语法结构的一部分，不是排版习惯。
- **哑效果变量必须有界**：定时器计数器用 `Nat` 递增会让状态空间无限，TLC 无法终止；哑效果只需要"变化与否"的区分，布尔翻转足够。
- **TLC 活性只认真实转换环**："无任何 action 使能"的纯停滞对 TLC 活性检查不可见——死锁类必须配可达性不变式（本模型的 `NotDeadlockFencing`）才能进入 TLA 体系。这解释了为什么宿主层死锁此前在所有模型中隐形。终态（全部送达、无 action 使能）经 `-deadlock` 关闭死锁误报后成为合法自环，由活性性质判定。
- **递减计数器消灭精确环**：干扰预算若随每次干扰递减并进入状态，饥饿 lasso 的精确状态环就不存在（TLC 找不到环），且状态空间随预算值线性爆炸（实测 999 预算下安全场景膨胀至 270 万状态）。本模型的解法：`Bound*=FALSE` 时无限干扰且不递减计数器（保留精确环），`TRUE` 时才递减（假设显式化）。
- 工程细节：TLC cfg 不接受负数字面量、常量替换不展开定义。
