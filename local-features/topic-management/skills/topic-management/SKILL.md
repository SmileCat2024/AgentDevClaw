# Topic 看板主题簇标注

主题簇（Topic）由会话引用关系客观形成，不是人工创建的分组。本技能覆盖两件事：

1. **工具边界**：`topic_list` 列出全部主题簇（topicId / 标题 / 简介 / 参考文档 / 相关提交 / 对话数 / updatedAt）；`topic_update` 逐个更新标注。仅此两个动作——不创建、不删除、不合并、不拆分簇。可更新字段：title、summary（字符串；`title: ""` 恢复自动标题，`summary: ""` 清除简介，慎用——会丢已有标注）；docs、commits（字符串数组，整体覆盖——传空数组清除，追加先读回现值合并后再提交）。一次只处理一个主题。
2. **写法规范**：标题与简介服务两类读者——用户事后浏览，回忆“当时干的什么事”；agent 接新任务时判断“这活干过没有、要不要下钻细看”。

## 标题：话题域，不是事件

标题回答“这簇对话**关于什么**”，用名词性话题域命名；不回答“做了什么”。

- 不带动作动词（修复 / 实现 / 验证 / 排查 / 重构 / 收口……这些词留给简介）。✗“修复搜索索引rename竞态” → ✓“搜索索引并发写入 EPERM”
- 跨会话稳定：同话题的新会话加入该簇后，标题依然成立。钉死单代快照的标题（如“P2活跃域Classic模块迁移试运行”）会过时，应升到工程级话题域（如“前端 ESM 绞杀者迁移”）。
- 与相邻话题可区分：同类工作分属不同簇时，标题要能互相区分（“前端插件化改造收尾”与“前端 ESM 绞杀者迁移”是两个工程，不要都叫“前端插件化”）。
- 不要沿用会话自动标题的风格：自动标题是单会话事件概括，天然带动作动词；改写时先剥离动作、提炼话题域。
- 专名保留原文（WorkThread Inbox、session_search、fw-config-panel），不翻译不转写。

## 简介：事件还原，人话优先

简介把“当时干的这件具体的事”还原出来，按三段组织：

1. **现象 / 动机**（第一句，纯人话）：当时遇到了什么、为什么干这件事。用户读到第一句就该想起当时的事，不需要先懂术语。
2. **做法**（中段，白话叙述）：干了什么、怎么解决的。允许且需要动作词定性（排查 / 修复 / 重构 / 落地）；专名嵌在叙述里，必要时带半句解释（如“收件箱（WorkThread Inbox，线程接收用户指令的地方）”）。
3. **结果锚点**（结尾）：提交号、PR、版本号、结项状态等硬锚点，可留一句总括（如“共 5 个提交交付”）；逐条清单交给 docs / commits 字段（见下节），不在简介里罗列。

**术语的定位：检索锚点，不是理解的必经之路。** 读者不懂简介里的任何术语，也应该能抓住这是件什么事；术语放在后半段，是给 agent 检索匹配用的。

### 正反例：同一主题的简介写法

以主题“ADR-0047 线程输入持久租约”为例，两种典型偏差与合格写法：

| 写法 | 文本 | 判定 |
|---|---|---|
| ✗ 名词清单 | 线程命令取消闭环、已领取消息误显排队气泡、行为矩阵测试。 | 只有词，没有事 |
| ✗ 术语密集 | ADR-0047 的实现与收口：线程输入持久租约确认协议（claim/ack、fencing 墙、幂等键）与崩溃恢复；顺带修复 call-arbiter 测试挂起。 | 要先懂术语才能还原事件 |
| ✓ 人话背景 | 落实 ADR-0047：发给 Coder 线程的指令改用持久化租约确认——领取要 claim、完成要 ack，配 fencing 墙和幂等键，保证崩溃恢复后指令不丢也不被重复消费；顺带修掉 call-arbiter 测试挂起。 | 第一句是动机，术语退到后半作锚点 |

## 参考文档与相关提交：结构化锚点

docs（参考文档）与 commits（相关提交）是简介里“结果锚点”的结构化升格：用户浏览看板不用从简介文本里捞提交号，agent 判断相关性时有现成锚点可下钻。

- **何时填**：主题有落地产物时顺手登记——涉及的 ADR / plan / 设计文档进 docs，落地的提交进 commits。没有就不填，不为填而填。
- **条目形态**：自由文本，推荐“定位符 + 半句说明”，如 `docs/adr/0047-lease.md — 线程输入持久租约决策`、`55f981a6 主题标注风格落成技能`。URL 原样写入（看板渲染为可点链接）。格式不强制：条目可读、可定位即可，其余尊重你的判断。
- **提交语义**：数组整体覆盖——追加条目先用 `topic_list` 读回现值，合并后整体提交；空数组清除该字段。
- **与简介的分工**：简介结尾保留一句总括，逐条清单进 docs / commits，两边不重复罗列。

## 信息不足时先调研，再标注

- 标题还是“新对话N”、或旧标题不足以还原事件的簇，先读内容再标注，不要凭标题推断细节。
- 调研路径：`session_list`（按时间窗收敛会话清单）→ `session_read_overview`（单会话概览 / wt- 前缀线程的代际导航）→ 需要细节再 `session_read_turn`。
- 依据现存标注改写时可以不深读，但拿不准的定性（如“缺陷排查”还是“功能落地”）必须核实。

## 工作流

1. `topic_list` 取全景，按最近活动排序。
2. 与用户对齐范围（时间窗 / 哪些簇）；未指明时按最近活动优先。
3. 逐个 `topic_update`（一次一个），数量多时分批推进。
4. 汇报用对照表（旧标题 → 新标题 + 新简介），让用户能直接验收；风格争议点（粒度、结果锚点去留）单独列出请用户裁决。

维护时机：用户要求整理时；或发现未标注 / 会话概括式标题的簇时，主动建议整理。
