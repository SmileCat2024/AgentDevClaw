# Implement — 按票实现

实现用户在 spec 或 tickets 中已经描述好的工作。上游已经决定的事就是输入，本流程的全部职责是把它变成一次 commit——没有访谈、没有澄清轮次、不提议另一种做法。这正是它与"直接让 agent 构建这个"的区别：后者会一边构建一边重新设计工作。

## 一次运行的五个节拍

1. 读取 ticket 或 spec，找出 seams（预先约定的测试边界）。
2. 在这些 seam 上驱动 tdd 流程，一次一个 red-green 切片。
3. 经常运行类型检查，随做随跑单个测试文件。
4. 完整测试套件只在结尾运行一次。
5. 执行 code-review 流程，然后把工作提交到当前分支。

## 边界与纪律

- **一次调用只做一张 ticket**。ticket 本应被切成恰好装进一个全新上下文窗口的 tracer-bullet 垂直切片；做完一张、提交、清空上下文再做下一张。每张票自包含，上一张的上下文才可抛弃。
- **不触碰工单状态**：流程到 commit 为止，不关闭工单、不勾选验收清单、不处理 code-review 产出的发现——那由维护者收尾。依赖链上的后续票据只有在前置票据被关闭后才解锁，所以工单不关闭会阻塞整条链。
- **提交目标是当前分支**：不新建分支、不询问、不开 PR（用户在指令中显式要求时除外）。开工前确认自己站在正确的分支上。
- 计划只存在于当前对话且规模不大时，直接就地 implement，不必去找不存在的 spec 文件；说明计划在对话里即可。
- `#2` 这类裸编号要按配置的 issue tracker 解析——全新会话里它可能指向某个 todo 文件而不是工单。拿不准时请用户给出完整引用（issue URL 或 `owner/repo#2`），并先复述工单标题再开工。

## 与相邻规范的关系

- 上游：tickets 由 to-tickets 之类流程拆分（垂直切片 + blocking edges）；implement 信任上游交付物，不重新校验它的形状——结构糟糕的票会按原样被构建。
- 内部：每个 seam 走 tdd 规范；tdd 拒绝在未确认的 seam 上写测试，所以 seam 约定要么来自上游 spec，要么发生在本次运行的第一次交互中。
- 收尾：commit 前执行 code-review 规范。
