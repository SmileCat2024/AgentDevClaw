## 1. 产品背景与核心判断

### 1.1 用户痛点

当 AgentDevClaw 的单 agent 能力基础（Feature 机制）已经打实之后，用户面临的新瓶颈是：**并行运行多个 agent 会话时的管理成本**。

典型场景：用户同时开发一个项目的多个模块，需要开启多个编程小助手会话并行推进。当前的体验是：

1. **启动焦虑**：一个个创建会话、等待启动、确认就绪——注意力被切碎，还没开始干活就累了。
2. **监控焦虑**：不知道哪个会话在正常工作、哪个卡住了、哪个在烧 token。被迫在多个 tab 之间不断切换。
3. **干预焦虑**：某个会话跑偏了，需要切过去、中断、重新给指令——上下文切换的认知成本极高。
4. **综合焦虑**：不记得哪个做完了、哪个还在跑、结果有没有冲突。没有地方"一眼看到全局"。

这四个焦虑叠加，导致用户不敢开太多并行会话。不是因为技术不支持，而是因为**认知带宽撑不住**。

### 1.2 行业误区

当前大量"多 agent 协作"产品的隐含假设是：模型能力足够强，可以放一个"管理者 agent"去自主拆解任务、分配工作、管理依赖、判定完成。

但现实是：

- **任务定义本身模糊**——"重构支付系统"这种指令，人类项目经理都需要反复澄清才能界定边界。
- **完成标准不可量化**——什么算"改完了"？没有人类判断，agent 会自己发明一个标准然后宣布成功。
- **错误会级联**——A 的错误输出被 B 当成正确输入消费，C 又在 B 的基础上继续，最后整条链都是错的。
- **虚假快感**——5 个 agent 都很忙，都在产出，但用户不敢用这些产出，因为无法验证、无法信任、也无法追溯问题出在哪。

### 1.3 AgentDevClaw 的判断

**在模型能力不足以让 agent 自主管理多 agent 协作之前，产品的核心价值是让人成为高效的 orchestrator——用最低的认知负荷，指挥、监控、验证多个 agent 的工作。所有的自动化都应该是"执行人的意图"，而不是"替代人的判断"。**

这条原则意味着：

- 所有实质性的判断和决策由人来做。系统做的是降低人做判断和决策的成本。
- 不自主拆解复杂任务、不自主分配工作给其他 agent、不自主判定工作完成。
- 但要让人的指挥极其低摩擦，让 agent 的产出极其可验证。

### 1.4 产品方向

基于以上判断，产品的下一阶段方向是：**以群聊为核心载体，构建一个即时通讯式的 agent 管理界面。用户通过群聊和私聊指挥多个 agent，管理员（超级助理）作为群聊的功能层提供协调和分析能力。**

## 2. 产品哲学：人是唯一的 Orchestrator

### 2.1 两条路径的分野

| | Agent 自主管理（当前不碰） | 人指挥多 agent（当前要做） |
|---|---|---|
| **谁拆解任务** | orchestrator agent | 人 |
| **谁分配工作** | orchestrator agent | 人 |
| **谁判定完成** | orchestrator agent | 人 |
| **谁管理依赖** | orchestrator agent | 人（系统辅助执行） |
| **系统的角色** | 替代人做决策 | 降低人做决策的成本 |
| **信任模型** | 信任 agent 的判断 | 信任人自己的判断 |

### 2.2 正确的演进序列

```
Step 1: 单 agent 做到强大、可组合、可监视（已完成 — Feature 机制）
          ↓
Step 2: 人能低成本地并行指挥多个 agent（当前要做 — 群聊指挥台）
          ↓
Step 3: 系统辅助人的指挥（依赖自动执行、状态自动汇总、异常自动提醒）
          ↓
Step 4: 在人监督下的半自主协作（agent 能处理明确的、有边界的子任务）
          ↓
Step 5: 高度自主的多 agent 协作（模型能力到位后）
```

**Step 2 是 Step 3-5 的前提。** 因为现在建的每一块基础设施——群聊消息流、provider API、上下文组装机制——未来都不会浪费。它们是"人指挥"的工具，但同时也是"agent 自主"的接口。区别只是调用方从人变成 agent——接口不变。

没有 Step 2 的人类指挥经验和基础设施积累，Step 4/5 的自主决策就是空中楼阁。

### 2.3 系统的四个核心职责

在这个框架下，系统的四个核心职责是**降低人的认知负荷**：

1. **低成本的态势感知**——不用逐个检查就知道全局（群聊态势层 + widget）
2. **低成本的指令下达**——不用层层菜单就能操控（@mention + 结构化输入）
3. **低成本的上下文保持**——不用自己记所有事（群聊消息流 + 透明取用）
4. **低成本的干预和纠正**——发现问题能立即介入（@mention 直接路由）

## 3. 核心概念：群聊作为共同上下文

### 3.1 定义

> **群聊是一组干话题相关且有边界事物的 agent 的共同上下文。**

每个限定词都有明确的产品含义：

- **"话题相关"**——群聊不是全局的。它是为了某个具体的事情而存在的。"重构支付系统"是一个群，"探索某套开源代码"可能是另一个群。不同群的上下文不串。
- **"有边界"**——群聊有生命周期。事情做完了，群就沉寂了。群聊的上下文是一个有头有尾的叙事，不是一条无限增长的 feed。
- **"共同上下文"**——群聊不是 agent 之间的消息总线，而是一份所有参与者都能读到、都能写入的共享文档。人写了什么，agent 能读到；agent 报告了什么，人和其他 agent 也能读到。

### 3.2 群聊的三个核心循环

产品中有三个不断运转的循环，它们都以群聊为枢纽：

**循环一：感知循环**
```
Widget 暴露状态 → 群聊消息流聚合状态 → 管理员通过群聊感知全局 → 做出更合理的建议
```

**循环二：指挥循环**
```
人在群聊表达意图 → 管理员理解意图或直接路由 → agent 执行 → agent 在群聊报告结果 → 人做决策 → 新的意图
```

**循环三：记忆循环**
```
消息持续流入 → 热窗口滑动 → 活态简报增量更新 → 用户可见/可纠正 → 管理员基于简报做判断 → 需要细节时检索归档
```

### 3.3 群聊作为产品主实体

在产品架构中，群聊不是辅助功能，而是**主实体**。用户的主要工作方式是：

1. 为某个项目/任务创建一个群聊
2. 拉入相关的 agent 身份
3. 指定（或由系统自动配置）管理员
4. 在群聊中指挥、监控、协调
5. 群聊作为这个项目的完整工作记录持续存在

**这取代了传统的"会话管理"概念。** 用户不需要理解"什么是 session""为什么要创建新 session""我的消息在哪个 session 里"——只需要像使用微信/QQ群聊一样自然地工作。

### 3.4 多群并存

支持多个群聊同时存在，各自独立：

- "支付系统重构"群：包含主代理（auth）、主代理（payment）、管理员
- "每日运维"群：包含 IM 接线员、调度员、管理员
- "探索调研"群：包含探索代理 A、探索代理 B、管理员

每个群有独立的消息流、独立的 agent 作用域、独立的管理员上下文。群之间不干扰。

这比"一个全局群聊"合理得多，因为不同的项目需要不同的参与者和不同的上下文。

## 4. 管理员：群聊的功能层

### 4.1 关键架构决策：管理员不是持续运行时

这是整个设计中最反直觉但最重要的决策。

**传统做法**：管理员是一个持续运行的 agent runtime，有自己的会话、有自己的上下文窗口、像其他 agent 一样存在。

**我们的做法**：管理员是群聊的一个**功能层**。它不持续存在，而是在被需要时激活，从群聊中取用上下文，执行任务后释放。

### 4.2 为什么不做持续运行时

如果管理员是一个持续运行时，它就面临上下文窗口的物理限制。群聊消息不断注入，上下文不断增长，最终必须压缩/摘要。这就回到了传统方案的老路：

- 上下文满了 → 压缩 → 信息丢失 → 用户不信任
- 压缩质量不稳定 → 管理员认知漂移 → 决策出错
- 用户不知道管理员"记得什么" → 黑盒 → 信任崩塌

更深层的问题是：**如果管理员的上下文包含了所有原始的工具调用、报错堆栈、调试过程，模型会获得错误的角色认知。** 它读着满屏的 `execute("read", {filePath: "xxx"}) → Error: ENOENT`，会开始觉得自己是个调试器而不是协调者。

### 4.3 管理员的工作模式

管理员的工作模式是"按需激活 + 透明组装 + 用完释放"：

1. **平时安静**：群聊在对话、agent 在工作、报告在流入，管理员不回应。它不是"每必回"的聊天机器人。
2. **被召唤时激活**：用户 @管理员，或裸 @某个 agent 需要路由解析，或某个条件触发（如 agent 报告了需要决策的问题）。
3. **激活时组装上下文**：从群聊中取用最近消息 + 相关每日总结 + 用户指定内容。这个过程用户能感知到"管理员在看资料"。
4. **回复时表明信息基础**："根据最近的消息和昨天的工作汇总……"让用户知道管理员的认知范围。
5. **通过 provider 调用 agent**：理解意图后，通过群内 agent 的 provider 能力声明调用相应操作。
6. **做完后释放**：不持续占用运行时，不持续消耗 token。下次被需要时再激活。

### 4.4 管理员与群聊的关系

```
群聊消息流（永久存储层）
├── 消息 1（2年前）
├── 消息 2
├── ...
├── 每日总结 A
├── 每日总结 B
├── ...
├── 消息 N（刚才）
└── 消息 N+1（现在）
        │
        │ 上下文组装（选择性取用）
        ▼
管理员工作上下文（临时消费层）
├── 系统提示词（角色定义 + 可用 provider 能力）
├── 每日总结（最近若干天的结构化摘要）
├── 最近消息（热窗口，原文保留）
└── 用户指定的补充内容（如"看看6月15号的讨论"）
```

两层之间的关系是**单向只读**：管理员从群聊中读取信息（选择性），但群聊本身不依赖管理员的读取状态。群聊是地基，管理员是访客。

### 4.5 管理员的核心职责

管理员不是"中转每条消息"的交换机，而是一个**参谋**。其核心职责包括：

1. **路由解析**：当用户裸 @某个 agent（不指定身份/会话）时，管理员从群聊上下文中判断该路由给哪个身份。
2. **全局分析**：用户问"现在什么进度""有什么风险"时，管理员组装上下文做综合分析。
3. **协调建议**：用户需要安排多人工作优先级时，管理员给出建议（最终决策权在人）。
4. **依赖管理**：用户表达条件依赖（"@A 完成后 @B 开始"）后，管理员负责监听 A 的完成并通知 B。
5. **经验沉淀**：管理员可以分析群聊中的共性错误，生成经验教训发到群里。

### 4.6 管理员可以跳过

管理员不是必经路径。确定的活，用户直接 @干活的 agent 身份下达指令，管理员完全不参与。只有需要全局视角时才 @管理员。

```
直接 @编程小助手·主代理<auth>: "重构 auth 模块的登录逻辑"  → 直接执行，管理员不参与
直接 @编程小助手·主代理<payment>: "等 auth 完成后你再开始"  → payment 执行，管理员不参与
@管理员: "看一下现在整体什么进度，有什么风险"  → 管理员组装上下文、分析、汇报
```

管理员的真正价值在于"需要全局视角时提供分析和建议"，不在于"中转每条消息"。

## 5. 上下文管理：存储与消费的分离

### 5.1 核心原则：分离"存储"和"消费"

这是与传统上下文管理方案的根本区别。

**存储层——群聊消息流**。永久、完整、append-only、用户随时可看。这是唯一的事实来源。任何信息只要进了群聊，就永远在那里，不会消失，不会被压缩，不会被篡改。

**消费层——管理员的工作上下文**。临时、选择性、每次激活时重新组装。管理员不"拥有"上下文，它每次都是"借"一部分群聊内容来用。用完就还回去。下次再激活时，重新组装一份新的。

### 5.2 为什么传统压缩方案会崩

传统方案的运转方式：

```
群聊消息 → 全部注入管理员上下文 → 上下文满了 → 压缩/摘要 → 继续注入 → 再满 → 再压缩
```

走到后面，管理员"记得"的东西是一层又一层的压缩残渣。用户完全不知道：
- 第 3 次压缩时丢了什么
- 现在管理员看到的"历史"准确度如何
- 它说的"我记得"是真的记得还是压缩后的幻觉

这个困境的根源是一个错误假设：**管理员的上下文必须容纳全部历史。**

### 5.3 我们的方案：透明取用

管理员每次激活时，从群聊中取用以下几类信息：

**最近的消息（热窗口）**：比如最近 20-30 条，原文照搬。保证管理员对当前情况有即时、完整的感知。

**每日总结（沉淀层）**：群聊中的一种特殊消息类型。每天结束（或按某种节奏）生成一条结构化的当日总结。它不是外部的 memory 文件，而是**群聊的一部分**——用户能看到、能纠正。管理员读取它来获取中长期的上下文。

**用户指向的特定内容**：用户说"看看 6 月 15 号关于 API 设计的讨论"，管理员去群聊归档里检索这些内容，纳入本次工作上下文。

组装后的管理员上下文大致长这样：

```
[系统提示词: 你是这个群的管理员。可用的 agent 身份和它们的 provider 能力如下...]

[每日总结]
  6月16日: auth 模块重构完成，payment 接口定义有争议，用户决定用 JSON
  6月15日: 项目启动，分派了三个模块的任务
  6月14日: 初始需求讨论

[最近消息 (最近20-30条)]
  用户: @管理员 现在什么进度？
  [主代理<auth>报告]: auth 重构完成，改了8个文件
  用户: 好，@编程小助手·主代理<payment> 开始对接
  ...

[用户指定的补充]
  (本次无)
```

### 5.4 每日总结的产品定位

每日总结**不是给管理员用的私有数据**，而是**群聊中的一种消息类型**。

它就像公司群里的"今日工作汇总"——由管理员（或后台机制）生成，发到群里，所有人可见。角色是：给群聊增加一层结构化的、易消费的信息层，让长跨度的上下文不需要翻几千条消息就能被快速理解。

因为它是群聊里的消息，所以：
- 用户能看到 → 可以验证准确性
- 用户能回复纠正 → 纠正内容也成为群聊的一部分
- 管理员下次组装上下文时能引用它 → 天然成为"记忆"的一部分
- 它不会消失 → 永久可查

**每日总结不是事后压缩，而是事中沉淀。它从一开始就在群聊里，是群聊叙事的一部分，不是外部系统对群聊的事后加工。**

### 5.5 干净日志 = 正确的角色认知

这是上下文管理的一个深层技术洞察。

如果把原始的工具调用、报错堆栈、调试过程都塞进管理员的上下文，模型会获得错误的角色认知。它读着满屏的技术细节，会从"协调者"漂移到"调试器"。回复的语气、视角、关注的层面都会变。

而每日总结是**经过格式化的人类语言叙事**：

> "今天 A 重构了 auth 模块，过程中遇到了一个文件冲突，已解决。B 完成了 payment 接口定义。C 因为缺少 API 文档暂停了。"

模型读到这种内容时，自然地进入"项目状态回顾"的认知模式。它知道自己是管理者，知道当前的项目态势，知道该从协调的角度来思考和回复。

**每日总结不只是"记忆压缩"，它同时是"认知锚定"——让模型每次激活时都站在正确的视角上。**

同时，结构化的每日总结天然提供了**时间结构**："6月16日：X 发生。6月17日：Y 发生。" 这弥补了大模型对时间理解差的弱点，给它一个清晰的时间线叙事。

### 5.6 三重确定性构建信任

用户不信任 assistant 的记忆，根本原因是不透明。我们的方案通过三重确定性解决信任问题：

1. **群聊里的东西不会丢**——这是物理确定性。消息就是消息，append-only，和你的微信聊天记录一样。用户的心智是"无限上下文"——群聊聊了两年，消息一直在那儿，该随时能看就能看。

2. **管理员看了什么它是明说的**——这是透明确定性。"我看了昨天的总结和最近 20 条消息。"不需要猜。用户一看管理员回复里说"根据昨天的日程……"，就知道它看了什么。如果用户觉得"前天那个 API 设计的讨论也得算上"，直接说一声。

3. **漏了什么我能补**——这是纠错确定性。用户永远可以指向群聊中的任意位置说"也看看这个"。管理员去取，纳入上下文，重新回答。

### 5.7 与传统方案的对比

对比两种架构下用户的内心独白：

**传统压缩方案：**
> "管理员说它记得我们决定用 JSON。它真的记得吗？还是压缩后的幻觉？上次的讨论具体说了什么？我得去翻 memory 文件……memory 文件里写的对吗？要不要我手动校对一遍？……算了，我不信任它了，自己来吧。"

**我们的方案：**
> "管理员说它根据昨天的总结知道我们决定用 JSON。我翻一下群聊——确实，昨天那条总结里写了。如果它漏了什么，我跟它说一声就行。"

## 6. 身份系统：工作空间的多面暴露

### 6.1 一个工作空间可以暴露多个身份

这是从"一个工作空间 = 一个 agent"到"一个工作空间 = 多个角色"的升级。

一个工作空间可以暴露多个身份，各有独立的 system prompt、Feature 组合、provider 能力声明。这些身份作为独立的 @mention 目标存在于群聊中。

```
编程小助手工作空间 暴露:
  ├── 主代理    — 擅长编码、调试、重构（完整 Feature 集）
  ├── 探索代理  — 只读分析、知识收集（受限 Feature 集）
  └── 审计员    — 代码审查、安全检查（特定 Feature 集）
```

### 6.2 与现有架构的对接

这跟现有架构完全对得上。编程小助手已经有 exploration 模式（`PROTOCLAW_SESSION_TYPE === 'exploration'`），已经有不同的 Feature 组合：

- **主模式**：TodoFeature, AuditFeature, AudioFeedbackFeature, WebSearchFeature, MemoryFeature, ShellFeature, LspFeature, UserInputFeature, ClawDispatchFeature, CheckpointFeature
- **探索模式**：ShellFeature, WebSearchFeature, MemoryFeature, ClawDispatchFeature

这些天然就是不同的"身份"。现在只是把它们从内部的环境变量升级为外部可 @mention 的一等实体。

### 6.3 身份声明的结构

每个身份需要声明：

| 字段 | 说明 | 示例 |
|---|---|---|
| **id** | 身份唯一标识 | `main`, `explorer`, `auditor` |
| **显示名** | 在群聊中显示的名字 | `主代理`, `探索代理`, `审计员` |
| **system prompt** | 该身份的系统提示词 | 各自的 prompt 文件 |
| **feature 组合** | 该身份启用的 Feature 列表 | 主代理用完整集，探索代理用受限集 |
| **provider 能力** | 该身份可被调用的操作集 | create_session, send, interrupt 等 |
| **能力描述** | 给管理员看的"说明书" | "这个身份擅长编码任务，可以创建新会话" |

### 6.4 身份的想象空间

不同类型的未来工作空间暴露身份的想象空间：

```
IM渠道工作空间:
  ├── 接线员    — 管理 IM 线路转接（对应现有 IMOperatorFeature）
  └── 客服      — 直接回复用户消息

Flow工作空间:
  ├── 架构师    — 编排图设计
  └── 运行时    — 执行编排图

调度工作空间:
  └── 调度员    — 管理定时任务

日程工作空间（纯 UI，无 agent runtime）:
  └── 日历     — 查询/管理日程（通过 provider 暴露能力，不运行 LLM）
```

注意最后一项：**某些身份可能不运行 agent runtime**。一个日程工作空间可能只是一个数据源，通过 provider 暴露 `query_schedule`、`add_event` 等操作，但不运行 LLM。管理员可以调用这些操作来"感知"用户的日程，但这些身份不会自己"说话"。

### 6.5 身份与会话的关系

身份是 @mention 的目标。身份背后的具体会话管理是工作空间自己的事：

- **编程小助手·主代理**：可能绑定到一个具体的编码会话（有项目目录、对话历史）
- **编程小助手·探索代理**：可能是一个一次性的探索任务（完成后锁定）
- **管理员**：没有会话概念，每次激活都是独立的
- **日历**：没有会话概念，就是一份数据

用户在 @mention 时不需要关心这些差异。@mention 的目标是身份，身份背后的复杂性被封装了。

## 7. 路由规则：@mention 的语义体系

### 7.1 核心路由矩阵

| 用户输入 | 含义 | 路由行为 | 管理员是否介入 |
|---|---|---|---|
| `@编程小助手·主代理<auth> 重构 auth` | 明确指令，限定身份+会话 | 直达目标，确定性路由 | 否 |
| `@编程小助手 重构 auth` | 意图明确但目标模糊 | 管理员解析 → 确定身份 → 路由 | 是 |
| `@管理员 安排一下 auth 的工作` | 纯协调请求 | 管理员全权处理 | 是 |
| 无 @mention | 讨论型消息 | 进入群聊上下文，不触发执行 | 否 |
| 多 @mention 同批发送 | 指令组合 | 各自路由，记录关联 | 视情况 |

### 7.2 限定符的语义

**有限定符 = "我知道该谁干"。无限定符 = "帮我找对人"。**

这在日常生活中也完全对应：

- "@张三(技术部) 你来修这个 bug" → 你知道找谁，直接说
- "@技术部 这个 bug 谁能修一下？" → 你不知道找谁，让部长分配

前者不需要部长介入。后者部长（管理员）出面协调。

### 7.3 限定符的语法约定

```
@工作空间                       → 泛泛 @，管理员介入解析
@工作空间·身份                   → 指定身份，直达
@工作空间·身份<会话/上下文标签>   → 指定身份 + 具体工作上下文，完全确定性路由
```

例如：

```
@编程小助手                      → 管理员介入："你要找谁？做什么？"
@编程小助手·主代理               → 直达主代理，使用默认/最近会话
@编程小助手·主代理<auth-service>  → 直达主代理，绑定到 auth-service 项目
```

### 7.4 会话选择器

当用户在输入框中打出 @编程小助手·主代理 时，系统弹出快速选择器：

```
输入 @编程小助手·主代理
    ↓
弹出快速选择:
  ┌──────────────────────────┐
  │ 📂 auth-service          │ ← 最近活跃
  │ 📂 payment-service       │ ← 最近活跃
  │ 📂 notification-service  │
  │ ─────────────────────── │
  │ + 新建会话...             │
  └──────────────────────────┘
    ↓
选择后输入框显示:
  @编程小助手·主代理<auth-service> │
```

这个交互跟微信群里的 @选择成员 是同一种心智。只不过这里的"成员"是会话/上下文维度。

**关键**：会话选择器的具体内容由工作空间自定义。不同的工作空间有不同的会话维度——编程小助手按项目目录分会话，Flow 工作空间按项目分会话，日程工作空间可能不需要选择器。

### 7.5 成本优势

`@编程小助手·主代理<auth>` 不唤起管理员，意味着：

- **零额外 token 消耗**——确定的指令直达目标，不经过管理员的 LLM 推理
- **零额外延迟**——不需要等管理员解析后再路由
- **管理员不成为瓶颈**——大量直接指令可以并行，管理员只在需要全局视角时才被召唤

而 `@编程小助手`（无限定符）唤起管理员，用户接受"我需要帮助"，愿意为此付出一点等待。

**用户通过是否打限定符，自主选择了"快路径"还是"智能路径"。不需要额外的 UI 开关。**

### 7.6 自然的行为演化

用户刚开始用时，可能不太清楚有哪些身份，经常打裸 @。管理员帮忙路由几次后，用户就学会了："哦，这种事我应该直接 @主代理。" 逐渐从智能路径迁移到快路径。

这是一个自然的效率提升曲线——系统不强迫用户学习，但用户用着用着自然就变快了。就像刚进一个公司时什么都找主管问，熟了之后直接找对应的同事。

## 8. 结构化输入：从 string 到指令组合

### 8.1 核心洞察

群聊的输入框不是一个 textarea（纯文本），而是一个**指令编辑器**——但用起来仍然像聊天。

每条输入可以包含多个 @身份 指令块。同一批发送的指令块之间自动产生关联关系。

### 8.2 示例拆解

```
@编程小助手·主代理<auth> 请完成登录逻辑的重构，确保 v1 API 兼容
@管理员 它完成之后检查一下，如果测试通过就让 payment 开始对接，如果没通过就列出失败原因
```

这不是一条消息。这是**两条指令的组合发送**。它们之间有明确的关联——第二条引用了第一条的完成状态。

如果这只是一段纯文本 string，系统得靠 NLP 去"猜"哪里是指令边界、哪里是依赖关系。猜错了就路由到错误的目标、遗漏了依赖条件。

但结构化输入让用户在输入时就声明好指令的结构。系统不需要猜。

### 8.3 输入框的产品形态

```
┌──────────────────────────────────────────────┐
│ [@编程小助手·主代理<auth-service> ×]           │
│ 请完成登录逻辑的重构，确保 v1 API 兼容          │
│                                              │
│ ── 关联指令 ──────────────────────────────── │
│                                              │
│ [@管理员 ×]                                    │
│ 它完成之后检查一下：                           │
│ 如果测试通过 → 让 @编程小助手·主代理<payment>   │
│   开始对接                                    │
│ 如果没通过 → 列出失败原因                      │
│                                              │
├──────────────────────────────────────────────┤
│                                    [发送]     │
└──────────────────────────────────────────────┘
```

每个 `@身份` 开启一个指令块。块与块之间有视觉分隔。发送时，系统把每个块路由给对应的目标，并记录块之间的关联关系。

### 8.4 隐式关联：同一批 = 协调组

"一次同时下达多个指令就可以起到关联的作用"——同一批发出的指令自动构成一个**协调组**。

系统这样理解：

```
情况1: 并行（多条独立指令同批）
  @A<auth> 做重构
  @B<order> 做对接
  → 两件事同时开始，互不依赖

情况2: 串行（带依赖表达）
  @A<auth> 做重构
  @管理员 A完成后让B开始
  → 先A后B，管理员负责衔接

情况3: 条件（带分支表达）
  @A<auth> 做重构
  @管理员 A完成后检查，通过则通知B，不通过则报告原因
  → 管理员做判断，分支执行
```

用户不需要学任何"语法"。他只是自然地写——先写给 A 的指令，再写给管理员的指令，中间用"完成后"这种自然语言表达依赖。系统从结构（同一批发送）中读取关联，从文本中读取语义。

### 8.5 指令型 vs 讨论型

@mention 的有无，天然就是"指令"和"讨论"的分界线：

**指令型**——给 agent 或管理员的工作指示。需要明确、可执行、带条件。结构化输入主要服务这种。

```
@编程小助手·主代理<auth> 先暂停当前任务   → 指令型，路由到目标会话执行
```

**讨论型**——跟群里分享想法、提问题、做决策。自然语言，不需要结构化。

```
今天 auth 模块先停一下，明天再说   → 讨论型，进入群聊上下文，不触发任何 agent
```

不需要额外的 UI 开关来区分。有无 @mention 就是分界线。

### 8.6 "确定性修饰"的意义

指令需要比纯聊天更"确定"的修饰。用户在给 agent 下达指令时，会自然地使用更结构化、更精确的语言：

- "请你完成……"（任务定义）
- "确保 v1 API 兼容"（约束条件）
- "完成后检查，如果 A 则 B，如果 C 则 D"（条件分支）
- "等他完成后开始"（依赖关系）

这种"确定性修饰"不是强制的语法，而是用户在与 agent 协作时自然形成的习惯。结构化输入框通过 @mention 分块来辅助用户组织这些修饰，但不强制任何格式。

### 8.7 群聊消息的展示形态

结构化输入让群聊消息流更干净。每条消息在群聊里的展示也是结构化的：

```
[你 · 14:30]
  → @编程小助手·主代理<auth>: 请完成登录逻辑的重构
  → @管理员: 完成后检查，通过则通知 payment 对接

[编程小助手·主代理<auth> · 14:35]
  收到，开始重构。预计修改 3 个文件。

[编程小助手·主代理<auth> · 14:52]
  ✅ 重构完成。修改了 login.ts, auth-middleware.ts, session.ts。
     全部测试通过。

[管理员 · 14:53]
  auth 测试通过。已通知 payment 开始对接。
```

每条消息的**发送者身份**带标签（`<auth>`），**接收关系**清晰可见。用户回看时，就像看一份结构化的会议纪要——谁说了什么、谁回复了谁、什么时候发生的。

**群聊上下文的干净度直接影响管理员的认知质量。** 结构化输入从源头保证了每条消息都有明确的身份归属和指令边界。

## 9. 群聊与私聊：天然的上下文隔离

### 9.1 核心映射

群聊和私聊的区分，是人类已经内化的信息管理直觉。不需要教，不需要解释，所有人都知道：

- **群聊里说的** = 所有人可见，是共享上下文
- **私聊里说的** = 只对对方可见，是私有上下文

把这个直觉映射到 agent 管理上：

| 场景 | 发生在 | 进入群聊共享上下文？ |
|---|---|---|
| 项目决策、任务分派、进度汇报 | 群聊 | 是 |
| 某个 agent 的详细编码指令、调试细节 | 跟该 agent 私聊 | 否 |
| 跟管理员讨论编排策略、分析风险 | 跟管理员私聊 | 否 |
| 管理员发布全局通知、经验教训 | 群聊（管理员发布） | 是 |

**这天然解决了上下文污染问题，不需要任何技术上的过滤机制。**

用户凭直觉就知道："这个调试细节不适合在大群里说，我单独找 A。" 于是这些细节永远不会进入群聊的共享上下文，永远不会干扰管理员的认知。

### 9.2 群聊保留的信息天然有意义

群聊里保留的，天然就是**对全局有意义的信息**——决策、状态、结果、风险。因为用户在私聊和群聊之间做选择时，已经做了信息过滤。

这意味着管理员从群聊取用上下文时，获得的信息密度很高、噪音很低。不需要额外的信息过滤机制。

### 9.3 私下思考、公开发布

管理员的一个重要工作模式：

1. 用户**私聊管理员**："整理一下今天发生的事情，有没有大家共犯的错误，列一下。"
2. 管理员**私聊中分析**（基于群聊上下文 + 每日总结）。
3. 管理员**在群聊公开发布**："今天发现三个共性错误：1) 多个 agent 修改了同一个配置文件。2) … 大家注意。"

这就是**私下思考、公开发布**——管理者的标准工作方式。

分析过程（管理员读群聊、推理、整理）不需要在群里展示，那是噪音。只有结论（给所有 agent 的经验教训）才值得发到群里成为共享上下文。

因为分析过程不在群里，群聊上下文继续保持干净。下一次管理员激活时，看到的仍然是干净的叙事，不是上一轮分析的思维碎片。

### 9.4 私聊的产品形态

私聊不是新的 surface，而是群聊界面的另一种模式：

- 左侧列表中，每个群聊下面可以展开其成员的私聊入口
- 私聊的界面与群聊一致（同样的消息流展示）
- 私聊的消息不进入群聊的共享上下文
- 私聊的上下文独立于群聊

用户在编程小助手的左侧列表中看到的现有会话，本质上就是"私聊"——只是现在有了群聊作为对照，私聊的定位更清晰了。

### 9.5 消灭"会话管理"这个反人类概念

当前所有 agent 产品都有一个绕不开的折磨：**会话管理**。创建会话、切换会话、恢复会话、给会话起名字、决定哪条消息属于哪个会话……这是给计算机设计的概念，不是给人设计的。

群聊/私聊模型把它彻底消解了：

- 你想跟 agent 团队协作 → 开一个群聊
- 你想跟某个 agent 单独深入工作 → 跟它私聊
- 你想让管理员分析全局 → 私聊管理员
- 你想让所有人知道一件事 → 在群里说

**没有"会话"，只有"聊天"。** 群聊和私聊是十亿人已经会用的概念。用户只是把"对面"从人换成了 agent。

"持久化"——agent 记住之前说过什么——也不是一个需要管理的功能，而是聊天的天然属性。你的微信聊天记录是持久的，不需要你做任何"持久化操作"。

## 10. 看板融入群聊：三层结构

### 10.1 核心判断：看板不是独立 surface

之前讨论过的 Widget 仪表盘，其功能可以融入群聊。因为如果群聊是共同上下文，那么所有状态、所有进度、所有产出，本质上都已经在群聊的内容里了。看板只是这些内容的另一种**视角**。

### 10.2 群聊界面的三层结构

**第一层：群头部（态势感知层）**

群的顶部，始终可见。显示：
- 群成员（哪些身份在群里）及各自的实时状态（运行中/空闲/出错）
- 群目标（一句话）
- 当前进度概览（进行中几项、完成几项、阻塞几项）

这一层替代了之前讨论的"status-grid widget"。但它不是一个独立的 widget，而是群聊的原生组成部分。用户在群里的时候它永远在视野里。

**第二层：消息流（交互层）**

群的主体。用户输入、agent 报告、系统事件，都在这里。但比纯文本聊天丰富——agent 的报告可以是**结构化卡片**（改了哪些文件、测试结果、遇到的问题），而不只是一段文字。

用户可以：
- 直接打字（自然语言指令或讨论）
- @某个身份
- 点 agent 报告卡片上的快捷按钮（深入查看 / 中断 / 回复）

**第三层：群侧边（细节层）**

可选展开。点击某个身份的状态或报告，在侧边显示详细信息——完整的会话记录、provider 操作面板、运行日志等。

这就是"深入查看"的去处。不在群里占空间，但一键可达。

### 10.3 为什么这比独立看板更好

独立看板的问题是：它和群聊是两个 surface。你在看板里看到 A 出错了，要切到群聊去处理。处理完再切回看板继续监控。上下文切换。

融入群聊后：你在群聊里看到 A 的状态变红了（顶部态势层），报告卡片显示错误详情（消息流），你直接在群里 @A 给新指令，A 恢复后状态变绿。全程不离开群聊。

**看板不是一个要去"看"的地方，而是你待着的地方本身就让你看得见。**

### 10.4 Agent 报告的结构化卡片

agent 在群聊中的报告不应该是纯文本，而应该是**富信息卡片**：

```
┌──────────────────────────────────────────┐
│ 🔵 编程小助手·主代理<auth> · 14:52         │
│                                          │
│ ✅ auth 模块重构完成                       │
│                                          │
│ 修改文件:                                 │
│   • login.ts (+45 -12)                   │
│   • auth-middleware.ts (+8 -3)           │
│   • session.ts (+15 -5)                  │
│                                          │
│ 测试: 12/12 通过                          │
│ 耗时: 17 分钟                             │
│                                          │
│ [查看详情]  [回复]  [新建关联任务]          │
└──────────────────────────────────────────┘
```

卡片上的信息一目了然，快捷按钮提供常见操作的入口。不需要切到该 agent 的页面就能获取关键信息和做出反应。

## 11. Provider 与 CLI：软耦合的接口契约

### 11.1 核心问题

群聊中有来自不同工作空间的多个身份。它们的内部实现完全不同：
- 编程小助手的"创建会话"参数可能是 `{path: "项目路径"}`
- Flow 工作空间的"创建项目"参数可能是 `{assemblyName, selectedFeatures, envDir}`
- 未来的日程工作空间的"添加事件"参数可能是 `{title, startTime, endTime}`

如果管理员 agent 硬编码了"怎么调用编程小助手""怎么调用 Flow 工作空间"，那就是紧耦合——每加一个新身份就得改管理员的代码。

### 11.2 CLI Provider 体系作为解法

AgentDevClaw 已有的 CLI Provider 架构（`server/providers/*.mjs` + `server/claw-core.mjs`）天然是解法。

每个工作空间通过 provider 声明自己能做什么。管理员加入群聊时，读取群内各身份的 provider 能力声明（就像读一份工具说明书），然后就知道：这个身份能被怎么调用、参数是什么、返回什么。

**这就是"软耦合"：管理员不假设任何身份的内部实现，只依赖 provider 声明的操作集。加一个新身份，只要它有 provider 声明，管理员就能用。**

### 11.3 Provider 操作的三种消费形态

Provider 声明是接口契约，有三种消费形态：

| 消费形态 | 消费者 | 传输格式 |
|---|---|---|
| CLI 命令 | 人类（终端） | 命令行文本 |
| MCP 工具 | Agent（LLM） | JSON 结构 |
| HTTP API | 前端 / 其他服务 | JSON over HTTP |

"CLI 形式"更多是一种**架构隐喻**——"每个工作空间声明自己可被调用的操作"。agent 消费时走的是 MCP 或 HTTP API，拿到的是结构化数据。CLI 只是给人用的一种形态。

### 11.4 当前的 Provider 现状与扩展需求

当前状态：
- 只有 `programming-helper.mjs` 一个 provider
- 已有操作：overview, explorations, subs, show, spawn, compact, create_session, resume
- 缺少**运行时控制类**操作

扩展需求——每个 workspace provider 都应该实现的标准操作集：

```
标准操作（所有 workspace 应实现）:
  status      — 当前运行时状态（idle/running/queued/error + 简要摘要）
  sessions    — 活跃会话列表（ID, 标题, 状态, 最后消息时间）
  send        — 向指定会话发送消息（经 CallArbiter 入队）
  interrupt   — 中断当前运行中的调用
  create      — 创建新会话
  close       — 关闭/停止会话

扩展操作（各 workspace 自定义）:
  explorations    — （programming-helper 已有）
  spawn           — （programming-helper 已有）
  ...
```

### 11.5 Provider 扩展路径

```
当前: 只有 programming-helper.mjs

目标:
  programming-helper.mjs  — 增加运行时控制操作（status, send, interrupt）
  flow-workspace.mjs      — 新建（status, sessions, create, deploy）
  qqbot.mjs               — 新建（status, lines, connect, disconnect）
  dispatch-console.mjs    — 新建（schedules, trigger, cancel）
```

在 `claw-core.mjs` 的 `createContext()` 中增加运行时控制函数（`getRuntimeStatus`, `sendToRuntime`, `interruptRuntime`），让所有 provider 都能用，而不需要每个 provider 自己写 HTTP 调用。

### 11.6 Provider 即控制面

一条 provider 声明，同时服务四种消费方：

```
Provider 声明:
  operations[]  → CLI 命令（人类用，终端执行）
               → MCP 工具（agent 用，管理员通过 MCP 调用）
               → Widget 操作（仪表盘用，前端直接调用）
               → 群聊命令（@mention 路由后系统调用）
```

这就是为什么 Provider 标准化是整个体系的地基。

## 12. Widget：工作空间的面孔与能力

### 12.1 Widget 不是"Agent 监控面板"

Widget 是**任意工作空间向外部世界暴露的面孔和能力**。它不绑定"agent"这个概念。

这意味着仪表盘（或群聊的态势感知层）不再是一个"多 agent 控制台"，而是一个**个人工作中心**——所有的工具、助手、日程、信息源，都有自己的位置。

### 12.2 不同工作空间的 Widget 形态

| 工作空间类型 | Widget 长什么样 | 暴露的能力 |
|---|---|---|
| 编程小助手 | 会话状态 + 最后消息 + 快捷操作 | create session, send, interrupt |
| Flow 工作空间 | 项目列表 + 装配状态 | create project, deploy assembly |
| 日程（纯 UI 工作空间） | 今日时间线 + 即将到来的事件 | query schedule, create event, check conflict |
| IM 渠道 | 在线状态 + 消息预览 | connect line, send message |
| 调度台 | 活跃定时任务列表 | create schedule, cancel, trigger now |

### 12.3 Widget 作为管理员的感知器官

每个 widget 背后都有一套能力接口（CLI + API），这套接口同时服务两种消费者——人类（直接看/操作）和 agent（被管理员调用）。

当管理员能感知到所有 widget 的状态时，它就不只是"知道哪个 agent 在跑"，而是**知道用户的完整工作上下文**：

- "用户今天下午 3 点有会" → 可以建议"要不要把编程任务安排在 2 点之前完成？"
- "payment 模块的会话卡住了" → 可以主动提醒"已经卡了 5 分钟，要不要我看看？"
- "调度台有个任务 10 分钟后要触发" → 可以提醒"10 分钟后 dispatch 会触发，确保目标 agent 在线"

### 12.4 Widget 的高度自定义

Widget 应该是**高度自定义的 HTML 模块，交给工作空间层来定义**。

有些工作空间不提供 agent，可能只是纯 UI 工作空间（如日程）。但它们都能暴露能力（CLI 与 widget 背后的接口），既可以被用户直接看到或进行控制，也可以被 agent 使用。

### 12.5 在群聊模型中 Widget 的位置

Widget 的功能融入群聊的三层结构中（详见第 10 节），不再作为独立 surface。具体映射：

| Widget 概念 | 在群聊模型中的角色 |
|---|---|
| 状态网格 | 群头部态势层 |
| Agent 报告卡片 | 消息流中的结构化展示 |
| 详细操作面板 | 群侧边细节层 |
| Provider 操作 | 管理员和系统调用身份的接口 |
| 快捷操作按钮 | 报告卡片上的内联按钮 |

没有一样东西是"游离在群聊之外"的。所有功能都长在群聊这棵树上。

## 13. 产品心智模型总结

### 13.1 一段话概括

> **一个即时通讯式的 agent 管理界面。你有一个联系人列表——里面是你的 agents（以身份为单位）和你的管理员。你有群聊——为某个项目拉一个群，把相关的身份拉进来，群里积累共享上下文。你有私聊——跟某个身份单独深入工作，或者跟管理员私下商量。群聊里积累的信息是干净的、持久的、所有人可见的。管理员从这里取用上下文，做分析，做建议，做汇报。你直接 @干活的身份下达确定指令，只有需要全局协调时才找管理员。没有会话管理。没有 session 切换。没有 memory 文件。没有上下文压缩。只有聊天——群聊和私聊。**

### 13.2 核心实体

| 实体 | 定义 |
|---|---|
| **群聊** | 有边界的工作上下文。永久 append-only 的消息流。管理员的工作上下文从这里取用。 |
| **身份** | 工作空间暴露的可 @mention 的实体。一个工作空间可以暴露多个身份，各有独立的 prompt、feature 组合和 provider 能力。 |
| **管理员** | 群聊的功能层。按需激活。从群聊取用上下文做分析、协调、路由。不是持续运行时。 |
| **人** | 真正的 orchestrator。在群里用自然语言指挥。所有实质性决策由人做。 |

### 13.3 核心交互

| 交互方式 | 语义 |
|---|---|
| `@身份·子身份<限定符>` | 确定性路由，直达目标，管理员不介入 |
| `@身份`（无限定符） | 管理员解析意图后路由 |
| `@管理员` | 纯协调请求 |
| 无 @mention | 讨论型消息，进入上下文不触发执行 |
| 多 @mention 同批发送 | 指令组合，隐式关联 |

### 13.4 核心架构原则

1. **群聊消息流是唯一的事实来源**，永不压缩，永不丢失。
2. **管理员的上下文是每次激活时从群聊中透明取用的子集**，用完即释。
3. **工作空间通过 provider + 身份声明实现软耦合**，管理员不假设任何身份的内部实现。
4. **人是唯一的 orchestrator**，系统只降低人指挥的成本。
5. **@mention 的有无和限定符的有无**天然区分指令/讨论、确定性/智能路由。
6. **群聊和私聊的区分**天然实现上下文隔离，不需要技术过滤。

### 13.5 三个核心循环

**感知循环：**
```
Widget 暴露状态 → 群聊消息流聚合状态 → 管理员通过群聊感知全局 → 做出更合理的建议
```

**指挥循环：**
```
人在群聊表达意图 → 路由（直接或经管理员）→ agent 执行 → agent 在群聊报告 → 人做决策 → 新的意图
```

**记忆循环：**
```
消息持续流入 → 热窗口滑动 → 每日总结增量更新（存入群聊）→ 用户可见/可纠正 → 管理员基于总结做判断
```

## 14. 演进路径

### Phase 1：Provider 扩展 + 群聊基础设施

**目标**：让所有 workspace 可被统一 API 操控，搭建群聊基础。

**关键工作**：
- `claw-core.mjs` 增加运行时控制函数到 context
- 各 workspace 的 provider 增加 `status`, `sessions`, `send`, `interrupt` 操作
- 新建 `flow-workspace.mjs`, `qqbot.mjs` 等 provider
- server.js 增加群聊 CRUD API（创建群、管理成员、消息流）
- server.js 增加每日总结生成机制
- server.js 增加上下文组装端点（给管理员用）

**交付物**：群聊基础设施可用，CLI 可操控所有 workspace。

### Phase 2：群聊前端 + 身份系统

**目标**：群聊界面可用，身份可 @mention。

**关键工作**：
- 新建 `public/src/app-chat.js`（群聊前端，独立于 app-ui.js）
- 群聊三层结构 UI（态势层 / 消息流 / 侧边）
- 身份声明机制（metadata.json 扩展）
- @mention + 会话选择器
- 结构化输入框
- 群聊消息流展示（含结构化卡片）

**交付物**：用户可以在群聊中 @身份 下达指令，看到 agent 报告。

### Phase 3：管理员功能层

**目标**：管理员可按需激活，提供路由解析和分析能力。

**关键工作**：
- 管理员的上下文组装逻辑（热窗口 + 每日总结 + 用户指定）
- 管理员的路由解析能力（裸 @mention → 确定身份 → 路由）
- 管理员的全局分析能力（进度汇报、风险评估）
- 管理员的依赖管理能力（条件指令执行）
- 每日总结的自动生成
- 管理员私聊（分析 → 群聊发布）

**交付物**：管理员可以在群聊中提供协调和分析能力。

### Phase 4：私聊体系完善

**目标**：群聊和私聊的完整体验。

**关键工作**：
- 私聊入口和界面
- 私聊与群聊的上下文隔离
- 私聊中的身份交互（与群聊一致但独立）
- 从私聊快速拉群（把当前对话升级为群聊）

**交付物**：用户可以在群聊和私聊之间自由切换。

### Phase 5：编排沉淀

**目标**：群聊中的成功协作模式可沉淀为持久工作流。

**关键工作**：
- 从群聊条件指令提取 Flow 编排图
- 从群聊消息流提取项目模板
- 群聊归档和回溯检索

**交付物**：群聊中跑通的协作可以固化为可复用的工作流。

## 15. 被纠正的设计误区

本节记录在设计讨论中被提出但最终被否定或大幅调整的设计方向，以及否定原因。

### 15.1 ~~管理员是持续运行的 agent runtime~~

**原始想法**：管理员是一个持续运行的 agent，有自己的会话和上下文窗口，像其他 agent 一样存在。群聊消息注入管理员的上下文。

**否定原因**：如果管理员是持续运行时，它的上下文窗口会满，必须压缩/摘要，导致信息丢失和信任问题。更深层的问题是，原始的工具调用和调试噪音混入上下文会导致模型角色认知漂移。

**替代方案**：管理员是群聊的功能层。不持续存在，按需激活。每次激活时从群聊中透明取用上下文子集，用完释放。

### 15.2 ~~所有 agent 的产出都通过 memory.md 压缩记忆~~

**原始想法**：会话超时或达到上下文上限时触发摘要，写入 memory 文件，下次会话加载。

**否定原因**：产生"悬崖效应"——消息 1-50 完整记得，第 51 条触发压缩后突然遗忘。用户无法预测何时遗忘、遗忘了什么。不可预测的遗忘比根本没有记忆更可怕。

**替代方案**：群聊消息流永久保存（存储层），管理员每次激活时选择性取用（消费层）。每日总结作为群聊内的特殊消息类型，事中沉淀而非事后压缩。

### 15.3 ~~Widget 仪表盘是独立的 surface~~

**原始想法**：一个独立的全局仪表盘页面，上面摆放各种来自不同工作空间的 widget。

**调整原因**：独立仪表盘和群聊是两个 surface，存在上下文切换问题。如果群聊是共同上下文，所有状态和进度本质上都在群聊内容里，看板只是另一种视角。

**替代方案**：看板融入群聊三层结构（态势层 / 消息流 / 侧边）。看板不是一个要去"看"的地方，而是你待着的地方本身就让你看得见。

### 15.4 ~~每个会话需要在群里拉一个"人"~~

**原始想法**：群成员列表中，每个编程小助手会话都是一个独立条目（"编程小助手·auth"、"编程小助手·payment"）。

**否定原因**：每新增一个会话就要"拉一个人进群"，太麻烦。

**替代方案**：群成员列表按身份维度组织（只有一个"编程小助手·主代理"）。会话选择通过 @mention 的二级交互完成（弹出选择器）。身份是一级选择，会话是二级选择。

### 15.5 ~~群聊输入是纯文本 string~~

**原始想法**：群聊输入框是一个 textarea，用户打一段纯文本，系统用 NLP 解析谁被 @mention、指令边界在哪、依赖关系是什么。

**否定原因**：NLP 解析不可靠。猜错了就路由到错误目标、遗漏依赖条件。

**替代方案**：输入框是结构化指令编辑器。每个 @身份 开启一个指令块，块与块之间有视觉分隔。同一批发送的块自动产生关联。系统不需要猜——用户在输入时就声明了结构。

### 15.6 ~~直接做自主多 agent 协作（orchestrator agent 自主拆解、分配、判定）~~

**原始想法**：放一个管理者 agent 自主拆解任务、分配工作给其他 agent、管理依赖、判定完成。

**否定原因**：当前模型能力不足。任务定义模糊、完成标准不可量化、错误会级联。结果是 agent 们忙得要死但产出不可信任——虚假快感。

**替代方案**：人是唯一的 orchestrator。系统的职责是降低人指挥的成本（态势感知、指令下达、上下文保持、干预纠正），不是替代人的判断。自主协作留待模型能力到位后，且会建立在人指挥的基础设施之上。

### 15.7 ~~会话选择器需要高度自定义~~

**原始想法**：不同工作空间的会话维度不同，需要给每个工作空间做高度自定义的会话选择器。

**调整原因**：一旦工作空间可以暴露多个身份（主代理、探索代理、审计员），身份本身已经做了区分。选择器的自定义灵活度不需要那么高——身份是一级选择，身份背后的会话绑定是工作空间自己的事。

**替代方案**：工作空间暴露多个身份。会话选择器只作为 @mention 的二级交互，且具体内容由工作空间按自身逻辑提供，但不需要复杂的自定义框架。

## 16. 开放问题

以下是设计讨论中识别出但尚未形成定论的问题，需要在后续设计阶段解决。

### 16.1 群的创建和管理 UX

建群、拉人、指定管理员这些操作，具体长什么样？是纯自然语言（"建一个群叫 xxx，拉 @主代理 @管理员 进来"），还是有轻量 UI 辅助（一个"新建群"按钮 + 身份选择器）？

**初步倾向**：UI 辅助为主，自然语言为辅。建群是一个低频但重要的操作，值得有专门的 UI 流程。

### 16.2 每日总结的生成时机和方式

每日总结是按固定时间生成（每天 23:00），还是按消息量触发（每 50 条消息）？由谁生成（管理员 agent 消耗 token，还是后台规则引擎不消耗 token）？

**初步倾向**：混合模式。按时间触发为主（每天一次），管理员 agent 生成。因为每日总结的质量直接影响管理员下次激活时的认知质量，值得消耗 token。

### 16.3 Widget 自定义 HTML 的安全边界

如果 widget 是工作空间层定义的自定义 HTML，怎么防止 XSS 或恶意操作？是否需要沙箱（iframe sandbox）？

**初步倾向**：本地部署阶段暂不需要沙箱。但如果未来开放远程访问或第三方工作空间，需要引入沙箱机制。

### 16.4 纯 UI 工作空间的实现形态

一个日程工作空间不运行 agent runtime，但需要 provider、widget 定义。是否需要引入新的 `kind: "workspace-only"` 类型？它如何与现有的 `kind: "agent"` 和 `kind: "workspace"` 共存？

### 16.5 群聊编排到 Flow 图的沉淀路径

管理员怎么从群聊对话中提取出结构化的 Flow 编排图？需要什么程度的 NLP 能力？这个功能的 ROI 如何？

**初步倾向**：Phase 5 再考虑。先把群聊本身做好。

### 16.6 CallArbiter 与群聊消息的关系

群聊中 @某身份 的指令最终要通过 CallArbiter 串行化执行。CallArbiter 保证 per-runtime 只有一个 onCall() 在跑。群聊场景下，用户可能想连续发多条消息给同一身份。dispatch queue 已经支持排队，但 UI 上需要显示"排队中"状态。

### 16.7 通知策略的精细化管理

不同身份在群聊中的通知行为（何时主动发言、何时保持安静）需要可配置。配置面板的具体形态和默认值需要设计。

### 16.8 跨群信息共享

不同的群聊之间是否需要信息共享？比如"探索调研"群产生的知识如何被"支付系统重构"群的管理员感知？群聊之间的信息流是否需要打通？

**初步倾向**：默认不打通。每个群是独立的上下文。如果需要跨群信息，用户可以手动复制或引用。保持群的边界清晰比跨群共享更重要。

### 16.9 管理员的多群上下文

一个管理员是否可以同时管理多个群？如果是，它在不同群的上下文是否独立？还是共享？

**初步倾向**：每个群的管理员上下文完全独立。管理员在不同群中表现为"不同的激活实例"，各自从各自的群聊取用上下文。

### 16.10 群聊的消息检索能力

群聊积累大量消息后，管理员需要能检索历史消息（"6月15号关于 API 设计的讨论"）。检索机制是基于关键词、基于语义、还是基于结构化标签？

**初步倾向**：先做关键词检索（简单可靠），后续考虑语义检索。每日总结本身就是一种结构化索引，可以作为检索的入口。

## 附录 B：术语表

| 术语 | 定义 |
|---|---|
| **群聊（Group Chat）** | 一组干话题相关且有边界事物的 agent 的共同上下文。产品的核心实体。 |
| **私聊（Private Chat）** | 用户与单个身份之间的一对一对话。上下文独立于群聊。 |
| **身份（Identity）** | 工作空间暴露的可 @mention 的实体。一个工作空间可暴露多个身份。 |
| **管理员（Admin）** | 群聊的功能层。按需激活，从群聊取用上下文做协调和分析。不是持续运行时。 |
| **限定符（Qualifier）** | @mention 中 `<...>` 内的会话/上下文标签。有无限定符决定路由确定性。 |
| **热窗口（Hot Window）** | 管理员工作上下文中的最近 N 条原文消息。 |
| **每日总结（Daily Summary）** | 群聊中的特殊消息类型，结构化的当日工作总结。 |
| **Provider** | 工作空间的操作声明，通过 CLI/MCP/HTTP 三种形态被消费。 |
| **上下文组装（Context Assembly）** | 管理员每次激活时从群聊中取用信息构建工作上下文的过程。 |
| **指令组合（Command Batch）** | 同一批发送的多个 @身份 指令块，自动产生关联关系。 |
| **态势层（Awareness Layer）** | 群聊顶部的常驻状态面板。 |
| **确定性路由（Deterministic Routing）** | 带@身份·子身份<限定符> 的指令直达目标，不经过管理员。 |
| **智能路由（Smart Routing）** | 裸 @身份 的指令经管理员解析后路由。 |
