# Coder 智能体调度

Coder 是可以独立调查、修改代码和运行验证的编码智能体。你负责交代任务、协调并行工作、检查结果；Coder 负责执行。

通过 `coder_shell` 创建工作线程并发送指令。同一项任务的追问、补充和返修沿用同一条线程，互不相关的任务分别创建线程。

## 委派一项任务

### 1. 明确要交给 Coder 做什么

发送前，先确定：

- **目标**：需要解决什么问题，交付什么结果。
- **目录和范围**：在哪个仓库工作，可以修改哪些部分，哪些部分不要动。
- **约束**：只读调查还是允许修改；是否允许提交、创建分支或使用 worktree。
- **验收要求**：需要运行什么验证，最终报告什么。
- **与其他工作的关系**：是否依赖前一项任务，是否会与其他正在进行的改动冲突。

有工单或方案文档时，提供路径和必要背景；没有时，直接在指令中写清楚，不必为了派发另建一套工单文档。

**相互独立、没有文件或构建产物冲突的任务可以并行。** 有交集的任务串行派发，前置任务未完成时不要让后续 Coder 开始修改，也不要让它定期查询前置任务是否完成。由你收到结果并验收后继续派发。

先查看目标仓库的分支和已有改动，避免把其他会话的工作当作本次任务的一部分。不要用 `reset --hard`、`clean` 或 `checkout -- .` 清理未知改动。

### 2. 创建线程

在 `coder_shell` 的 `command` 参数中执行：

```bash
new-session coder /home/dev/AgentDevClaw '修复工具进度显示'
```

将路径替换为本次任务的目标目录，必须是**已存在的绝对路径**；不要沿用上一项任务的目录。

返回内容包含：

```text
sessionId=...
threadId=...
```

后续使用 `threadId` 派发、查看和归档，通常不需要操作 `sessionId`。创建时会自动建立线程，无须再调用 `create`。

### 3. 发送任务

```bash
send wt-xxx progress-fix-001 '修复工具进度显示问题。目标、相关入口、允许修改范围和验收要求如下……'
```

第二个参数是本次指令的**幂等键**，用于避免同一指令因重试而重复执行：

- 一次新的任务指令使用一个新键。
- 不确定上一次是否提交成功时，保留原键，不要换键再发。
- 追加要求、要求返修或明确重新执行时，使用新键。

`send` 很快返回，**不用等 Coder 做完**。默认会自动跟踪这次任务，完成、失败或需要你处理时会通知你。

如果只想提交、不需要自动通知，使用：

```bash
send wt-xxx progress-fix-001 '任务指令' --dispatch-only
```

提交成功但通知跟踪未建立时，按回执中的 `commandId` 重新调用 `watch`，不要重复发送任务：

```bash
watch wt-xxx --command=cmd-xxx
```

### 4. 继续工作，或者等待通知

派发后可以继续处理其他事情。如果现在只想等待，执行：

```bash
watch wt-xxx
```

同时等待多项任务：

```bash
watch wt-aaa wt-bbb
```

`watch` 默认跟踪每条线程最近一次派发，不重放历次任务的报告；查看或恢复某次历史任务时使用 `--command=<commandId>`。返回后，本轮结束并等待通知；任务已经结束时，会直接返回结果。自然结束本轮也不会取消 Coder 的工作。

**不要用 `sleep` 加 `show/list/result` 循环查询进度。** 这些命令用于需要时查看信息，不用于定时轮询。

### 5. 检查结果，必要时继续追问

收到完成通知后，先看通知是否包含足够信息；需要完整报告时执行：

```bash
result wt-xxx
```

有多轮回复时，返回内容会附轮次索引，可以查看指定轮；同一轮有多条回复时，取该轮最后一条：

```bash
result wt-xxx --turn=2
```

根据任务要求核对实际文件、diff、测试和构建结果。Coder 说“完成”不是验收依据；通过项、失败项、未验证项应与实际证据一致。

结果需要修改时，向原线程发送明确的补充指令，使用新幂等键：

```bash
send wt-xxx progress-fix-002 '检查结果发现……请在原任务范围内修正，并补充……验证。'
```

### 6. 完成后归档

任务验收和必要的交付完成后，归档线程：

```bash
archive wt-xxx
```

未归档线程会占用工作空间的线程名额。不要为了等推送授权而保留已经完成的线程；归档不影响你之后推送代码。

**归档正在执行的线程会立即打断它。** 只归档自己负责且已经结束的线程，不要替其他会话清理线程，也不要用归档来结束自己的等待。

默认由你验收后处理提交、分支和推送，除非已明确授权 Coder 执行。推送必须有用户授权；用户没有要求提交时，不要因为技能写了收尾流程就自行提交。

## 怎样写好任务指令

### 调查、审查和探索

交代要回答的问题、调查范围、是否只读及输出要求，让 Coder 独立形成结论。

例如：

> 审查消息订阅模块在断线重连和会话切换时的正确性。只读，不修改文件。报告确认的问题、触发条件、代码依据和未能验证的部分。

如果目的是全面审查，不要把任务缩成只验证你已经想到的一个问题。若本来就是验证某个具体假设，则直接说明假设，并要求同时检查支持和反对它的证据。

### 修改和实现

交代目标、修改边界、必要背景及验收标准。需要协调多个 Coder 时，还要写清楚：

- 其他任务正在修改哪些部分。
- 本任务可以使用哪些文件和构建产物。
- 在当前目录直接工作，还是使用指定分支或 worktree。
- 是否允许 commit、push 或分支操作。
- 完成后希望留下怎样的工作区状态。

不要让 Coder 猜测这些安排。它不知道你同时派发了哪些任务，也不知道其他会话有哪些未完成改动。

指令中通常应包含：

- 任务目标；有工单时附工单号和路径。
- 目标仓库、工作目录和允许修改范围。
- 必要的前置结果、相关文档或提交。
- 验收命令或可判断完成的标准。
- 不覆盖其他会话改动的要求。
- 最终报告需要列出的结果、验证、未验证项和风险。

验证可以从定向检查开始，再按影响范围扩大到相关回归和全量测试，不必每次都先跑最重的构建。

## 批量派发与 Bash 写法

`coder_shell({ command })` 的 `command` 可以是一段 Bash 脚本，用变量、循环和条件组织调度命令。

它不是执行任意系统命令的终端。文件读写、代码搜索和 Git 操作仍使用对应工具或普通 Bash 工具，不要把 `git`、`curl`、`rm` 等命令放进 `coder_shell`。

### 按工单列表创建并派发

先确认这些工单互相独立、可以并行，并将目录和要求替换为本次任务的实际内容。工单编号用于生成各自的标题、幂等键和指令，共同要求只需写一次：

```bash
set -e
tickets=(123 456 789)
threads=()

for ticket in "${tickets[@]}"; do
  created=$(new-session coder /home/dev/AgentDevClaw "处理工单 #$ticket")
  thread=${created##*threadId=}
  if [[ "$thread" != wt-* ]]; then
    printf '工单 #%s 未取得线程 ID，请检查创建回执。\n' "$ticket"
    exit 1
  fi

  send "$thread" "ticket-$ticket-dispatch-001" \
    "请处理工单 #$ticket。先阅读对应工单全文，按工单要求完成修改和验证。
     仅修改该工单范围内的文件，不覆盖其他会话的改动。
     不提交、不推送；完成后报告修改内容、验证结果和未验证项。"
  threads+=("$thread")
done

watch "${threads[@]}"
```

`$()` 获取创建结果，参数展开提取线程 ID，随后直接用于派发，无须在两次工具调用之间手工复制。每次 `send` 提交后循环继续，**不会等前一个 Coder 做完再派发下一个**；`send` 后接 `&&` 也只判断提交是否成功。

末尾的 `watch` 表示派发完后等待通知；如果还有其他事情要做，可以省略。即使把 `watch` 写在循环内，也只会在整段脚本返回后进入等待，不会在循环中途暂停。

示例遇错即停，已完成的创建和派发不会撤销。检查逐条回执，保留工单与线程的对应关系，只补未完成的部分，不要从头重新创建整批线程。

需要“先完成 A，再执行 B”时，先派发 A，收到通知并验收后再派发 B。不要用查询循环等待 A。

### 批量保存报告，验收后归档

同样的语法也可用于读取结果和收尾。先保存已结束任务的报告：

```bash
set -e
for thread in wt-aaa wt-bbb; do
  result "$thread" > "report-$thread.txt"
done
```

文件保存在当前工具工作目录，不是自动写到 Coder 的项目目录。工具仍保留调度回执，重定向不保证报告内容不出现在工具返回中。

阅读报告并核对实际结果后，在另一次调用中归档已验收、由自己负责的线程：

```bash
set -e
for thread in wt-aaa wt-bbb; do
  archive "$thread"
done
```

### 支持的写法和限制

支持变量、数组、`for` / `while` / `until`、`if` / `case`、函数、算术、命令替换 `$()`、管道、`;`、换行、`&&` / `||`、重定向和 heredoc。

可用辅助命令：

- 输出和判断：`echo`、`printf`、`true`、`false`、`test`、`[`，以及 `[[ … ]]` 条件表达式。
- 变量和流程控制：`read`、`set`、`break`、`continue`、`local`、`declare`、`typeset`、`export`、`readonly`、`unset`、`return`、`shift`、`exit`、`:`。

不支持 `eval`、`source`、`exec`、变量生成命令名、进程替换或后台 `&`。算术表达式和数组下标内不能使用命令替换；需要时先用普通赋值保存结果。

使用时注意：

- `;` 前一项失败后仍会继续；`&&` / `||` 和 `if` 按当前命令的退出状态决定下一步。需要遇错停止时使用 `set -e`。
- 脚本最后成功，不代表前面每一条都成功；工具会保留逐条调度回执，应检查其中的失败。
- 整段脚本会先检查命令和可直接确定的参数；包含变量的参数在展开后再次检查。因此，后面一项报错时，前面已完成的创建或派发不会撤销。
- 变量只在本次工具调用内有效，不会保留到下一次调用或收到通知之后。
- 每次调用最多执行 10,000 次循环、20,000 次命令；达到工具超时或被用户打断时，停止后续命令，已派发的 Coder 不会因此取消。
- 重定向仅允许工作目录内的相对文件路径，不允许 `..`、绝对路径或符号链接。捕获或重定向命令输出，不会隐藏工具保留的调度回执。
- 长指令应正确引用，避免其中的引号、`$` 等字符被当作脚本执行。可以先用文件工具准备内容，再读入并作为参数传递；不要把任务文本当成脚本拼接执行。

## 命令速查

以下命令均放在 `coder_shell` 的 `command` 中。带值的选项使用 `--选项=值`，可放在参数任意位置。执行 `help` 可查看用法。

| 命令 | 用途 |
|---|---|
| `new-session coder <绝对目录> ['标题']` | 创建 Coder 会话和线程，返回 `sessionId`、`threadId` |
| `create coder <sessionId> ['标题']` | 给已存在但尚无线程的 Coder 会话建立线程 |
| `send <threadId> <幂等键> '<指令>' [--dispatch-only]` | 发送指令，默认自动跟踪并通知 |
| `watch <threadId> [threadId...] [--command=<commandId>]` | 查看或建立跟踪，并在本次工具返回后等待通知；已结束则直接返回结果 |
| `result <threadId> [--turn=N]` | 获取最后一轮或指定轮的完整回复 |
| `list [agentId] [选项]` | 查找线程 |
| `show <threadId>` | 查看线程详情、待发送指令数量和最近事件 |
| `deliver <threadId>` | 再次尝试投递线程中尚未送达的指令，不另建一条指令 |
| `archive <threadId>` | 归档线程；正在执行时会被打断 |
| `unarchive <threadId>` | 取消归档；之后发送指令才会重新开始工作 |

`new-session` 和 `create` 的第一个参数固定为 `coder`。通常只需 `new-session`；仅在已有会话确实缺少线程，或创建回执提示需要补建时使用 `create`，不能给不存在的会话建立线程。

`advance`、`resume` 不可用，不要用它们尝试恢复失败的线程。

### 查找线程

`list` 默认返回最近活动的 10 条未归档、未关闭线程。查历史时加 `--all`，取消条数限制用 `-n=0`。

```bash
list coder
list --dir=/home/dev/AgentDevClaw
list --title=工具进度
list --status=executing,pending-commands
list --failed
list --all -n=50
list --all -n=0
```

选项可以组合：

```bash
list --dir=/home/dev/AgentDevClaw --status=executing
```

- `--dir` 包含该目录及子目录，路径分隔符和大小写会统一处理。
- `--title` 按标题关键字检索。
- `--status` 可同时指定多个状态。
- `--failed` 查找标记为失败的线程。
- 返回内容包含线程 ID、状态、标题、目录、待发送指令数量和时间信息；有未显示的线程时会附提示。

默认列表有条数限制，不能仅凭默认返回的条数推算剩余名额。需要完整核对时使用 `-n=0`。创建因名额已满被拒绝时，先归档自己已经完成的线程，或请用户调整上限；不要归档别人的线程腾位置。

## 遇到问题时

先区分：**任务没有提交成功、任务执行出问题、还是自动通知中断了。** 三者处理不同，不要一遇到超时就重新派发。

### 不确定指令是否提交成功

提交请求超时或连接中断，不表示任务已取消。

先查看回执、线程详情和已有指令，确认是否已接收。确需重试时，使用原线程、原幂等键和原指令，不换新键。

同键重试的处理方式：

| 情况 | 结果与下一步 |
|---|---|
| 尚未接收过这个键 | 接收指令，正常开始处理 |
| 已接收，仍待发送给 Coder | 不再添加相同指令；可用 `deliver` 再次尝试发送 |
| 已经执行过 | 不会再次执行；查看结果 |
| 需要追加、修正或重新执行 | 使用新键发送新指令 |

不要通过故意重复发送任务来测试去重。

### 已接收，但没有开始执行

用 `show` 查看线程状态和待发送指令。回执中的 `delivered=0` 表示当时没有完成投递，不等于指令丢失。

需要再次尝试投递时执行：

```bash
deliver wt-xxx
```

这会尝试启动该线程的 Coder 并发送尚未送达的指令，无须另发一份任务。

- 返回 `handoff_in_progress`：正在自动接续，等待即可。
- 返回 `runtime_ready_timeout`：Coder 未能及时启动，检查启动报错，解决原因后再投递或用原键重试。
- 返回 `head_session_missing`：线程对应的会话已不存在，需要先核对并处理遗留指令，再归档旧线程、重新创建任务；不要在无法确认旧任务状态时直接复制派发。
- 返回 `succession_precondition_violated`：先确认该条是否是系统用于接续的指令。它被作废不表示你的任务指令丢失，不要因此重发原任务。

`delivered=1` 只说明指令已送达。没有立即看到文件变化时，Coder 可能还在阅读、调查或验证，不要直接认定没有开工。

### 自动通知中断

出现 `monitor_unreachable`、`runtime_unavailable`、`association_lost`，或者主会话接续、重启后提示未恢复跟踪时：

1. 用 `show` 查询任务当前情况。
2. 必要时用 `result` 获取错过的结果。
3. 重新 `watch`；有 `commandId` 时明确指定。

这只是在恢复跟踪，**不要重新发送任务**。已有通知始终发给原会话，不会因为你切换界面而改投到其他会话。

右侧后台面板可以查看任务状态。关闭面板不会停止跟踪；卡片状态也不能代替结果验收。

### Coder 长时间没有新消息

长工具调用期间可能没有新事件。需要调查时，结合 `show`、最新日志和目标仓库的变化判断，不要只看一段旧日志或文件是否变化。

如果环境提供 Debugger 工具，可以查看最近的执行步骤、工具错误和超时信息。不要假定一定有该工具。

确认仍在正常执行时继续等待；确认失败后，先处理尚未送达的指令，再决定是否发送修正要求。新的修正指令应说明要改变的做法，而不是重复要求运行上次失败的无界命令。

不要为了让状态恢复正常而直接杀进程、重启整个服务或删除状态文件。

### Coder 自动接续

Coder 工作较长时可能自动换一个会话继续原任务。**继续使用原 `threadId` 即可，正常情况下不需要你操作，也不需要重发指令。**

只有出现明确失败，或有证据表明任务上下文丢失、重复修改、执行不再推进时才调查。`show` 中的 `head` 变化和 `handoff_*` 事件可用于确认是否发生了接续。

出现 `status=rotation_failed`、`failed=true` 且事件显示接续失败时，报告阻塞并请求恢复处理，不要重发任务，也不要尝试不存在的 `advance/resume` 命令。

### 工作区出现意外变化

先查看 diff、最近提交和其他正在执行的任务，确认归属：

- 出现额外修改：可能来自其他会话，不要清理或顺手提交。
- 工作区突然干净：可能已经有人提交，先检查 `git log`，不要直接认定修改丢失。
- 确认属于本任务但超出约定：检查必要性，再决定保留、要求修正或单独验收。
- 属于其他会话：保持原样，只处理已确认归属的文件。

测试失败时，区分本任务引入的问题、已有失败和环境问题，分别报告，不把“不是本次引入”写成“测试通过”。

### 线程被归档、关闭或删除

`thread_archived`、`thread_closed`、`thread_deleted` 表示线程已经结束或不再可用，**不表示任务已成功完成**。先检查已经留下的结果，再决定后续工作。

误归档时可用 `unarchive` 恢复；恢复不会自动继续执行，核对被打断的工作后再发送明确指令。已经了结的任务有新需求时，创建新线程。

## 验收与交付

按任务性质检查，不要求每次机械执行全部检查项：

- 实际结果是否满足目标，修改是否在约定范围内。
- 涉及迁移或替换时，旧实现、引用和加载关系是否处理完整。
- 测试、静态检查和构建是否真实执行，结果是否与报告一致。
- 是否需要更新构建产物、重启或补在线验证。
- `git diff --check` 是否通过，无关文件是否被混入。
- 调查任务的结论是否有证据，未知和未验证部分是否说清楚。

需要提交时，按已验收的任务或板块组织提交，不混入其他会话的修改。提交后检查 Git 状态和实际提交内容。推送另按用户授权执行。

对用户报告当前结果和下一步即可，不必每次输出线程内部状态。任务被阻塞时说明阻塞原因和需要的处理；最终交付说明：

- 完成了什么。
- 验证结果，包括失败和未验证项。
- 剩余风险或仍需执行的重启、补测。
- 提交信息（如有）。
- 线程是否已归档；仍保留时说明实际原因。
