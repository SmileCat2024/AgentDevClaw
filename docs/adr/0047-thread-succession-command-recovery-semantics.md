# ADR 0047: 线程接续的指令恢复语义

日期：2026-11-11
状态：已接受（阶段 1-5 已实施：消费判定闸与原子换头（`commitSessionSuccession`）、Viewer 持久接收队列与两层去重、claim/ack 确认协议与 fencing 身份链、入口旁路收口（HTTP / CLI / ACP 契约）、真实宿主往返验收与两仓库全量回归；各阶段实施记录见「实施顺序与范围」内标注，遗留边界在各阶段「已知边界」中显式记录）

## 背景与问题

线程接续（换棒）时，上一棒的 Inbox 指令需要判定"哪些该转交新 head"。两天内两个方向相反的生产修复：

- de4d5d03（11-05，修丢）：`delivered` 是终态且只表示"已交给 runtime"，接续发生在轮次产出终态事件前，指令永久滞留。修复引入 `requeueUnfinishedCommands`——换 head 前回收"已投递但事件流里没有 turn.completed"的指令。
- 9e71b99a（11-06，修重）："没有 completed"不等于"没有消费"。改为：该棒任一 turn 事件的 `sourceRef` / `consumedSourceRefs` 出现指令的 commandId 即视为已消费，不重放。

代码中可直接观察到根因：接续回收用 WorkThread Inbox 的 `delivered` 状态与独立 Board 的轮次事件共同判断输入是否消费；但 `delivered` 只表示 Viewer user-turn 请求被接受，事件上报是 best-effort、Board 只保留有界窗口，且退役 head 的迟到事件可能不被记录。于是没有消费引用有两种解释：输入未进入旧 runtime，或消费事实未被留存。de4d5d03 与 9e71b99a 分别暴露了把缺少完成事件解释为未完成、以及已消费引用用于防止重放的取舍；当前实现仍不能从不完整事件流证明输入未消费。

## 决策

### 1. 两层承诺——确认框架立场，不推翻

框架 Inbox 明确不承诺 LLM 副作用 exactly-once；命令身份持久化、幂等入队和可追踪投递状态，与 successor 核对现实的恢复策略分别处理不同层次的问题。Claw 采纳这一边界，同时要求接续回收不得超出现有证据作出消费判定：

- **命令接收层**：稳定 commandId / 幂等键和持久 Inbox 防止重复入箱；这是记录命令意图，不证明 runtime 已接收或执行。
- **runtime 投递与消费层**：可恢复投递和消费确认是两个独立保证。HTTP 接受只代表投递端接受请求；消费回执要有可恢复、去重且与接续可排序的持久协议。未建立该协议前，不把 `delivered` 或事件缺失解释为消费/未消费结论。
- **业务执行层**：不承诺 LLM 副作用 exactly-once。turn.completed 只代表轮次结束，不代表指令意图达成；副作用可能发生在轮次中途。消费或业务结果不确定时，由 successor 核对现实后决定继续、补做或报告无法核实。

### 2. 回收判定：只认正向消费证据，不从事件缺席推断未消费

接续时对每条退役 head 上 `delivered` 的普通指令作三分判定：

1. **已消费**：可靠关联的执行事实明确包含该 `commandId`（`sourceRef` 或 `consumedSourceRefs`）→ 不作为新输入重放。轮次完成、失败、取消本身都不是消费证明；消费引用才是。
2. **可证明未消费**：只有存在独立于 best-effort 事件窗口的权威证据，证明该命令从未进入旧 runtime 的输入队列/会话上下文，才可作为原指令重投。当前 board 事件中“没找到引用”，无论窗口为空、非空或水位看似未满，都不构成该证明。
3. **无法判定**：凡已 delivered 而没有可验证的消费证明、也没有权威未消费证明的命令，一律显式待核对；包括 board 读取失败、无事件、部分事件、裁剪、上报失败、迟到事件拒收、runtime/服务崩溃及任何来源不完整的情况。不得自动原样重放，也不得当作已完成或静默遗忘。

因此当前 board 事件只能提供“看见消费”的正向线索，不能为“没有消费”提供完备性证明。除非另有可靠完整性契约，9e71b99a 的正向识别仍可用于防重，但其反面不能推出可重投。事件窗口水位或事件条数不能证明某个 commandId 的事件没有丢失。

待核对必须是线程持久数据中的一等事实，含稳定 commandId、原指令内容/必要元数据、来源 head、判定原因与处置状态；不得只写入 `lastReason`（该字段是单一原因槽，不提供可查询待办集合或生命周期），也不得依赖临时内存、被裁剪的 board 或默认会播种的恢复指令。尚未完成消费分类的 `delivered` 命令与 unresolved 记录同受保护：在明确结清前不得被 Inbox 的终态裁剪删除；当前 `pruneCommands` 的 200 条上限不得丢弃它们。

新 head 的恢复不得依赖模型主动调用查询工具。自动接续提交时，未决清单必须作为持久化 successor 输入原子附带或以等价机制强制进入后继首轮上下文；手动免播 R3 时不得擅自启动模型轮次，但未决项必须在用户/调度方可见的线程状态和 API 中明确呈现，并可继续追踪。每项处置须通过有 commandId 的明确结果写回线程记录；新 head 查询能力是补充，不是唯一发现路径。待核对项只有在明确处置并持久化后才能结清，线程归档、重启、再次接续或通知失败不得使其消失。

这实现的是**不确定性不丢失、避免盲目重放**，不是业务副作用“不丢不重”：successor 可能无法核实外部现实，或核实本身不完整；该限制必须向调度方显式呈现，不能把模型核对当作形式保证。

### 3. 状态归属与事务边界

- **框架负责权威数据与原子状态转移。** Inbox 命令、head、接续挡板和命令投递状态都由 WorkThread 持久化；凡需要跨重启保留、参与重试/归档/接续并能被调度方查询的恢复事实，必须由同一权威模型持有。当前 Claw 先将命令改回 `pending`、再调用 `advanceHead` 是两个独立写入；补偿回滚不能消除崩溃窗口，不能作为最终正确性方案。框架应提供单一事务操作，在验证 expected head / revision、更新命令恢复判定、推进 head、清挡板时原子提交；任一步失败则整个状态不变。具体字段与迁移在实施设计中确定，不直接依赖 Claw 对 `core.store` 的内部写入。
- **应用层负责恢复策略与外部现实核验。** Claw 选择哪些输入需要 successor 核对、组织面向 Coder/其他宿主的处置流程，并将 unresolved 状态呈现给调度方；不在 Claw 另建与 Inbox 竞争的权威 ledger。框架提供持久、可寻址的 unresolved 命令事实及原始内容/来源；现有 `continuationPolicy` 只在 begin 时构造播种文本，不能假定它能读取之后才产生的不确定项。自动接续须在提交时把未决清单持久附加到 successor 首轮输入或提供不依赖模型选择的等价强制注入；手动免播接续则不得自动启动首轮，但须在 API/UI 状态上明确标记待核对并持续可见。恢复读取工具不能作为唯一发现通道。
- **事件证据只允许单向裁决。** 有可靠命令身份关联的消费记录可证明已消费；board 缺失事件不能证明未消费。只有将来存在带完整性保证的接收/消费确认协议，才可把其正向确认作为更强证据。当前 board 的水位、条数和“同一棒有其他事件”均不提供这种完整性保证。退役 Session transcript 的证据能力已核实（2026-11-11）：`Message` 仅有 `source`/`tag` 身份槽、无 sourceRef 字段；消费主路径（`agent.ts` 的 `addUserMessage` 调用点）与 busy 注入路径落用户消息时均不携带 commandId；真实 coder 会话快照全部消息零 sourceRef，全文唯一出现点是 `runtime.lastCallOutcome.sourceRef`（单槽、仅最后一轮存活）。因此 transcript 当前不构成正向消费证据，「transcript 缺少引用」永远不能推出未消费。若阶段 3 选择把「已进入执行上下文」确认落在消息持久化上（消费时将 commandId 盖入消息并随快照落盘），可作为确认协议的候选载体，但属新增契约，不是既有事实。
- **接续副作用必须可重试。** 投递、恢复指令构造及通知均可能在事务提交后失败；应由持久状态和幂等操作使服务重启/重复触发收敛，而不是用跨文件补偿伪造原子性。

### 4. 旁路收口

任何能向线程成员会话直投、推进 head 或唤醒旧 runtime 的生产入口，都必须服从线程 Inbox、head 与归档/挡板门禁；管理入口不得静默绕过接续事务。当前 input-gateway 对能解析到线程宿主且匹配当前 head 的输入已有服务端路由到 Inbox 的防线；这不覆盖直接调用底层 `submitUserTurn`、目标解析失败或其他会话寻址入口。实施前按实际目标解析方式逐项盘点并给出拒绝、迁移或保留理由：

- `POST /protoclaw/threads/:threadId/head` 原直接调用 `core.advanceHead`，绕过 successor READY 门、命令恢复判定及接续事件发布。阶段 1 已前置消费判定闸（与接续编排共用 `createRetiredCommandGate` 权威实现，判定不过返回 409 稳定 code，head 不动）；successor READY 门、原子事务编排与接续事件发布已由阶段 4 折入完整编排（见「实施顺序与范围」阶段 4 记录），并发 CAS 契约保持。
- 前端 `getActiveThreadInputTarget` 校验失败会回到当前视图常规 user-turn 路径。线程宿主会话不得因此直投旧 Session；服务端须依据目标 session 的线程归属强制走 Inbox 或明确拒绝，不把一致性保障寄托于前端状态。
- Remote Claw embedded-connector 当前按映射的 `localSessionId` 激活/启动该会话 runtime 后直调 `submitUserTurn`，不解析线程 head。应在投递前解析线程归属：线程成员输入转为 threadId 寻址并经 Inbox；历史 head、归档线程和接续挡板按同一门禁拒绝或排队，不得复活旧 head。
- IM 门户自身路径使用 CallArbiter；qqbot 声明 `threadHost: true`。需区分门户自有会话与外部 WorkThread：自有路径保留其门户串行语义，外部线程目标须经 Inbox；不得把 `threadHost` 声明误解为每个内部 Call 都应重新入同一线程。
- work-group、memo、后台通知、ACP、CLI 及 runtime restart-resume 的路径需逐项核实是否寻址线程、是否属于用户命令或内部唤醒、是否可触达退役 head，并为每类定义不变量和负向测试。未完成盘点前不得宣称线程输入入口已封闭。

### 5. 正确性所需的投递/消费协议

当前 `delivered` 只记录 Viewer user-turn 请求被接受，没有与 WorkThread 命令状态原子关联的持久消费回执。框架 Bridge 未把幂等键传到 Viewer；Viewer 的 `sourceRef` 目前是关联元数据而非去重键，排队输入保存在进程内 session 状态。因而“Viewer 接受、WorkThread 标记 delivered”之间的崩溃会使重试缺少接收端去重保护；Viewer 重启也可能丢失已接受但尚未消费的排队输入。不能仅在 Claw 回收函数内增补规则解决这些问题；框架协议设计与必要实现属于本决策实施范围。

协议至少要区分并持久表达：

- **已提交**：WorkThread Inbox 持有稳定 commandId 和完整命令载荷；提交幂等。
- **runtime 已接收待处理**：接收端以 commandId 去重，并在确认前持久接管输入；确认丢失后重试同一 ID 不会重复入队。当前 Viewer 的内存队列尚不满足持久接管。
- **已进入执行上下文**：runtime 对命令给出可关联的消费确认，含 head/session 身份；该确认区别于轮次终态与业务完成。
- **尚未接收或待恢复**：有权威协议证据证明 runtime 未接收，或已接收但仍在持久待处理队列且可安全转交，才允许重新调度；无法证明时进入持久 unresolved，不原样重放。

投递确认需有持久 outbox/重试、接收端幂等、确认去重与乱序处理，并与 head generation / 接续提交建立 fencing 和线性化顺序，防止迟到旧 head 请求或回执污染新 head。服务崩溃发生在任何确认边界时，恢复都必须从持久状态收敛。该协议保证命令的接收/调度事实可追踪，不承诺模型意图完成或外部副作用 exactly-once。

具体框架 API、存储 schema、旧记录迁移和外部调用方兼容策略由实施设计细化；实施设计不得降低以上语义。当前没有确认协议前，任何未被可靠消费确认覆盖的 `delivered` 命令都必须保留为 unresolved，不能声称系统已达到自动不丢不重。

## 实施顺序与范围

阶段按降低风险与尽早建立可见性的价值排序；协议建设与待核对落地并非严格串行依赖。未有完整消费确认协议时，先将无法证明的命令持久保留为待核对是安全的保守行为。

1. **实施前止静默**：Board 读取失败或必要恢复状态不可读取时，接续不得当作“没有待恢复命令”继续推进；明确返回可重试失败并保留旧 head 权威。此处选择暂时牺牲换头可用性，避免在无法读取恢复依据时静默遗忘或可能重放；不能把瞬时读失败伪装成命令已消费/未消费，也不能只写 best-effort 告警后继续。对持久损坏的 Board，须提供运维可执行的隔离/重建流程；重建导致证据缺失时相关命令统一标为 unresolved 后再允许接续，不能永久卡死或静默跳过。**已实施（Claw 侧消费判定闸，边界按「待判定集合」条件化）**：权威实现为 `createRetiredCommandGate` 工厂，`applySessionSuccession` 提交点与 `POST /threads/:threadId/head` 端点共用（端点不再旁路判定，409 稳定 code）。判定顺序：先计算退役棒窗口内 delivered 且非接续的待判定集合——集合为空则无需证据、放行（board 装配或文件缺失都不阻断：board 文件惰性创建，缺失是普通线程的合法态）；集合非空时证据成为必要，逐条要求可靠消费引用，全部可判定才放行，否则抛稳定 code（status 409）交失败链路收敛 `rotation_failed`、清挡板、旧 head 保持权威，证据补齐后重走 begin→apply 可恢复。三类失败 code：`getState` 抛错或 board 装配缺失 → `board_state_unreadable`；board 无状态（框架 `board.getState` 把「文件存在但解析失败」与「无文件」一律吞成 null）或保留窗口里看不到退役棒的任何事件（整棒被裁剪 / 上报失败）→ `recovery_evidence_incomplete`；窗口可见但存在缺消费引用的指令 → `recovery_evidence_ambiguous`（决策 2 的阶段 1 落地：缺引用不构成未消费证明，不得自动重放——原「无引用即重投」的过渡行为已移除，de4d5d03 的重投场景由阶段 2 的 unresolved 处置承接，在此之前一律失败收敛而非重放或滞留）。负向测试覆盖三类 code、board 装配缺失且无待判定指令的放行、端点级 409 拦截与放行；变异证据：改回静默跳过则失败收敛用例失败、改成无条件拦截则六个依赖无待判定路径的用例失败、移除缺引用拦截则判定闸用例失败。**阶段 2b 已整体退役该判定闸**：缺引用 / 证据缺失不再失败收敛阻塞换头，改由框架原子事务转 unresolved 持久承接（`commitSessionSuccession`）；瞬时读取失败（unreadable）仍保留「拒绝换头、可重试、旧 head 权威」语义（code `evidence_unreadable`）。`board.getState` 的类型化完整性信号（区分损坏与不存在）与隔离/重建流程已在阶段 2a 落地（`readStateDetailed` 三态 + `quarantineBoard`）。

网关三处均不对账（已核实），恢复路径是接续换头的消费分类转 unresolved；已知缺口：滞留水位告警只盯 pending，delivered 滞留无告警面（后续项）。(2) 真实宿主往返验收（`test/thread-succession-roundtrip.mjs`，隔离实例 + 真 server.js + 黑洞模型端点，不进默认套件）——锚点先于 spawn 的身份对齐、忙时排队、换头分类（已消费 / 转 unresolved）、successor 身份采纳、重启持久、归档收尾（inflight drain）10 步全过。联测抓到 4 个真实缺陷并已修：BasicAgent 构造器白名单丢弃 `runtimeInputIdentity`（身份从未离开 runtime，见决策 3）、UDS 注册字段名错配（`sessionId` vs 契约 `workSessionId`）、successor 身份时序缺口（采纳通道）、测试自身双线程误建（fencing 正确拒绝）。(3) 阶段 5 独立 Coder 审查（两仓库真实 dist wire 闭环探针）发现 10 项缺陷，全部修复并配回归测试（关键项经变异验证）：**P0-1** bridge 对机器通报（reminder / system_continuation）附加 commandIdentity 被 Viewer 契约拒收（invalid_input 不可重试 → 通知指令标 failed，自动接续的恢复指令与 unresolved 清单到不了新 head）——改为仅用户意图类（user_message / external）携带 fencing 身份；**P0-2** 宿主 spawn 身份与框架 wire 派生双口径（legacy 多棒线程派生 N vs 宿主自写 `|| 1`，指令被 fencing 永久拒收）——宿主统一经 `thread-integration.resolveHeadGeneration` 透传框架派生，不自写 fallback；**P1-3** Viewer `handleRequestInput` 队首转交会把带身份命令直答活动租约（绕过 claim/ack：无持久 lease、无身份校验、无回执盖戳）——带 commandIdentity 的队首项不转交，留给 claim 路径；**P1-4/P1-5** 手动换头端点事件形状修正（`thread.head-advanced` 携 kind/agentId/fromSessionId/toSessionId/reason，前端 thread-store 要求 from/to 同场）＋退役旧 head runtime（`stopManagedAgent`，先于补投递，对齐自动接力语义——旧 runtime 滞留会以自洽身份继续 claim 队列、事后执行已分类 unresolved 的指令）；**P2-6** ack 幂等（ack 成功写持久消费集，重复 ack 命中幂等成功而非 409；已消费重投提交面命中 `delivery: 'consumed'` 不重新入队）；**P2-7** delivered 缺 deliveredAt 语义从「窗口外静默跳过 / 可裁」改为「无法归属」——分类层转 unresolved（稳定 code `unattributable`）、`pruneCommands` 保守豁免（恢复依据不可逆丢失）；此语义修正同步更新了 3 处沿用旧假设的存量用例（框架 workthread-core、Claw 复刻用例、thread-lifecycle-e2e ## 后果与正确性边界

- 该决策要求不完整的 board 观察不得作为未消费证明，并规定待核对事实可恢复、可发现、可处置；自动投递正确性须由持久确认协议与原子接续实现，successor 核对不构成外部副作用 exactly-once 保证。
- 故障语义需区分：接续事务失败时 head 与命令状态保持原样；事务成功后投递/通知失败时，持久待办仍可由后续触发点重试；尚未核实的消费状态不得被标为已完成或删除。若现实无法核实，需保留 unresolved 并返回可见的阻塞/人工介入结果。未结清记录不得因时间或容量策略自动过期；记录容量治理只能作用于已明确结清的历史，并保留必要审计引用。达到自动恢复承诺的前提，是持久确认协议与原子换头均已实施并通过崩溃/并发验收；此前只承诺显式保留不确定性，不宣称自动不丢不重。
- 兼容边界：保留现有 commandId、幂等入箱、`pending`/`delivered`/`failed`/`cancelled` 对旧调用方的可见语义；`delivered` 仍是“投递端接受”的历史状态，不提升为执行确认。新增待核对状态不得让旧消费者把它误当 pending 自动重放；未分类 delivered 与 unresolved 均不得被终态裁剪删除，状态更新也不得抹去首次投递的审计事实。字段迁移、旧记录默认解释及 API/UI 投影必须在实施设计中锁定。
- 责任分层：框架持有 Inbox 与 head/挡板的原子状态事实及可寻址待办；Claw 持有宿主策略、现实核验流程和调度方呈现。若实现证明现有框架写入面无法保证这些原子不变量，应扩展框架契约，而非在 Claw 直接改内部 store 或另建第二真相。
- 验收必须覆盖事故回归（de4d5d03、9e71b99a）、正向消费证据/缺失证据边界、接收与标记间崩溃后重试不重复入队、Viewer 重启后的排队恢复、board 查询失败不得推进 head、持久损坏 Board 的重建与 unresolved 收敛、部分裁剪、事务崩溃注入、重复接续/重启/重复通知、自动首轮强制携带 unresolved、手动免播时调度方可见且不自动启动轮次、归档与 >200 条终态裁剪、旧投递审计留存、无接续运行期 runtime 失联、旧 API 消费者及真实宿主调度反馈。每个生产旁路均须有负向测试证明不能绕过 Inbox/head/归档门禁；HTTP、ACP、CLI 的 unresolved 结果必须有契约测试。测试需证明旧路径在目标语义下仍成立，并对移除任一正确性约束的变异明确失败。
