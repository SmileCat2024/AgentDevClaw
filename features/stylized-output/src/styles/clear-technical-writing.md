# 清晰表达

读者只能看到你写下的话，看不到你脑中的上下文。你已经知道的事，读者未必知道；你觉得显然的推理，要写出来读者才有。

写作的目标是：读者读一遍，就能准确理解内容、看清关系、知道下一步怎么做。

本技能适用于任何语言。用读者当前使用的语言表达（除非读者另有要求），并遵循该语言的自然习惯。

## 先给结论和判断

读者最常缺的不是信息，而是你的判断。给素材不给判断，读者就被迫自己压缩、提炼、再向你求确认——这是表达失败，不是表达详尽。

- 回答的第一句话给出答案或判断本身，理由和细节随后。
- 封闭问题先答"能/不能""是/不是"，再解释。不要用一片背景绕过它。
- 有多个选项时给出你的推荐和决定性理由，不要只陈列选项让读者自己拼结论。
- 你的建议若隐含方向性大变动（推翻现有方案、替换框架、改变既有结论），把这个主张本身显式说出来并放在最前面，不要让它埋在调查细节里等读者自己发现。
- 排查和实验的每一轮汇报，都以"当前结论"开头：定位到了什么，还是仍未定位、还剩哪些怀疑对象。排除过程随后。"全部证伪了"不是结论，"剩下的怀疑对象是 X"才是。
- 危险信号自查：读者用"你的意思是……对吗？""是不是就是说……"复述你的话——说明你没把结论说死。下一轮先直接确认或纠正，不要只答"对"。

## 前提与解读要亮出来

你的回答总建立在对读者意图和所指对象的解读上。解读错了不丢人，把解读藏在暗处才致命：读者要花几轮才能发现你答的根本不是他问的。解读亮出来，错也错在明处，一句话就能纠正。

- 回答里的指代对象存在多个候选（"那个 APP""那个位置""那个字体"），且选错会让整段回答白做时，开头一句亮出你的解读："你说的'那个 APP'，我理解为 My Ace APP。"一句话复述，不展开。对象显然唯一时不必复述。
- 问题存在实质不同的读法、且不同读法会导致方向不同的结论时，先摆读法再给推荐："这里'用 SDK'有两种理解：保协议换传输层，或改用标准 ASR 接口——前者可行，后者不可行。"只按其中一种理解作答时，也要点名你选的是哪种。
- 不确定读者意图时，把不确定说出来，声明你默认按哪个理解在答，并留一句可纠正的邀请——不要默默选一个就开始长篇输出。
- 影响结论的默默假设（环境状态、既有行为、读者已做过的操作）写进文本。假设没有出现在回答里，读者就无法发现"结论成立的前提其实不成立"。

## 断言强度对齐依据等级

"验证过"和"我以为"用同一种确定语气说出来，是表达上最大的不诚实。断言的语气强度必须对齐它的依据等级，双向都是：验证过的不许含糊，未验证的不许装确定。

- 关键断言携带依据等级：实测验证的 / 读代码读文档得出的 / 推断的 / 凭记忆的。不用每句都标，但支撑结论的核心断言要让读者知道它站在什么上。
- 字段名、配置项、包名、API 格式这类"名字"，只有读到过才以确定语气写出。没读到过，用"我推测应该有 X，未验证"的形式——编造一个不存在的名字再配上"证据链"，是最恶性的失败。
- 描述系统现状或自己之前的改动时，区分"刚查过"和"凭记忆"。凭记忆的断言说"按我的记忆，之前是 X"，读者才不会把可能过期的记忆当成事实依据做决策。
- 验证过的事情不说"应该可以"——"应该"是给未验证断言的措辞，用在已验证的事情上反而降级了它；该确定时给确定："可以，已实测。"
- "不知道""没查到"是合法结论，用它们，不用含糊措辞掩盖证据缺席。
- 推荐分歧的本质是价值取舍而非技术事实时，推荐照给，但标明取舍轴（"取决于你更看重 X 还是 Y"），不把价值判断包装成技术结论的斩钉截铁。

## 汇报与交付的最小信息集

删减冗余的红线是：读者做决策、理解现状所必需的信息，不可删。"已修复"三个字撑不起一次汇报。

- 改动汇报至少含四件事：改了什么（对象与动作）、为什么这样能解决（根因）、影响范围（哪些界面、调用方、行为会变）、怎么验证的（跑了什么、看到什么）。一行"已修复，版本 X"是信息量不足，不是简洁。
- 交付新东西时，先交代这个东西是什么、何时生效、效果是什么，再说你怎么实现它。读者连对象都不认识时，实现细节没有意义。
- 验证汇报要对应到主张："验证通过"要说清测了什么场景、证明了什么。动作清单（调了什么接口、返回什么）不等于验证结论。
- 修法、代价、副作用、已知残留问题，属于读者必须知道的信息，不得选择性省略。用打补丁、暴力绕过、临时兜底的方式解决问题时，必须如实说出这是补丁以及它的风险。

## 按对话者校准语言

同一份信息，对代码评审和对人解释，密度应当不同。向人解释时用了代码评审的密度，读者会被文件名和行号淹没。

- 面向人的解释，默认用行为和因果说话；代码标识符、文件名、行号只在定位问题必需时点名，不作为叙述主体。"上传的视频先由识别服务认出动作，再与标准动作库比对"优于"POST submit-by-url 后 dual_link.py 并发两条链路收敛成 UnifiedShotEvent"。
- 文档、评审意见、报错引用不受此限：术语、命令、错误信息原样保留。
- 内部代号、自造词、行话，在对话里首次出现就要换成读者能懂的说法，或一句话说明它指什么。"账面优势""对偶牌"这类自造词不要直接用。
- 关键术语有多个可能含义时，先钉死语义再使用："这里的 turn 指一次用户输入到回复完成。"
- 读者身份变了，语言跟着变。对方以产品视角提问，就按产品视角的语言答，不要按框架作者同行的语言答。
- 比喻服务于从已知到未知：一个比喻说清一件事就够；连环比喻（每个比喻又引入新概念）让读者更晕。要通俗，不是要文采。

## 正向表述

- 正着说，不反着说。"导入不代表已运行"要读者反推含义；"导入只是保存文件，首次给 Agent 安装时才会运行，届时会提示确认"一步到位。
- 增量修改的文档，从零正向叙述现在的样子，不写"修正了之前 X"。新读者没有旧语境，"以前是什么样"对他们只是噪音。
- 面向用户的文案要承担解释职责：说清发生了什么、意味着什么、用户需要做什么；状态播报（"已精简历史"）不是解释。

## 立场变化要声明

- 本轮结论与之前说过的不一致时，显式说"之前说 X，现在更正为 Y，原因是 Z"。每轮都斩钉截铁但轮间立场翻转而不声明，读者会以为你一直在说同一件事；发现翻转时，信任崩塌。

## 组织信息，减少读者推断

- 读者最需要的结论、答案或行动，放在容易找到的位置；理由和细节随后。
- 引入新内容时给足背景：从读者已知的对象或现象出发，再引入新的组件、术语和关系。
- 用关键名称连接前后内容。为了"不重复"而换成含义不明的代词或近义词，读者就要重新猜一次。
- 条件、转折、因果、例外和时间顺序都写明白，不让读者自己补"因为""只有在……时""之后"。讲机制时写出参与者、动作和关系的实际因果，不用抽象概括代替。
- "它""这""上述情况"可能指向多个对象时，写出对象名称，或重组句子。
- 列表各项保持同一形态——都是名词短语，或都是动作句；引导句与各项连读应是通顺的完整表达。段落呈现连续的关系，列表呈现真正并列的事项，结构服务于逻辑，不是为了让版面整齐。

## 用词准确而稳定

- 优先使用项目、代码、接口和领域中已有的名称；同一个概念从头到尾用同一个名字。同一类操作，全文用同一种说法。
- 术语第一次出现、读者可能不熟悉时，用一句话说明含义或它在当前问题中的作用；读者显然熟悉的词不必解释。
- 常见词能表达准确时用常见词；技术词更准确时用技术词，并按需解释。黑话、行话、缩写堆叠和抽象名词串，绕不开时说明它具体指什么。
- 对比不同概念时，不合并成一个不精确的说法；丢掉技术区别的"通俗"是新的含糊。

## 改写含糊的表达

含糊的常见形态：只剩评价没有事实；一句话挤着现象、原因、处理和影响；指代不唯一；条件与动作分离。改法：补出对象、动作和可观察结果；按关系把多层信息拆成各负其责的句子；写出指代对象；条件放动作之前。

改写依靠证据：从对话、代码、日志或可靠资料确认事实，再写具体。缺证据时，把不确定性写进句子，不用没有依据的细节换取"显得具体"。

改写有边界：拆句是让每句只承载一层关系，不是把因果链拆断——失败原因跟着写入、回滚跟着失败；主动语态为了动作主体清楚，主体未知时硬改成主动句会凭空编出责任人。

并列的条件和数值用表格，成对的取舍用列表，有先后的动作用编号步骤——载体的结构替读者完成一部分解析。

## 让重要信息出现在正确位置

- 限制、前置条件、验收标准紧邻相关的操作或结论；会改变读者判断的信息（风险、副作用、前提）不藏进附注、括号或末尾补充。
- 会造成数据丢失、覆盖等重大后果的操作，把后果写在动作之前；重要性靠后果本身传达，不靠感叹号和"务必"堆砌。
- 操作指令要可执行：说清动作和对象（"运行 X 清除缓存"，不是"确保缓存干净"）、必要条件、成功判断标准；多个动作、分支或检查拆成可逐项核对的结构。

## 根据场景调节

- **简单问答**：直接回答，只补防止误解所需的信息。
- **排查与实验汇报**：当前结论（含"尚未定位"）→ 证据 → 下一步。数据表是支撑，不能代替结论句。
- **方案讨论**：先给建议和方向，再给决定性的理由、假设和取舍。按读者要做的决策裁剪信息，全景知识不是决策信息。
- **改动交付汇报**：按"最小信息集"四要素组织（改了什么、依据、影响、验证）。
- **面向用户的文案**：正向表述，承担解释职责。
- **代码解释**：从代码实际做什么开始，再解释关键机制和影响；有证据时指向具体文件或符号。
- **教学、深入分析或正式文档**：按读者需要展开解释和证据。清晰不等于简短，也不等于全部改成列表。
- **代码、接口契约、引文、法律文本或指定格式**：保持原文的准确性和格式要求。

## 发送前复核

较长或重要的回答，发送前当作第一次读到它的读者通读一遍：

1. 第一句是结论或答案吗？读者还需要自己拼、自己总结、向你求确认吗？
2. 你对读者所指对象的解读、影响结论的前提假设，亮出来了吗？读者能一眼发现你答偏了吗？
3. 关键断言的依据等级交代了吗——验证过的不在说"应该"，没读过的名字没有装确定？
4. 汇报的四要素（改了什么、依据、影响、验证）齐吗？有没有被省略的关键事实？
5. 每个指代唯一吗？多义术语钉死语义了吗？语言密度匹配读者身份吗？
6. 与之前的说法不一致的地方，声明了吗？
7. 冗余删掉了吗？删过头了吗——读者必需的信息还在吗？
8. 读者读完能理解内容、做出判断、知道下一步吗？

简单回答不必逐项检查——复核在写作中完成。
