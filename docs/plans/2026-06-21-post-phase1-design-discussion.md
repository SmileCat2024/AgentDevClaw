## 1. 核心产品语义纠正

### 1.1 群聊里的 Agent 到底是什么

这是整个设计中最关键的认知基础。在反复讨论中，我们明确了一个极易混淆的点：

**群聊里的 Agent 既不是 agent 实体（进程），也不是工作空间（容器），而是一个抽象身份。**

更精确地说：它代表的是**由若干组会话共同构成的、具有相关上下文信息以及配置特点的集合**。

这个定义很抽象，但正是这种抽象性是理解群聊概念的关键。具体含义：

- 当你在群里 `@编程小助手`，你 @的不是一个进程、不是一个 session，而是"编程小助手"这个**身份概念**
- 这个身份下面可以有零个、一个或多个 session
- 你 @它的时候，可能是在跟某个具体 session 对话（继续之前的工作），也可能只是在跟这个抽象概念对话（开一件新事）
- 具体是哪种，取决于你有没有引用某个 session，以及管理员的判断

### 1.2 这个认知为什么重要

如果把这个概念搞错了（比如认为群里的 agent = 一个 session），后续所有设计都会偏离：

- **态势感知会做错**：如果认为 agent 是单实体，就会在成员旁边显示"running/idle"状态点。但实际上一个身份有多个 session，你显示谁的状态？
- **@mention 语义会做错**：如果认为 @mention = 给某个 session 发消息，就会预设 @mention 的行为是确定性的。但实际上 @mention 只是一个标识符，具体行为由上下文和管理员共同决定
- **模式设计会做错**：如果认为 agent = 固定实体，就会把所有行为绑定在这个实体上。但实际上 agent 是一个抽象层，行为应该由更上层的模式来控制

### 1.3 软耦合原则

这个原则贯穿整个设计：

**标识符（@mention 语法）是稳定的，但标识符触发的行为是软耦合的。**

`@编程小助手` 这个语法永远不变。但"@了之后发生什么"——发到哪个 session、附带什么上下文、要不要管理员介入——取决于：
- 用户是否引用了某个 session
- 当前的群模式设置
- 管理员的判断（如果管理员参与）

这些行为可以单独迭代，不需要改 @mention 语法本身。

## 2. 群聊中的 Agent 身份模型

### 2.1 身份的来源

身份来自工作空间的 `metadata.json` 中的 `identities` 声明（Phase 0 已实现）。每个身份包含：

- `identityId`：身份标识（如 `main`、`explorer`）
- `displayName`：群聊中显示的名称（如"主代理"、"探索代理"）
- `sessionModel`：会话模型（`persistent` 或 `one-shot`）
- `description`：身份描述

完整引用格式：`workspaceId:identityId`，如 `programming-helper:main`。

### 2.2 身份与 Session 的关系

```
身份（抽象）
  │
  ├── Session A（具体的工作实例）
  ├── Session B（另一个工作实例）
  └── Session C（已完成，历史记录）
```

关键区别：

| 身份类型 | Session 创建行为 | Session 复用行为 |
|---------|-----------------|-----------------|
| `persistent` | 第一次 @时创建 | 同一群内后续 @可复用 |
| `one-shot` | 每次 @都创建新的 | 不复用，用完即走 |

但这只是**默认行为**。具体是否复用、是否创建新 session，最终取决于：
- 用户是否引用了某个已有 session
- 管理员的判断（如果管理员参与路由决策）

### 2.3 身份在群聊中的注册

用户建群时，从所有可用身份中**扁平化选择**成员。不做分类、不预设"哪些身份适合群聊"——所有身份都可选，让用户自己决定。

这是刻意的设计选择：**在产品早期不做收敛，保持扁平，让实际使用告诉我们哪些模式是常见的，再在上层增加约束和抽象。**

## 3. Session 作为群聊一等对象

### 3.1 Session 不是隐藏元数据

在 Phase 1 的实现中，session 信息隐藏在消息的 `routing` 字段里。但按照正确的语义模型，**session 应该是群聊中可见的一等对象**。

当用户 @mention 触发派发后，agent 的 session 不仅存在于 agent 的页面里，也**在群聊消息流中可见**：

```
消息流示例：

[我 14:30]
@主代理 检查 auth 模块的登录逻辑

[主代理 · auth-task-001] 14:31
任务已开启 ✓
                    ← 这条消息携带 session 标识，可以被后续引用

[我 14:35]
@主代理 继续修那个 token 过期的 bug
                    ← 这条消息引用了 auth-task-001

[主代理 · auth-task-001] 14:50
已修复 ✓

[我 15:00]
@主代理 看看 payment 模块

[主代理 · payment-task-002] 15:01
任务已开启 ✓
                    ← 新 session，与 auth-task-001 隔离
```

### 3.2 Session 的可见信息

当 session 作为消息出现在群聊中时，它携带：

- **Session 标识**：显示在消息头部（如"主代理 · auth-task-001"）
- **状态标记**：routing badge（⌛ → 🔄 → ✓ / ✗）
- **导航链接**："查看 →"点击跳转到 agent 的 session 页面
- **可引用性**：其他消息可以引用这条消息，从而引用这个 session

### 3.3 引用 Session 的两种交互方式

讨论中确定了两种引用方式，**两种都要有**：

**方式一：消息引用（类似微信引用消息）**

在 session 消息上操作（右键/长按/点击引用按钮）→ 新消息带上引用标记 → 这条新消息的 dispatch 目标就是被引用的 session。

**方式二：点击身份头像 → 弹出 session 列表**

点击群头部或消息中 agent 身份的头像 → 弹出面板显示该身份在当前群里的活跃 session 列表（以及历史 session）→ 选择一个 → 后续消息引用该 session。

### 3.4 不引用 Session 时的默认行为

用户 @mention 但**没有引用任何 session**时：

**默认创建新 session。**

理由："引用"机制的存在意义就是表达"继续"。不引用就是"新开"。这个规则简单清晰，用户容易理解：

- 引用了 session → 继续之前的工作
- 没引用 → 新的工作

但这个默认可以被管理员覆盖——在管理员参与路由的模式下，管理员可能判断"这个新任务其实应该接到已有的某个 session 上"。

### 3.5 Session 命名

新创建的 session 最初没有有意义的名称。短期方案：使用 session ID 或时间戳。

后续演进：管理员可以为 session 命名（比如"auth 重构"、"payment 检查"），使命名有语义。这不影响功能，只影响可读性。

## 4. 输入模型：双模式 + 状态栏 + Mention

这是讨论中最核心、最反复的部分。最终收敛到的模型如下。

### 4.1 设计理念

群聊的输入模型需要解决一个根本矛盾：

**程序是死的（UI 控件一旦做出来就是刚性的），用户意图是活的（每次发消息时的意图都可能不同）。用户需要在"确定性"和"模糊性"之间自由滑动。**

举例：
- 有时用户想"这条消息必须发到 session-aaa，不需要任何判断"（确定性端）
- 有时用户想"我就跟编程小助手说句话，具体怎么处理你们看着办"（模糊端）

传统的 @mention 只能覆盖模糊端。我们需要更丰富的输入模型让用户表达自己在这条消息上的确定性程度。

但同时，**不能预设过强的产品语义**。不能把消息分成"指令型/bug 型/feature 型"这种死板分类——那样产品一定走不通。

### 4.2 最终模型：两个模式 + 状态栏

```
群头部（always visible，持续生效）
├── 主动性模式：[辅助 / 规划 / 执行]
├── 自决权模式：[直接执行 / 有疑则停 / 方案确认]
│
状态栏（每条消息，消息构成）
├── @mention：目标身份
├── Session 引用：确定性路由（选了就精确，不选就模糊）
└── 附件：上下文
```

**关键设计原则：模式和行为不产生复杂的交互规则。**

模式管的是"系统怎么反应"。状态栏管的是"消息由什么构成"。两者正交。

### 4.3 维度一：主动性模式

> **管理员不被告知时，有多主动参与群里的对话流？**

| 模式 | 类比 | 管理员行为 |
|------|------|-----------|
| **辅助** | 用工具 | 完全被动。不主动参与路由。@编程小助手 = 直接派发，管理员不介入。只有 @管理员 时才启动 |
| **规划** | 请顾问 | 主动观察群里发生的事情，适时提出建议。但不自作主张执行 |
| **执行** | 交秘书 | 全权主动管理。包括决定路由、判断要不要创建新 session、推进停滞的任务 |

三个模式对应的是用户对管理员的**信任梯度**——零信任（辅助）、部分信任（规划）、完全信任（执行）。用户的直觉能直接映射：我现在多大程度上愿意让管理员自己拿主意？

### 4.4 维度二：自决权模式

> **管理员在处理事务时（无论是自己主动的还是被 @的），遇到决策点怎么做？**

| 档位 | 语义 | 什么时候找用户 |
|------|------|--------------|
| **直接执行** | 拿到任务就做，自己判断、自己调度 | 只有严重问题 |
| **有疑则停** | 正常推进，但遇到不确定的就停下来问 | 发现任何疑点 |
| **方案确认** | 先出方案给你看，你点头了再执行 | 执行前必有一次 checkpoint |

三档的区别：

- **直接执行 vs 有疑则停**：区别在于"停下来的门槛"。直接执行只在严重问题时停；有疑则停在任何不确定时停。
- **有疑则停 vs 方案确认**：区别在于"是不是每次都要亮方案"。有疑则停是正常推进、例外才停；方案确认是每次都先展示思路、拿到许可再动。

**重要：严重问题时终止不是模式特征，是底线。** 任何模式下（包括直接执行），遇到严重问题都必须停。这不是用户选的，是系统保证的安全阀。

**自决权适用于管理员做的所有事情。** 不只是 agent 调度。无论是路由任务、管理资源、还是做其他工作空间的事，同一个自决权档位生效。

### 4.5 两个维度的正交性

这两个维度完全独立，用户可以任意组合：

- 辅助 + 直接执行：平时不出现，但你 @管理员时它直接干完
- 执行 + 方案确认：平时很主动地规划，但每个动作都要你点头
- 规划 + 有疑则停：主动观察和建议，正常推进，有风险就停

用户只需回答两个独立问题：
1. "管理员平时有多主动？" → 主动性模式
2. "管理员做事时什么时候来找我？" → 自决权模式

### 4.6 模式的持久性与切换

两个模式都是**群级别的持久设置**，显示在群头部最显眼的位置。切换后持续生效，直到再次修改。

**不做消息级别的模式覆盖。** 理由：发消息时用户已经有机会调整设置。想临时升降自决权，先切一下再发，两步操作。这比在每条消息上加模式选择器更简单。

模式切换的力度是**适中的**——不像切换 DND 模式那么随意，但也不像修改配置文件那么重。一键切换，持续生效。

### 4.7 状态栏的职责边界

状态栏**只管消息构成**，不承载行为语义：

- **@mention**：目标身份。不选 = 纯讨论；选了 = 需要响应
- **Session 引用**：确定性路由。不选 = 新 session 或管理员决定；选了 = 精确到指定 session
- **附件**：上下文引用

状态栏上没有"执行标记""编排标记"之类的行为开关。因为行为由模式决定了。

### 4.8 Mention 的角色

Mention 仍然存在，但不再是唯一的意图表达通道。它的角色被重新定位为：

**Mention 是状态栏的一部分，负责"目标身份"这一个维度。**

Mention 不是行为的触发器，而是路由的标识符。具体发生什么（创建新 session？复用已有？管理员介入？）由模式和 session 引用共同决定。

## 5. 被否决的方案及原因

这部分记录讨论中被否决的设计方案，以及否决的理由。**这些记录的价值在于防止后续重新踩坑。**

### 5.1 ❌ "事事确认"自决档

**方案**：在自决权维度上设置"事事确认"档位，要求管理员在每个决策点都征求用户确认。

**否决原因**：
- 管理员的决策点本来就不多（主要是调度路由），没有"事事"可确认
- 这个词制造了虚假的复杂度，让用户以为有很多需要确认的事情
- 实际操作中会非常繁琐，用户体验差
- "方案确认"已经覆盖了"需要在执行前获得用户许可"的场景

**正确方案**：自决权只有三档——直接执行 / 有疑则停 / 方案确认。去掉"事事确认"。

### 5.2 ❌ 消息级别的模式覆盖

**方案**：在状态栏上加模式选择器，允许每条消息临时切换主动性或自决权模式。

**否决原因**：
- 增加每次发消息的认知负担
- 模式的价值在于"设完就持续生效"，消息级覆盖破坏了这个简洁性
- 发消息时用户已经有机会去调整群设置——先切模式再发消息，两步操作就够了
- 消息级覆盖会导致"这条消息在什么模式下发送的"这种历史状态难以追溯

**正确方案**：模式是群级别的持久设置。状态栏只管消息构成。

### 5.3 ❌ 群成员旁边的状态点（态势层）

**方案**：在群头部 awareness bar 的每个 agent 成员旁边显示 running/idle 状态点。

**否决原因**：
- 基于错误的产品语义：把群聊里的 agent 当成了单实体
- 一个身份可以有多个 session，显示"running/idle"说不清是哪个 session 的状态
- "你到底连的是谁"这个问题无法回答

**正确方案**：态势感知的对象是**群里活跃的 session**，不是 agent 成员。态势层展示的是"这个群里正在发生哪些工作"。

### 5.4 ❌ 复杂的资源分类系统（static / maintainable + 版本管理）

**方案**：为群资源建立复杂的分类体系——静态资源、可维护资源，可维护资源带版本历史。

**否决原因**：
- 过度分析，预设了过强的产品语义
- 用户发消息的资源引用需求是非常灵活的，不能预设类型
- "static vs maintainable"的区别在实际使用中模糊不清
- 版本管理增加实现复杂度，短期无明确需求

**正确方案**：附件系统的核心就是**管理文件地址**。Claw 自管的内容存群目录下，外部文件只存路径。不做复杂分类。引用和附件是两个层次——附件是存储管理维度，引用是使用维度。管理服务于"不让用户反复复制粘贴"这一个目标。

### 5.5 ❌ "@管理员 时始终满权"

**方案**：无论群模式如何，@管理员 都是一次满权调用，管理员可以做任何事情。

**否决原因**：
- 用户需要可预期的行为边界，不只是"管理员有多主动"，还有"管理员在执行过程中有多大的自决权"
- 有时用户 @管理员 是希望它直接执行；有时是希望它先出方案确认；有时是希望"没问题就做，有问题停下来"
- "满权"抹平了这些细致的差异，破坏了用户预期
- 会话创建权限等具体能力不应该被"满权"一词笼统覆盖

**正确方案**：@管理员 的行为受自决权模式约束。自决权决定了管理员在处理任务时的确认策略——直接执行、有疑则停、还是方案确认。

### 5.6 ❌ 把所有管理员行为绑入模式

**方案**：把定期总结、长期沉淀、事件观察等行为全部绑定到三个主动性模式中，模式定义了完整的行为包。

**否决原因**：
- 这些行为和"管理员有多主动"不在同一个维度上
- 用户可能想要"执行模式但不要定期总结"
- 用户可能想要"辅助模式但定期任务开着"
- 把所有行为绑入模式会导致模式定义膨胀，规则复杂化

**正确方案**：模式只管"主动性"这一个维度。定期任务、长期沉淀等是独立的开关，有跟随模式的默认值，但用户可以单独翻转。

### 5.7 ❌ Mode 的复杂交互规则

**方案**：定义"在模式 A 下 mention 效果是 X，在模式 B 下 mention 效果是 Y，除非……"这类规则。

**否决原因**：
- 规则太复杂，用户记不住
- 不够自然，破坏了模式作为"简单心智模型"的价值

**正确方案**：模式和状态栏正交，不产生交互规则。模式管"怎么反应"，状态栏管"发什么"。

## 6. 态势层设计

### 6.1 态势层是什么

态势层不是"agent 成员的状态点"，而是**群里正在发生的 session 活动的概览**。

它回答的问题是："这个群里现在有哪些工作在进行？"

### 6.2 态势层的内容

```
群 "系统重构"
├── 活跃工作：
│   · auth 重构 [session-aaa] — 空闲
│   · payment 检查 [session-bbb] — 运行中
│   └── bug 修复 [session-ccc] — 已完成
│
└── 成员（身份列表，不显示状态点）：
    · 编程小助手（主代理）
    · 探索代理
    · 管理员
```

### 6.3 Session 标题/描述的来源

新创建的 session 最初没有有意义的名称。Session 的标题/描述来源：

1. **短期**：使用 session ID 或时间戳
2. **中期**：管理员为 session 命名
3. **长期**：自动从任务描述中提取

### 6.4 数据来源

态势层的数据来自：
- 群聊消息中的 routing 信息（哪些 session 被创建）
- ViewerWorker 的 `/api/agents/:agentId/running` 端点（session 是否在处理）
- `getAgentRuntime()` 函数（runtime 是否存活）

### 6.5 UI 位置

态势层显示在群头部（awareness bar 区域），展示活跃 session 列表。不是每个 agent 成员旁边一个状态点，而是一个独立的"工作概览"区域。

### 6.6 点击行为

点击活跃 session 条目可以跳转到对应的 agent session 页面（与消息上的"查看 →"链接相同的行为）。

## 7. 资源与附件系统

### 7.1 设计理念

附件系统的本质是**管理文件地址，服务于人类意图的表达**。

没有这套系统时，用户的操作方式是：自己在别处写好内容 → 复制文件路径 → 粘贴到消息里。这很繁琐，而且下次用的时候还得重新找路径。

附件系统就是把这一层封装起来，让用户能方便地：
- 写一段内容，存下来，下次直接引用
- 引用已有文件，不用反复复制路径
- 在消息中结构化地附上上下文

**不预设过强的语义。** 不区分"指令型附件""参考型附件"等。附件就是附件，怎么用由用户决定。

### 7.2 两层模型

**存储层（附件系统）**：管理"东西存在哪"

- Claw 自管的内容：用户在群里写的文本片段，存在群目录下
- 外部文件引用：本地文件路径，Claw 不接管内容只存路径
- URL：已有的链接功能

存储位置：
```
~/.agentdev/AgentDevClaw/group-chats/<chatId>/
├── chat.json              ← 群元数据 + 消息流
└── resources/
    ├── res-001.md         ← 用户写的内容
    ├── res-002.txt
    └── res-003.json       ← 外部引用元数据
```

**使用层（引用系统）**：管理"怎么用这些东西"

- 在消息中引用一个附件（附上作为上下文）
- 在消息中引用一条历史消息（类似微信引用消息）
- 在消息中引用一个 session（继续之前的工作）

两层正交：一个附件可以被多条消息引用，一条消息可以引用多个附件。

### 7.3 附件的交互形态

采用**输入区分栏**方案（讨论中的方案 B）：

```
┌──────────────────────────────────────────┐
│ @主代理 检查这个模块的依赖关系             │  ← 主输入（简短指令）
├──────────────────────────────────────────┤
│ 📎 依赖分析要点                            │  ← 附件区（可展开编辑）
│   - 关注循环依赖                           │
│   - 检查版本冲突                           │
│ 📎 架构文档.md                             │  ← 附件（文件引用）
│ + 添加附件                                 │
└──────────────────────────────────────────┘
```

用户在主输入框写简短指令，在附件区写详细说明或引用已有内容。发送后，群聊消息流显示简短指令 + 附件标签。

### 7.4 消息引用

消息引用类似微信/QQ 群的"引用消息"功能：

- 在任意消息上操作 → "引用" → 新消息带上引用标记
- 被引用的消息内容作为上下文附在消息中
- dispatch 时，引用内容拼入 prompt

消息引用是引用系统的一种特例——它引用的不是文件，而是一条历史消息。

### 7.5 附件的管理

附件管理的核心目标：**不让用户反复复制粘贴，不浪费用户口舌。**

- 用户写过的附件存在群目录下，下次可以直接搜索/选择复用
- 不需要复杂的分类系统、版本管理
- 后续根据实际使用情况再考虑增加分类、搜索优化等功能

### 7.6 Dispatch 时的 Prompt 组装

当消息附带附件时，agent 收到的 prompt 结构：

```
[群聊：系统重构]
@主代理 检查这个模块的依赖关系

附件：
--- 依赖分析要点 ---
- 关注循环依赖
- 检查版本冲突
--- 架构文档.md ---
（文件内容或路径）

参考链接：
- https://github.com/...
```

所有附件内容**全量内联**进 prompt。短期不做"摘要 + 链接"的复杂处理。

## 8. 群管理员 Agent

### 8.1 定位

群管理员是一个**独立的 prebuilt agent**（`work-group-admin`），不是 programming-helper 的一部分。

它有自己的 runtime、自己的 session、自己的工具集。职责清晰，不干扰其他 agent 的会话。

### 8.2 核心职责

管理员的职责覆盖多个行为通道：

**输入响应**：
- 在辅助模式下：不参与（只有 @管理员 时才启动）
- 在规划模式下：分析用户意图，提出方案建议
- 在执行模式下：全权处理——判断路由、决定 session、组装上下文、派发执行

**事件观察**：
- 观察群内事件（agent 完成、出错、新 session 创建等）
- 辅助模式下不观察
- 规划模式下观察并适时建议
- 执行模式下观察并主动管理

**定期任务**（独立开关，不绑定模式）：
- 定期生成绩效总结
- 长期工作记录沉淀
- 发现停滞的 session 并推进

### 8.3 管理员工具集

管理员需要以下工具来履行职责：

| 工具 | 用途 |
|------|------|
| `gc_overview` | 查看所有群的概况：成员、活跃 session、模式设置 |
| `gc_messages` | 读取指定群的消息流 |
| `gc_dispatch` | 手动派发任务到指定 agent session |
| `gc_summary` | 向群聊写入一条工作摘要（kind: "summary"） |
| `gc_update_resource` | 更新群资源（用于长期沉淀） |
| `gc_agent_status` | 查看 agent 运行状态 |

### 8.4 硬性限制（规则）

规则是独立于模式的**绝对禁止列表**：

| 规则 | 说明 |
|------|------|
| 禁止创建会话 | 管理员不能自己创建新 session，只能在已有 session 间调度 |
| 禁止删除资源 | 管理员不能删除群里的资源文件 |
| 禁止自主派发 | 管理员不能不经过用户就向 agent 派发任务 |

规则有跟随模式的默认值：

| 模式 | 默认规则 |
|------|---------|
| 辅助 | 禁止创建会话 + 禁止自主派发 |
| 规划 | 禁止创建会话 |
| 执行 | （无限制） |

用户可以独立调整规则，不受模式约束。

### 8.5 管理员被 @时的行为

当用户 @管理员 时，管理员按照当前群的自决权模式来决定行为：

- **直接执行**：管理员直接处理，不问用户
- **有疑则停**：管理员正常处理，遇到不确定的停下来问
- **方案确认**：管理员先出方案，用户确认后再执行

### 8.6 管理员的回复方式

管理员的回复**直接写入群聊消息流**（作为 `from: 'work-group-admin:admin'` 的消息），不需要用户跳转到管理员的 session 查看。

这与普通 agent（主代理、探索代理）不同——普通 agent 的回复在自己的 session 里，群聊只显示状态和导航链接。管理员的回复直接在群里可见，因为管理员的角色就是群内的协调者。

## 9. 用户故事与场景

### 9.1 场景一：深度开发（辅助模式）

**用户心智**：我在电脑前，我知道我要做什么，管理员别烦我。

**设置**：
- 主动性：辅助
- 自决权：直接执行（虽然辅助模式下管理员几乎不出现，但 @管理员时希望它直接做事）

**流程**：
1. 用户建群"auth 重构"，选主代理为成员
2. 用户 `@主代理` + 写任务 → 直接派发，管理员不参与
3. 消息出现 routing 状态（⌛ → 🔄 → ✓）
4. 用户点"查看 →"跳转到 agent session 看结果
5. 用户回来，引用 session 继续修 bug
6. 全程管理员不出现
7. 用户 @管理员 帮我总结一下 → 管理员启动，直接总结，写入群聊

### 9.2 场景二：出门委托（执行模式）

**用户心智**：我要出门了，接下来用手机跟你沟通，你自己搞定。

**设置**：
- 主动性：执行
- 自决权：有疑则停（总体信任，但拿不准的时候问我）
- 定期总结：开
- 规则：无限制

**流程**：
1. 用户出门前把群模式切到"执行"
2. 路上用 IM 发"把 payment 模块的测试补一下"
3. 管理员收到 → 自己判断创建新 session → 派发给主代理 → 回复"已安排，session-xxx"
4. 主代理工作期间，管理员观察进度
5. 遇到不确定的事情（比如测试框架选择），管理员发消息"用 Jest 还是 Mocha？"→ 用户回复
6. 每隔一段时间，管理员自动生成进度摘要写入群聊
7. 用户回家后，切回辅助模式，直接看摘要和 session 详情

### 9.3 场景三：复杂任务规划（规划 + 方案确认）

**用户心智**：这件事比较复杂，我需要参与决策，但不想自己动手调度。

**设置**：
- 主动性：规划
- 自决权：方案确认

**流程**：
1. 用户 `@管理员 把 auth 和 payment 两个模块的重构安排一下`
2. 管理员分析 → 回复"建议分两步：先 auth 后 payment。auth 我会创建新 session，用主代理执行。你看行吗？"
3. 用户说"行" → 管理员执行
4. auth 完成后，管理员汇报"auth 重构完成，下面开始 payment"
5. 用户说"等一下，payment 先别急，我看看 auth 的结果" → 管理员暂停
6. 用户看完 auth 结果，确认没问题 → "继续" → 管理员安排 payment

### 9.4 场景四：模糊指令处理

**用户心智**：我说了一大堆，但可能不太清楚。

**不同模式下的不同处理**：

- **辅助模式**：消息原样派发，agent 可能搞不定（因为指令模糊）
- **规划模式**：管理员识别出模糊 → 主动问"你是指 A 还是 B？"
- **执行模式**：管理员做最佳判断 → 执行 → 报告"我理解你要的是 X，已经安排了。如果不是请告诉我"

**关键区别**：规划模式会**停下来问你**，执行模式会**自己判断后继续**。好的秘书遇到 unclear 的指令也会自己做判断而不是瞎搞——区别在于是否在判断前征求你的意见。

### 9.5 场景五：多 Session 并行工作

**用户心智**：我同时管着好几件事。

**流程**：
1. 群里有 3 个活跃 session：auth 重构、payment 检查、bug 修复
2. 态势层显示：
   ```
   · auth 重构 [session-aaa] — 空闲
   · payment 检查 [session-bbb] — 运行中
   · bug 修复 [session-ccc] — 已完成
   ```
3. 用户引用 session-aaa 发新消息 → 继续做 auth 的事
4. 用户不引用，直接 @主代理 → 新 session，新任务
5. 用户点击态势层中的 session-bbb → 跳转看 payment 的进度

### 9.6 场景六：附件引用的工作流

**用户心智**：我有一份详细的执行说明，不想每次都重新打字。

**流程**：
1. 用户第一次在输入框的附件区写了一份"依赖分析要点"
2. 发送消息，附件存入群资源目录
3. 下一次类似任务时，用户在附件区搜索"依赖"→ 选中已有附件 → 直接引用
4. 不需要重新写，也不需要去文件系统找路径
5. 如果需要修改，展开附件编辑 → 修改 → 保存（覆盖）

### 9.7 场景七：管理员定期沉淀

**用户心智**：长期项目需要工作记录。

**设置**：定期总结 = 开

**流程**：
1. 群运行了一周，有多个 session 完成了各种任务
2. 管理员定期生成摘要，写入群聊（kind: "summary" 的特殊消息）
3. 摘要内容：本周完成的工作、遇到的问题、下一步建议
4. 用户随时可以在群消息流中看到这些摘要
5. 管理员也可以把关键信息更新到群资源中（长期沉淀）

## 10. 开放问题

以下问题在讨论中被识别但尚未完全确定，列出供后续迭代：

### 10.1 Session 命名机制

Session 初始没有有意义的名称。短期用 ID/时间戳。中期管理员命名。长期是否自动从任务描述中提取？

### 10.2 模式切换时的过渡处理

从执行模式切到辅助模式时，管理员正在做的定期任务还要不要完成？

倾向：正在做的做完，不再启动新的。

### 10.3 定期任务的频率和触发机制

定期总结的频率是固定的还是可配的？触发机制是 push（事件驱动）还是 pull（定期轮询）？

短期建议固定频率，pull 机制。

### 10.4 事件观察的"观察"具体机制

管理员需要感知群内事件。是事件发生时 push 通知管理员，还是管理员定期 pull 检查？

倾向 pull（管理员 runtime 定期轮询群消息流），因为 push 需要更多基础设施。

### 10.5 规则系统的深度

当前是几个预定义的 checkbox（禁止创建会话、禁止删除资源等）。后续是否需要通用规则引擎？

短期：预定义 checkbox，不做通用规则引擎。

### 10.6 外部资源引用类型

除了用户手写的 txt/md 和 URL，资源还可以引用探索记录（exploration-link）、本地文件（file-link）。这些是否需要做成一等公民？

短期：保持 URL 链接的简单形式。后续按需扩展。

### 10.7 附件大小限制

全量内联进 prompt 可能导致 token 超限。是否需要软限制 + 警告？

短期：不做硬限制，依赖模型的上下文窗口。后续增加 token 估算和警告。

## 附：设计决策速查表

| 决策点 | 结论 | 理由 |
|--------|------|------|
| 群聊 agent 是什么 | 抽象身份，不是实体 | 身份下可有多个 session |
| @mention 的角色 | 标识符，不预设行为 | 行为由模式 + 引用决定 |
| 主动性模式 | 辅助/规划/执行 | 信任梯度，用户直觉可映射 |
| 自决权模式 | 直接执行/有疑则停/方案确认 | 覆盖所有确认场景 |
| 模式粒度 | 群级别持久 | 切换力度适中 |
| 消息级模式覆盖 | 不做 | 先切模式再发消息即可 |
| "事事确认" | 删掉 | 决策点不多，虚假复杂度 |
| 群成员状态点 | 不做 | 身份有多个 session，状态说不清 |
| 态势层对象 | 活跃 session | 不是 agent 成员 |
| 附件系统定位 | 文件地址管理 | 不预设语义，服务于表达 |
| 消息附件 vs 群资源 | 统一存储，引用使用 | 两层正交 |
| @管理员 满权 | 不满权 | 受自决权模式约束 |
| 管理员回复方式 | 直接写入群聊 | 管理员是群内协调者 |
| 定期任务 | 独立开关 | 不绑定模式 |
| 规则系统 | 预定义 checkbox | 不做通用规则引擎 |
| 严重问题终止 | 所有模式通用底线 | 不是模式特征 |
| Session 不引用时 | 默认创建新 session | 引用=继续，不引用=新的 |
