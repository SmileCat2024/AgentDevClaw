# ADR-0053: 结构性优势即架构承诺（如何让能力不可搬运）

日期：2026-11-19
状态：Proposed（原则草案，待评审后转 Accepted）
关联：[ADR-0045](0045-external-plugin-package-and-workspace-assembly.md)、
[ADR-0046](0046-plugin-management-product-system.md)、
[ADR-0052](0052-plugin-model-and-mental-model.md)

## 背景

插件体系的设计（包级处置、装配层级=可见性、配置分层、空间私有仓库）可以被
任何人照抄。功能层面的领先不构成优势：写进文档就能被复刻，在更强的底层上
可能做得更顺。

真正的问题是：**要让别人适配这些能力时必须伤筋动骨，或者即使硬做，也会
自损契约与插件体验。** 这不能靠功能清单实现，只能靠架构承诺。

本 ADR 定义"结构性优势"的判据、五类可积累的承诺、维护规则与检验方法。
它约束的是我们往哪里投资源、哪些东西不能为了短期便利让步。

## 架构范式差异：插件树中心 vs 工作空间中心

两套体系的差异不在功能，而在"什么是一等公民"。

| 维度 | 插件树中心（dsh） | 工作空间中心（我们） |
|---|---|---|
| 一等公民 | 插件树 / profile | 工作空间 / 身份 |
| 执行模型 | 单进程共享服务容器 | 每身份独立 runtime 进程 |
| 组合模型 | 命令式 patch 层叠 | 声明式 `$mount` + 明确合并规则 |
| 配置模型 | entry config 整体替换 | 四层配置树 + `$mount` 语义分离 |
| 可见性 | 插件自述 / profile 全局 | 由装配事实派生（`when.agentIds`） |
| 分发单元 | npm 包 + bundle patch | 不可变 tgz（三面）+ 内容寻址环境 |
| 隔离单位 | 会话级 isolate realm | 空间级：数据、配置、资产、进程 |
| 生命周期 | Cordis fiber + HMR | 装配事务 + runtime 重启 |

由此得到四个"对方要改核心才能拥有"的差异：

1. **执行边界**：我们以工作空间身份起独立进程；单进程共享容器要变成多进程边界，
   等于换掉插件运行模型。
2. **声明式装配**：`$mount` + 合并规则 + 可见性派生；命令式 patch 层叠没有
   "装配事实"这个概念，只有"多层覆盖后的结果"。
3. **配置分层**：四层配置树与装配同源但语义分离；patch 的 config 是整体替换，
   要做分层就要改 patch 语义与所有作者的文件。
4. **内容寻址分发**：tgz + digest + 环境 hash；npm 解析是可变且全局的。

## 可挖掘与强化的架构优势

**边界原则（不可违反）**：Feature 是框架的运行时单元，基类、生命周期、上下文
注入、工具与 hook 注册面都属于框架本体；工作空间、装配、分发、治理属于应用层。
任何"为了平台可替换而把 Feature 抽象成通用能力接口"的改动都是层次倒置，不做。

按"已有 / 可挖掘 / 待补"分：

**已有（要守住，别退化成功能）**

- 工作空间数据分区与每身份 runtime：隔离、崩溃影响面、资源归属都以空间为单位。
- 声明式 `$mount` 与四层配置：装配与参数同源不同语义。
- 三面插件契约（工具/UI/数据）与可见性派生：面板与数据面按装配身份投影。
- 内容寻址环境：同一依赖集复用环境，升级与回滚可预测。

**可挖掘（架构上成立，但还没做实）**

- **框架不做产品治理**：Feature 保持框架运行时单元的本体（基类、生命周期、
  上下文注入、工具与 hook 注册）；工作空间、装配、分发、治理归应用层。
  产品模型可以在应用层演进，不必改动框架语义。对方的问题不是"插件绑死服务
  容器"本身，而是把产品治理（profile / patch / entry / row）长在了框架语义里，
  产品模型因此无法表达工作空间、配置分层与包级处置。
- **装配事务**：装配/升级/回滚是一个事务（计划 → 校验 → 执行 → 提交 → 可回滚）。
  patch 体系没有事务概念，层序变化即结果变化。
- **装配计划可审阅**：声明 → 解析 → 依赖/冲突/可见性计划 → 执行；计划是产品
  对象（可 dump、可 diff），不是 YAML 层叠的副产物。
- **执行边界产品化**：每空间沙箱、配额、健康检查、滚动替换进程；不是"有进程"，
  而是"空间是执行与治理边界"。

**待补（不改架构，但必须做）**

- 治理 seam：权限/审计/配额插到工具调用、面板数据面、装配三条路径的统一入口。
- 契约冻结：manifest、宿主注入 API、事件面的稳定面清单与兼容策略。
- 关系模型：工作空间/项目/目录/线程/渠道/审批的关系图作为一等数据模型，
  而不是散落在各模块的字段。

## 决策

### 1. 定义：结构性优势 = 能力的正确性依赖不可搬运的宿主承诺

一项能力是结构性优势，当且仅当满足以下任一条件：

- 把能力搬到别处，**行为不再成立**（依赖宿主的生命周期/状态/治理）；
- 硬搬到别处，**必须改掉对方的插件契约或插件作者要重写插件**；
- 硬搬到别处，**用户或作者要放弃已有资产**（数据、关系、治理记录）。

只满足"界面更好""操作更顺"的，是功能优势，不算。

### 2. 五类架构承诺

#### 2.1 状态所有权：权威状态只存在于宿主

**机制**：装配事实、配置来源、启用态、运行时生命周期、权限决策、审计记录
由宿主唯一持有；插件只能通过宿主 API 查询，不能自持权威状态。

**为什么抄不动**：复刻功能容易，复刻状态机难。适配方要么伪造状态（在跨
工作空间、升级、恢复时立刻暴露），要么接入我们的状态 API（等于接受我们的
契约）。

**现状与要求**：已开始收敛（`$mount` 是装配唯一事实源；overview 是派生视图）。
要求：不允许出现第二份可写的装配/状态清单；前端缓存、环境就绪判断都必须
标注为派生。

**判据**：把插件搬到别处，它是否还能回答"我被谁装配、在哪些工作空间可见、
我的配置从哪来"？不能 = 结构性。

#### 2.2 生命周期所有权：正确性只在我们的生命周期下成立

**机制**：装配 → 环境准备 → 挂载 → 失败回滚 → 升级迁移 → 崩溃恢复 →
资源回收，是宿主定义的完整生命周期；插件只提供声明与实现点。

**为什么抄不动**：抄一个"加载插件"很容易，抄"在失败、并发、升级、回滚
下仍然正确"极难。这需要长期踩坑、测试矩阵与恢复语义。适配方若只抄功能，
在异常路径上会不断暴露差异。

**现状与要求**：我们已有 provision/回滚/环境自愈的雏形；缺的是把"升级
不丢状态、崩溃可恢复、装配状态单一权威"做成可验证标准。

**判据**：在升级、崩溃、回滚、并发装配四种场景下，插件行为是否可预测？

#### 2.3 契约冻结：对外面薄而稳，内部实现厚而可演进

**机制**：冻结的是**应用层声明**（manifest、面板协议）与**框架公开面**
（Feature 的 name / tools / hooks / getCapabilities / 状态捕获等），不是把
Feature 抽象成通用能力接口。破坏性变更升 major 并保留一个版本的兼容垫片。
冻结的只是少量稳定面，不是全部实现，也不改写框架本体。

**为什么抄不动**：生态一旦按契约写插件，迁移成本 = 重写插件 + 重新验证。
适配方要么接受我们的契约（放弃自己的模型），要么要求作者写两套（自损体验）。

**现状与要求**：ADR-0046 已承诺面板协议随 minor 冻结；需要扩展到 manifest
与宿主 API，并建立变更评审（任何改动先问"是否强迫第三方插件修改"）。

**判据**：一次破坏性变更会让多少插件失效？有没有迁移工具与公告周期？

#### 2.4 治理不变量：横切所有执行路径，不可被单个插件绕过

**机制**：权限、配额、审计、成本、数据边界是执行模型里的不变量，插在每个
工具调用、每次装配、每个数据面请求的必经路径上，而不是某个页面上的开关。

**为什么抄不动**：抄一个"权限页"容易；让所有执行路径都经过同一治理点，
必须在执行模型里插入 seam，改所有插件与调用链。单个插件无法绕过，才叫结构性。

**现状与要求**：我们有工作空间数据分区、runtime 配额、通知权限的雏形；
缺统一的治理点与审计记录。

**判据**：写一个第三方插件，能否绕过权限/审计/配额？能 = 不是结构性。

#### 2.5 数据与关系资产：离开后关系失去上下文

**机制**：会话历史与连续性、线程接续、工作空间归属、协作关系、渠道绑定、
调度任务、治理记录。导出容易，但"重建关系"难。

**为什么抄不动**：文档可以复制，关系不能。适配方拿到导出数据，也拿不到
"这段历史属于哪个工作空间、接续了哪条线程、经哪个渠道进来、被谁审批"。

**现状与要求**：这些资产已存在，但没有被当成"壁垒"来维护（缺乏导出/迁移
语义、关系完整性校验）。

**判据**：用户迁走时，哪些关系必须重建？重建成本是否显著？

### 3. 维护规则（防止优势退化）

1. **单一权威**：任何状态只允许一个可写来源；新增派生视图必须显式标注。
2. **契约变更评审**：先问"是否强迫第三方插件修改"；能兼容就不破坏；破坏
   必须给迁移工具与时间窗。
3. **真实生命周期测试**：插件测试必须走真实装载与生命周期路径。绕过真实
   加载的测试会给出虚假信心（这是插件框架最常见的系统性逃逸）。
4. **治理点收口**：新增执行路径必须经过既有治理 seam；不允许插件自行实现
   权限/审计。
5. **迁移成本盘点**：定期列出"用户迁走会丢什么"，作为投资排序依据。
6. **伪优势止损**：界面布局、卡片样式、按钮位置这类可抄设计，不再作为
   竞争优势投入超额资源。

### 4. 伪结构性优势（不要误判）

- 插件页信息架构、装配清单视觉、卡片徽章；
- 包级处置的按钮与文案；
- 配置分层的表单布局；
- 仓库的三层命名与来源徽章。

这些要做，但它们是卫生标准，不是壁垒。把它们当护城河会导致资源错配。

### 5. 检验方法（可执行）

1. **移植测试**：把一个真实插件搬到另一套插件框架，记录需要改的代码行数、
   丢失的行为、需要重写的配置。改得越少，我们的优势越弱。
2. **绕过测试**：写一个恶意/越权插件，尝试绕过权限、审计、配额、可见性。
   能绕过就说明治理不是不变量。
3. **恢复测试**：升级、崩溃、回滚、并发装配后，装配状态与用户配置是否一致。
4. **契约测试**：模拟一次破坏性变更，统计受影响插件与迁移工作量。
5. **迁移成本盘点**：逐项列出用户资产，标注"可导出 / 需重建 / 会丢失"。

### 6. 路线（三步）

1. **收口状态与治理**：完成装配状态单一权威；把权限/审计/配额插到所有执行
   路径的同一 seam。这是所有后续承诺的地基。
2. **冻结外部契约**：manifest、宿主注入 API、事件面定版本与兼容策略；建立
   变更评审与迁移工具。
3. **资产化**：为会话/协作/渠道/治理记录定义导出与迁移语义，并保证关系
   完整性（导出后仍能回答归属与上下文）。

## 后果

- 资源投入从"插件页体验"转向"状态、生命周期、治理、契约"。
- 插件作者继续写 Feature（框架本体不变）；需要冻结的是应用层声明与框架公开面。
- 破坏性变更流程变重；需要兼容垫片与公告周期。
- 需要长期维护"真实生命周期测试"与"移植/绕过/恢复"三类检验。
- 明确否决"为平台可替换性抽象掉 Feature"的路线：它逆转框架本体的性质，
  且会把下层改成与产品无关的东西。

## 开放问题

- 契约冻结的具体范围（manifest 字段、宿主 API、事件面）需要逐项列出并定
  兼容级别。
- 治理不变量归应用层（Claw）；框架只在执行点暴露可插拔的钩子，不承担产品
  治理。需要与 ADR-0028 的分层判据对齐后逐项落到执行路径。
- 数据导出的格式与"关系完整性"的校验方式待定。
