# Test-Driven Development — 红绿循环

TDD 是 red → green 循环。本规范是让该循环产出值得保留的测试的参考：什么是好测试、测试放在哪、反模式、循环规则。每一节在每个循环都适用——在循环之前和之中查阅，而不是事后。

探索代码库时先读 `CONTEXT.md`（若存在），让测试名称与接口词汇匹配项目的领域语言，并遵守所触碰区域的 ADR。

## 什么是好测试

测试通过公开接口验证行为，而不是实现细节。代码可以彻底重写，测试不应该跟着动。好测试读起来像规格说明——"user can checkout with valid cart" 一眼说明存在什么能力——并且在重构后依然存活，因为它不关心内部结构。

示例与 mocking 准则见 [references/tests.md](references/tests.md) 与 [references/mocking.md](references/mocking.md)。

## Seams — 测试放在哪里

**seam** 是测试所在的公开边界：观察行为而不伸手进内部。测试活在 seams 上，永不针对内部实现。

**只在预先约定的 seams 上写测试。** 写任何测试之前，先写下待测 seams 并与用户确认；未确认的 seam 上一条测试都不写。你不可能测一切——预先约定 seams 正是让测试精力落在关键路径与复杂逻辑上，而不是摊到每个边缘情况。

要问的话："公开接口是什么？我们应该测哪些 seams？"

当接口形状本身悬而未决——模块多深、seam 属于哪一层、接口该暴露什么——参考 codebase-design 的词汇（模块、接口、深度、seam、adapter、leverage、locality）：那是一份参考资料，不是一次要运行的会话。

## 反模式

- **Implementation-coupled（耦合实现）**——mock 内部协作者、测试私有方法、或通过旁路验证（绕过接口直接查数据库）。识别标志：重构后行为没变，测试却挂了。
- **Tautological（同义反复）**——断言用与代码相同的方式重算期望值（`expect(add(a, b)).toBe(a + b)`、用同样方式手工推导的快照、常量断言等于自身），构造上必然通过，永远无法与代码不一致。期望值必须来自独立的真值来源：已知的字面量、手算的示例、spec。
- **Horizontal slicing（水平切片）**——先写完所有测试，再写所有实现。批量测试验证的是想象中的行为：你测的是事物的形状而不是用户可见行为，测试对真实变化失去敏感，并在理解实现之前就锁死了测试结构。改用**垂直切片**——一个测试 → 一段实现 → 重复，每个测试都是响应上一循环所学的 tracer bullet。

## 循环规则

- **先 red 后 green。** 先写失败的测试，再写恰好让它通过的代码。不预期未来的测试、不加投机性功能。
- **一次一个切片。** 每个循环一个 seam、一个测试、一段最小实现。
- **重构不属于本循环。** 它属于 review 阶段（见 code-review 规范），不属于 red → green 实现循环。
