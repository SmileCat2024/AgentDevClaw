# 先标准化本地显式资源寻址，再引入新的传输方式

## 状态

已接受（2026-08-22 grill-with-docs Phase 0 决策）。

## 背景

AgentDevClaw 当前同时处理多类资源：逻辑 Agent、工作会话、运行时实例、工作区宿主和页面焦点。历史上的 `currentAgent` 语义已经从 AgentDev 框架的服务端状态、ViewerWorker 协议和 DebugHub IPC 中移除；Claw 与 DebugHub 页面仍各自保留页面焦点，但焦点不再是运行时寻址依据。

后续系统可能需要在同一个页面中访问不同执行端上的 Agent。若在引入新的传输方式时同时修改既有 API、Feature 通讯和状态模型，容易把“执行归属”“资源寻址”“页面展示”和“网络连接”混成一个隐式状态，破坏本地链路并制造难以恢复的同步问题。

因此需要先在完全本地的前提下，把现有协议整理为可扩展的显式资源寻址契约。

## 决策

Phase 0 只做本地协议标准化，不实现任何新的传输或跨实例访问能力。

本阶段的核心规则：

1. Runtime 请求必须使用显式 Agent/Session/Runtime 资源身份；页面焦点不参与服务端寻址。
2. `agentId`、`sessionId`、`runtimeId`、`parentId` 和页面焦点是不同概念，不以一个字段替代另一个字段。
3. Runtime-scoped 与 Host-scoped 操作分开建模；Host 操作没有明确目标时只表示本地宿主，不根据页面焦点猜测。
4. 请求元数据、操作关联和失败错误码先在本地链路中统一，暂不增加自动重试、离线队列或状态镜像。
5. 既有本地请求的 URL、响应和执行路径保持兼容；新抽象只在现有本地目标上落地。
6. 本阶段不得加入 SSH、隧道、连接配置、远程 Catalog、跨主机路由、中继、WebSocket 或远程专用服务。

未来如果引入新的执行端，传输层只能作为目标解析后的实现细节，不能反向改变业务 Feature 的寻址方式。

## 取舍

### 选择本地先行标准化

优点：

- 可以用现有单机数据和测试验证身份边界；
- 不引入网络抖动、断线恢复和跨主机一致性变量；
- 本地链路的回归容易定位；
- 后续传输层复用已验证的请求、错误和幂等契约。

代价：

- Phase 0 不会立即产生跨主机功能；
- 需要先清理部分旧命名和隐式调用；
- 一些 Host API 要明确目标语义，短期内可能暴露原有模糊处。

### 不选择立即加入远程适配

如果把 SSH、远程 Agent 聚合和本地代理同时加入，任何失败都可能来自身份、接口、连接、重试或 UI 聚合，无法证明本地协议本身是正确的。该方案违反“远程执行端负责远程工作、本地只负责连接”的职责边界，也会让未来 Feature 被迫感知传输方式。

## 不变量

- 本地 Agent 的请求不经过新的远程路径。
- 缺少目标身份的 Runtime 请求显式失败，不静默选择页面焦点或列表第一项。
- 写操作的结果未知时不能伪造成功。
- 页面焦点只影响页面展示，不改变服务端执行归属。
- Phase 0 完成后删除或关闭新标准化层，不会留下远程运行时或连接进程。
