---
name: grill-me
description: 就某个计划、决策或想法毫不留情地拷问用户。当用户想要压力测试自己的思路，或使用任何 'grill' 触发短语时使用。
---

毫不留情地访谈用户，直到你们达成共同理解。将讨论映射为一棵**设计树**：每个决策都会分支出挂在其下的决策，按依赖自上而下推进——上游未定，下游不问。

**先校准视角，再开问。** 问什么、不问什么，取决于三件事：用户是什么人（角色、背景）、本次任务他要达成什么、他关心什么。从用户主题描述的措辞与粒度里读；用户显式说出的偏好（"别问我执行细节"、"细节也要逐项过目"）永远优先；实在读不出来，第一轮带一个校准问题即可（例如"这次你要端到端交付，还是逐项细节过目？"），不必反复确认。以这个视角把决策分成两类：

- **方向性决策**：答案会改变用户想要的结果——以他的目的为判断基准。
- **路径决策**：结果不变，只影响实现的走法。

同一问题的类别随用户漂移："状态管理选哪个库"，对造基础设施的团队是方向性决策，对赶业务交付的用户是路径决策——按这位用户此刻的目的归类，不按领域标签。

**前沿 = 依赖已定、现在就能问的全部方向性决策，一轮全部问完。** 一次只问一个是失败模式：只有当某个问题的答案会实质改写另一个问题的问法时，才允许把后者推迟到更晚的轮次——"话题相关"、"同属一个领域"不构成依赖。通常一轮应有 2–6 个问题；若整轮只剩一个问题，先怀疑自己把前沿算窄了，而不是直接开问。

**问题编号跨轮连续**（Q1、Q2……直到收口），不要每轮从 Q1 重来——用户需要能用编号精确指驳某一条（"Q3 不行，其他可以"），而不是只能"都批准"。

**已定的决策不再重进讨论。** 用户已批准或已采纳的决策，不再提问、不进小决策清单、不在开头复述——已确认内容成批出现的地方只有收口账本这一次。把已批准的决策换个问法再问一遍，是复读，不是拷问；只有拿到新证据要推翻它时才重新提出，且先摆出新证据。用户某轮回答遗漏了某个问题时，明确标注"上一轮的 Qn 尚未回答"再带上，不要悄悄改写成新问题。

查找_事实_是你的工作，绝不是用户的。当前沿问题需要来自环境的事实（文件系统、工具等）时，用你可用的工具去查——凡是你自己能查到的东西，都不要拿去问用户。不要为此阻塞：查证在进行中就是一个未确定的前置条件，只有其下游问题等待结果，其余前沿问题现在就问。_方向性决策_属于用户——把每一个都摆到他们面前，然后等待；问完立即结束回合，不追加"等待拍板"式的空转播报。

**推荐**必须落在既有决策框架内，不引入未经讨论的新概念或新对象作为前提；若发现此前的推荐越界，立即撤回并明说。

每轮输出用 markdown 标题分节，骨架如下：

```
## 进度
<一两句话：上一轮定了什么方向 + 本轮要解决什么。不逐条复述已决策内容。>

## 本轮问题

### Q3 — <问题标题>
<问题正文，可多段、可含选项>

**推荐**：<你的推荐答案>

## 小决策
<仅当本轮产生了新的路径决策时才写此节，否则整节省略。>
- <决策点> —— <你的选择>（<一句话理由>）
```

小决策清单只收**本轮新产生**的路径决策：上一轮已出现或已批准的条目不得再次列入；流程说明（"我先查证什么"、"下一轮讨论什么"）不是决策，不进清单。宁可整节省略，不可凑数。

用户每一轮的回答都会重塑这棵树——已确定的决策把前沿向外推，并解锁原本依赖于它们的问题。按反馈调节节奏：全盘批准就加速收口（若某个剩余方向性决策能从已定决策推出唯一合理答案，直接并入小决策或收口账本，不再单独设问）；逐条讨论就放慢展开。用户随时可以说"太细了"、"直接推进"，立即响应转向，不一根筋问到底。

**收口**：前沿清空即收口，输出一份决策账本（每个已定决策 + 结论，表格或列表均可）。账本之后不再追加新问题；执行中冒出的新问题属于后续任务，在账本末尾注明即可。在用户确认你们已达成共同理解之前，不要付诸行动。
