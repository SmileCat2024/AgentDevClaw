# 显示过程滚动问题的积累与验收反思

日期：2026-09-27。依据 Git 历史、工作区修复前快照、此前会话记录，以及本轮真实页面数值采样和用户体验反馈。性能数据及其边界见 [调查与修复记录](2026-09-27-chat-process-scroll-performance.md)。

结论：屏外内容应限制渲染成本这一原则早就被采用，但没有成为所有实现分支必须守住的约束。后续不断解决局部问题，最后又为避开旧窗口成本而让中等规模会话全量布局；减少 DOM 和通过功能测试，没有证明浏览器每次滚动的工作量受到控制。本轮修复让实测高度与可见范围分离，保留真实占位、限制远处整行的浏览器工作，并由实际客户端反馈闭环。

## 为什么这个基本原则没有真正落稳

1. **“有虚拟化模块”被当成“所有历史成本已受控”。** 旧窗口主要处理工具/过程子树，保留 DOM、估算高度和大量缓冲行；助手正文、元素自身动画、sticky 合成以及关闭窗口后的全量分支不受同一约束。折叠裁剪只改变可见高度，不能保证内部复杂结构没有浏览器成本。
2. **没有统一性能契约。** 为位置正确性不断加入补偿，每项局部测试可以通过；为避开这些补偿再关窗口，也能让某个基准变好。没有守住“任意模式下远历史不能持续放大滚动费用”，局部成功便可以抵消原先的保护机制。
3. **测量指标与用户故障不完全对齐。** DOM 数、首次渲染、JS 扫描耗时、几何不跳变都各有意义。用户的症状是前台连续滚动被阻塞半秒至数秒，需要检查完整浏览器链路与最长停顿。普通无头环境也不能代表实际客户端启用的所有 native 路径。
4. **对有限证据下结论过早。** “缩小扫描没效果”说明假设需要修正；“某组跳过函数后没长任务”还需内容/模式/位移一致。记录里多次承认实验失真，但仍反复使用“根因”“决定性”等措辞，容易把用户下一轮体验当成继续查错的唯一机制。
5. **修复没有及时形成版本闭环。** 大量尝试和回滚混在工作区，代码、报告与实际模板状态会分离。一次提交包含别人已有调整时，Git 记录只能说明何时收录，不能直接解释设计来源。更需要保留固定基线、有效实验与失败反馈。

这构成开发和验收规范的问题，但现有证据不能证明某个参与者“水平差”或某次美术变更独自引入全部故障。也不能把功劳只归于最后一步：前面的 Read 减负、补偿正确性和 sticky 修复保留了价值。我本轮前三步在独立环境改善了数字，用户仍严重卡顿，同样应记为未完成，而不是事后改写成每步都成功。

## 本轮如何改变验收

先在实际故障页面确认：消息/模板完整、显示过程开启、确实是全量分支；再区分应用回调与没有对应昂贵回调的浏览器工作。随后用实测行高隐藏远处整行，以全行几何一致性检查防止滚动条缩水和跳动，用尾部更新/展开/宽度/导航检查保持业务行为。最后同时接受采样的大停顿下降和用户的实际成功反馈，才判定这条会话的主要问题改善。

这是“基础原则终于在这条执行路径上落实”的修复，不是证明所有浏览器内部成本已逐项归因。可访问性放大因素有隔离实验支持，但实际页面原生调用栈没有直接证实；保留 DOM 也意味着它并非完整的有界内存方案。离屏浏览器查找、连续选择和可访问性遍历的边界已写入渲染参考。

后续规范应守住三个可检查的条件：

- 每个显示/窗口分支都必须说明远处内容的成本如何受控；禁用一套虚拟化必须有等价保护，节点门槛不能替代浏览器工作预算。
- 长会话改动要固定真实消息、真实动态模板与源码，确认实际位移和前台状态，记录最长停顿；功能正确和首次渲染变快不算滚动验收通过。
- 小批提交已验证改动；报告明确区分有效证据、失败实验和用户反馈，不提前称整体根因已解决。性能环境与交互边界有变化时重新验收。
