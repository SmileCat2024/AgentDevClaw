# 远程 Agent 访问：问题空间、能力边界与探索计划

> 文档创建日期：2026-07-23  
> 当前状态：产品与技术探索阶段，尚未确定界面形态和最终架构  
> 关联文件：`server/shared/proxy.js`、`server/shared/constants.js`、`server.js`、`public/src/app-core.js`、`public/src/app-main.js`、`public/src/modules/template-engine.js`

---

## 一、要解决的问题

Claw 当前主要运行在用户本地。用户也会在远程服务器上运行 Claw 和 Agent，但需要打开另一个浏览器窗口访问远程实例，难以在同一工作流中持续关注和操作本地、远程任务。

这项需求真正要解决的是：

> 当某个 Agent 或工作空间确实具有远程运行需求时，用户能否从当前 Claw 工作流自然地发现、进入并操作它，而不必手工切换到另一个独立站点？

这里的关键词是“某个 Agent 或工作空间”。远程访问不是所有 Agent 都需要拥有的全局产品形态。

例如：

- 编程类 Agent 可能需要访问远程服务器上的项目目录、会话和运行时；
- 某些工作空间可能同时存在本地与远程执行位置；
- IM 渠道的门户代理主要承担消息入口和渠道管理，从业务语义上通常没有连接远程工作空间的必要；
- 纯本地配置、设备或桌面能力也不应因为系统支持远程访问而被自动远程化。

因此，本阶段不把“所有 Agent 混排在统一远程列表中”设为目标，也不预设最终界面一定是左侧栏分组、远程终端页或服务器管理页。

## 二、当前能够确认的用户诉求

### 2.1 已确认诉求

1. **减少环境切换**：对于确有远程需求的工作流，用户不应频繁在多个 Claw 页面之间切换。
2. **保持操作连续性**：进入远程上下文后，消息、运行状态、工具执行、Todo、User Input 和中断等核心能力应尽量连续。
3. **连接可靠**：用户发出的输入和中断不能处于“看起来成功、实际上没有送达”的未知状态。
4. **业务代码复用**：底层通信、身份和错误处理应尽量统一，避免每个 Feature 重写一套远程协议。
5. **按业务语义启用**：只有适合远程运行的 Agent、工作空间或具体能力才暴露远程入口。

### 2.2 尚未确认的问题

以下内容仍是产品问题，不应在需求分析阶段提前定型：

- 远程入口位于 Agent 列表、工作空间内部、独立连接页，还是搜索/命令入口；
- 用户首先选择“服务器”“工作空间”“Agent”还是“会话”；
- 本地与远程对象是否混排，还是在进入某个业务 Agent 后再选择执行位置；
- 是否需要展示远程服务器本身，还是只展示用户可操作的工作空间；
- 一个工作空间能否同时挂载多个远端；
- 远程对象是否支持完整管理，还是先只支持查看和交互；
- 哪些能力可以无差别复用，哪些能力必须明确区分本地和远程。

### 2.3 本阶段非目标

- 不确定最终 UI 布局和信息架构；
- 不要求所有 Agent 都支持远程连接；
- 不承诺所有 Feature 自动获得完整远程能力；
- 不在缺少幂等、确认和恢复协议时承诺“与本地完全一致”；
- 不把 SSH、WebSocket 或某种 ID 前缀提前固化为唯一方案；
- 不立即代理全部 `/protoclaw/*` 管理接口。

## 三、能力边界：远程访问不是一种页面，而是一组可选能力

### 3.1 需要区分的领域对象

后续设计至少要区分以下概念，不能只用一个 `agentId` 同时表达全部含义：

| 对象 | 含义 | 示例 |
|------|------|------|
| 连接位置 | 一个可访问的 Claw/Viewer 运行环境 | 本机、开发服务器、测试服务器 |
| 业务 Agent | 用户理解的能力入口 | 编程小助手、IM 门户代理 |
| 工作空间 | Agent 操作的项目或业务上下文 | 本地项目 A、远程项目 X |
| 运行时 Agent | ViewerWorker 中已经启动的具体会话进程 | 某次编程会话的 runtime ID |
| 会话 | 可恢复的历史与状态单位 | workspace session |
| 能力 | 对该对象允许执行的动作 | 查看、输入、中断、会话管理、文件传输 |

最终界面可以选择隐藏其中一些概念，但底层模型不能把它们混为一谈。

### 3.2 远程适用性应按业务范围声明

远程能力默认关闭，由业务 Agent、工作空间类型或产品配置明确声明适用范围。概念上可以表达为：

```text
remoteAccess:
  applicability: disabled | workspace | runtime | custom
  capabilities:
    - observe-runtime
    - send-input
    - interrupt
    - manage-sessions
    - transfer-files
    - manage-config
```

这只是能力模型草案，不是最终配置格式。

示例：

| 场景 | 可能需要的远程能力 | 默认判断 |
|------|--------------------|----------|
| 编程小助手的远程项目 | 工作空间发现、会话、运行时交互、文件/图片 | 值得探索 |
| 远程服务器上的独立 Agent runtime | 状态查看、输入、中断 | 值得探索 |
| IM 渠道门户代理 | 通常只管理本地渠道和消息入口 | 默认不启用 |
| 本地设备或桌面 Feature | 依赖本机资源 | 默认不启用 |
| 模型和 OAuth 配置 | 权限与凭据边界复杂 | 不自动继承，单独评审 |

### 3.3 “代码只写一套”的准确含义

可复用的应该是底层访问契约，而不是强迫所有界面和业务对象表现一致：

- 上层通过统一目标引用发起请求，不直接拼远程地址；
- 网关统一处理目标解析、身份转换、超时、错误和可观测性；
- 业务层仍可决定是否展示远程入口、展示哪些动作；
- Feature 若只使用标准运行时能力，可以复用远程通道；
- Feature 若依赖本地文件、设备、OAuth、可执行模板或专用 `/protoclaw` API，需要单独声明和验证。

因此，“一套底层通信契约”是目标；“所有 Agent 和 Feature 自动远程化”不是目标。

## 四、现有架构事实与限制

### 4.1 当前数据链路

```text
浏览器
  ├── /api/*、/template/* 等
  │      ↓
  │   Claw Server proxyToViewer()
  │      ↓
  │   ViewerWorker
  │      ↓ UDS / Named Pipe
  │   Agent runtime
  │
  └── /protoclaw/*
         ↓
      Claw Server 的工作空间、会话、配置、图片和业务逻辑
```

已确认的有利条件：

- 浏览器模式下，大部分 Viewer 请求使用同源相对路径；
- Viewer 请求集中经过 `proxyToViewer()`；
- ViewerWorker 已提供消息、工具、Hook、Todo、输入和中断等运行时 API；
- SSH 隧道可以作为安全传输候选，无需直接暴露远端端口。

### 4.2 不能被“切换 origin”自动解决的问题

1. **身份不是单一 agentId**：本地生成的远程复合 ID 不能原样发送给只认识原始 ID 的远端 ViewerWorker。
2. **部分请求没有 agentId**：模板、静态资源、日志、MCP 信息和 current 请求缺少天然路由键。
3. **侧栏不只读取 Viewer 列表**：前端还依赖 `/protoclaw/get_connected_agents`、工作空间和会话元数据。
4. **静态模板是可执行代码**：把远端模板代理为本地同源模块会扩大安全边界。
5. **图片和附件是本地文件**：本地上传得到的绝对路径不能直接交给远端 Agent，反向亦然。
6. **Viewer success 不等于 Agent 已收到**：Viewer 到 UDS/Agent 的最后一跳仍可能失败。
7. **多端点轮询不是原子快照**：messages、tools、hooks、overview、todo 可能来自不同 revision。

这些问题与最终 UI 无关，是任何产品形态都必须遵守的底层约束。

### 4.3 当前前端形态带来的探索要求

当前侧栏将业务 Agent、工作空间信息和 Viewer runtime 数据合并后展示。这不意味着未来远程能力必须继续使用同一种聚合方式。

在决定界面前，需要先回答：

- 用户是在寻找远程服务器，还是寻找某个 Agent 能操作的远程工作空间；
- 远程 runtime 是独立业务对象，还是某个工作空间当前运行状态；
- 与远程无关的 Agent 是否完全看不到远程概念；
- 当远端离线时，应保留工作空间入口、显示最后状态，还是隐藏；
- 用户切换的是业务上下文还是网络目标。

## 五、产品形态候选：只作为验证假设

以下方案可以制作低成本原型，但当前不选定其中任何一个。

### 5.1 候选 A：在具体 Agent 内选择工作空间位置

用户先进入“编程小助手”，再在它支持的工作空间列表中看到本地和远程项目。

可能优势：

- 远程能力只出现在业务上需要它的 Agent 中；
- IM 门户等无关 Agent 不会出现多余入口；
- 用户关注的是项目和任务，不必先理解服务器。

待验证问题：

- 多种 Agent 是否能共享同一个远程工作空间；
- 远程 runtime 不属于已知工作空间时如何进入；
- 连接管理和故障诊断放在哪里。

### 5.2 候选 B：独立的远程连接/环境入口

用户先打开远程环境，再浏览该环境提供的 Agent、工作空间和会话。

可能优势：

- 连接状态、认证和权限边界清楚；
- 与直接打开远端 Claw 的心智模型接近；
- 适合管理多台服务器。

待验证问题：

- 是否仍然造成“进入另一个世界”的割裂感；
- 如何与本地同一业务 Agent 的工作流衔接；
- 是否暴露了用户不关心的服务器概念。

### 5.3 候选 C：统一搜索或列表中的远程对象

本地和远程对象在统一入口中出现，通过来源、状态或分组区分。

可能优势：

- 切换成本最低；
- 适合同时关注多个正在运行的 Agent。

待验证问题：

- 容易混淆业务 Agent、工作空间和 runtime；
- 会给不需要远程能力的 Agent 增加噪音；
- 多服务器、多项目后列表是否失控；
- 权限与危险操作是否足够清晰。

### 5.4 候选 D：基于任务或最近运行记录进入

不展示完整远端目录，只在最近任务、通知、搜索结果或明确链接中打开远程上下文。

可能优势：

- 产品表面最轻；
- 远程概念只在实际发生时出现。

待验证问题：

- 首次发现远程工作空间的路径；
- 离线对象和历史会话如何管理；
- 是否适合需要长期浏览远程项目的用户。

### 5.5 原型评估维度

每个候选形态至少用以下任务验证：

1. 打开远程编程项目并继续已有会话；
2. 在本地和远程两个编程任务之间切换；
3. 远端断线时理解当前状态并恢复；
4. 找到正在等待 User Input 的远程任务；
5. 使用 IM 门户代理，确认界面中没有无意义的远程入口；
6. 面对多个服务器和同名工作空间时仍能判断当前操作目标；
7. 执行中断、删除、配置等高风险操作时能明确识别作用位置。

评估结果应先确定用户的对象模型，再决定导航和视觉结构。

## 六、与产品形态无关的技术契约

以下契约可以先研究，但不应反向决定 UI。

### 6.1 请求必须携带显式目标上下文

不建议仅依赖 `remote:srv1:agentId` 字符串前缀和 URL 正则推断目标。更稳妥的内部模型是一个结构化引用：

```ts
type TargetRef = {
  locationId: string;      // local 或某个已配置远端
  runtimeId?: string;      // ViewerWorker 原始 runtime ID
  workspaceId?: string;    // 业务工作空间 ID
  sessionId?: string;      // 可选会话 ID
};
```

最终对浏览器暴露的 URL、header 或 opaque ID 仍待设计，但必须满足：

- 不把本地复合 ID 原样发送给远端；
- path、query、body 和响应中的身份转换一致；
- 无目标或目标失效时 fail closed，不悄悄回退本地；
- `current` 状态由明确的拥有者管理，不能依赖多个 ViewerWorker 各自的隐式 current；
- 同名 Agent、工作空间和会话不会碰撞。

### 6.2 能力发现优先于能力假设

远端连接建立后，应先获得可用能力，而不是假定本地和远端完全一致：

```text
location
  ├── runtimeRead: available
  ├── runtimeWrite: available
  ├── workspaceDiscovery: unavailable
  ├── sessionManagement: available
  ├── fileTransfer: unavailable
  └── rendererPolicy: local-bundle-only
```

产品层根据业务 Agent 的需求和远端实际能力决定是否展示入口和动作。

### 6.3 写操作需要端到端可靠性协议

关键写操作至少需要：

- 客户端生成稳定的 `operationId`；
- 本地网关维护有界 outbox，并明确是否持久化；
- 远端按 `operationId` 幂等处理；
- 区分“网关收到”“Viewer 收到”“Agent 已处理”；
- 超时后可查询最终状态，而不是盲目重发；
- 重连、进程重启和用户取消时有明确规则；
- 队列有容量、过期和背压策略。

在这套协议完成前，只能描述为“远程请求可用”，不能描述为“消息绝不丢失”。

### 6.4 读状态需要 revision 和降级语义

- 对同一 runtime 的核心状态提供 `sessionEpoch/revision`；
- 聚合结果标记数据来源和采集时间；
- 单个远端失败不阻塞本地和其他远端；
- 区分在线状态、最后已知状态和未知状态；
- 重连后通过全量快照或游标 replay 恢复；
- ViewerWorker 重启后的 epoch 变化必须可识别。

### 6.5 远端代码与文件需要独立信任策略

- 不默认把远端模板作为本地同源 JavaScript 执行；
- 优先使用本地已安装且版本/哈希匹配的渲染模板；
- 必须运行远端渲染逻辑时，使用沙箱和窄 RPC；
- 图片与附件使用显式上传/下载或内容寻址，不传递跨机器绝对路径；
- 远端文件、配置和 OAuth 操作按独立权限域评审；
- 日志与错误不得泄露密钥和本机敏感路径。

### 6.6 连接资源必须有生命周期所有者

无论最终使用 SSH、VPN、WebSocket 还是其他传输，都需要：

- `starting / ready / degraded / reconnecting / stopping / stopped` 状态；
- 每个远端独立的超时、熔断和重连策略；
- 子进程、socket、timer 和后台 Promise 的明确所有者；
- 启动部分失败时不暴露半初始化连接；
- 配置重载和进程退出时的幂等清理；
- Host Key 或等价服务器身份校验；
- 参数数组启动进程，避免把配置拼入 shell；
- 本地监听端口只绑定 loopback。

## 七、传输方案：候选而非产品结论

### 7.1 SSH 隧道

SSH 隧道适合作为早期技术验证候选：成熟、加密、可连接仅监听 loopback 的远端服务，也符合“类似远程终端”的用户心智。

但仍需验证：

- Windows、macOS 和 Linux 的 SSH 可用性与凭据体验；
- Host Key、私钥、ssh-agent 和口令交互；
- Viewer 与 Claw 两类端口如何映射；
- 断线后由谁重启 SSH 进程；
- 动态端口分配、冲突和清理；
- 多服务器并发与资源开销。

OpenSSH 的 keepalive 可以帮助检测断线，但普通 SSH 进程不会自行完成完整的业务重连、请求恢复和幂等处理。

### 7.2 VPN、直连 HTTPS 或反向连接

这些方案可能更适合已有内网、容器平台或无需本地 SSH 客户端的场景，但需要额外考虑服务认证、证书、部署和暴露面。

### 7.3 WebSocket 或事件流

WebSocket 可以减少轮询延迟，但不自动解决可靠性。若采用实时推送，仍需 sequence、断线游标、补拉快照、背压和权限控制。

本阶段只验证传输能否满足目标契约，不让传输方案决定产品导航。

## 八、探索与实施阶段

### Phase A：需求与对象模型验证

目标：确定哪些真实工作流需要远程能力，以及用户认为自己正在操作什么对象。

- 选取编程 Agent、独立远程 runtime、IM 门户代理三个差异明显的样本；
- 记录它们需要和不需要的远程能力；
- 明确工作空间、runtime、会话和服务器之间的关系；
- 产出能力矩阵和非目标清单；
- 不写生产级隧道和全局列表。

退出条件：能够解释为什么某个 Agent 出现远程入口，而另一个不出现。

### Phase B：产品原型验证

目标：比较第五章的候选形态，不预设胜出方案。

- 制作低成本交互稿或最小前端原型；
- 用真实任务验证进入、切换、断线、恢复和高风险操作；
- 验证 IM 门户等无关 Agent 不受干扰；
- 记录用户是否更关注服务器、工作空间、Agent 还是任务；
- 形成产品形态决策记录。

退出条件：选定首个交付场景及其入口，但不要求覆盖所有 Agent。

### Phase C：只读技术 Spike

目标：验证结构化目标路由和故障隔离，不做写操作承诺。

- 连接一个远端环境；
- 读取其能力、工作空间或 runtime 列表；
- 查看一个远程 runtime 的消息和状态；
- 验证同名 ID、无 agentId 请求和单远端断线；
- 不执行远端模板代码；
- 不把远端失联扩散为本地页面不可用。

退出条件：目标身份、来源标记、超时和降级行为稳定。

### Phase D：交互可靠性

目标：在一个已选定业务场景内支持输入、中断和恢复。

- 实现 operationId、幂等和分层 ACK；
- 验证请求已发送但响应丢失的情况；
- 验证 Viewer 到 Agent 的最后一跳失败；
- 验证断线、重连、进程重启和队列上限；
- 明确哪些操作允许重试，哪些需要用户确认。

退出条件：关键写操作不会因自动重试而重复，也不会把未送达显示为成功。

### Phase E：按需扩展能力

根据已验证的业务需求逐项增加：

- 会话管理；
- 工作空间管理；
- 图片与文件传输；
- 远端配置；
- 安全的模板/渲染交付；
- 多远端与实时事件流。

每项能力单独评审权限、失败域和产品入口，不以“透明代理全部 API”为默认方案。

## 九、验证矩阵

### 9.1 产品验证

- [ ] 编程 Agent 的远程入口符合用户对工作空间的理解
- [ ] IM 门户代理没有出现无业务意义的远程入口
- [ ] 用户能明确判断当前对象位于本地还是远端
- [ ] 多个同名 Agent/工作空间不会造成误操作
- [ ] 远端离线时，界面表达符合用户预期
- [ ] 高风险操作明确展示目标位置和影响范围

### 9.2 契约验证

- [ ] path、query、body 和响应身份能够往返转换
- [ ] 无目标、未知目标和失效目标 fail closed
- [ ] 无 agentId 请求拥有明确作用域
- [ ] 单个远端失败不阻塞其他来源
- [ ] 能力发现结果能够控制可用操作
- [ ] 本地与远端状态带有来源、epoch/revision 和时间信息

### 9.3 可靠性与安全验证

- [ ] 模拟请求已执行但响应丢失，不产生重复输入
- [ ] Viewer 到 Agent 写入失败不会返回最终成功
- [ ] 重连后可以查询或恢复操作状态
- [ ] outbox 容量、过期和清理生效
- [ ] 连接关闭后无残留子进程、socket 和 timer
- [ ] Host Key/服务器身份校验失败时拒绝连接
- [ ] 远端模板不能获得本地 Claw 的同源权限
- [ ] 图片与附件不依赖另一台机器上的绝对路径

## 十、需要形成的决策记录

在进入正式实现前，至少形成以下 ADR 或产品决策：

1. **首个远程使用场景**：先服务哪类 Agent/工作空间，明确排除哪些对象；
2. **产品入口与对象模型**：用户首先选择什么，远程来源如何表达；
3. **目标身份契约**：location、workspace、runtime、session 如何编码和转换；
4. **能力发现与权限**：谁声明能力，默认值和降级规则是什么；
5. **传输与凭据**：首个环境采用什么方案，生命周期由谁负责；
6. **写操作可靠性**：幂等、ACK、重试、持久化和取消语义；
7. **模板与文件信任**：远端代码、图片、附件如何安全交付；
8. **状态一致性**：revision、快照、replay 和 Viewer 重启语义。

## 十一、当前结论

远程访问值得继续探索，但现在只能确定底层存在可复用的代理与运行时接口，不能据此推导出最终产品一定是“本地和远程 Agent 在左侧统一混排”。

更合适的推进方式是：

1. 先按 Agent 和工作空间梳理远程能力是否有业务意义；
2. 用多个差异场景验证用户真正想进入的是服务器、工作空间、Agent 还是任务；
3. 再选择界面形态；
4. 同时用只读 Spike 验证目标路由、故障隔离和安全边界；
5. 最后在一个明确场景内完成可靠写操作，而不是一次性“远程化全部 Claw”。

远程连接应当成为一项可被合适业务对象使用的基础能力，而不是强加给所有 Agent 的统一界面概念。
