# 显示过程模式的滚动性能调查

日期：2026-09-27。前半部分记录基于 HEAD `0a8cb35` 与当时工作区的只读调查；文末“后续修复”记录用户授权快速修复后的实现与验证。用户明确反馈：不开启“显示过程”时不卡，开启后滚动有周期性顿挫，并担心长会话卡死。美术调整是时间线索，尚不能单凭先后顺序认定因果。

工作区没有冻结成独立版本；调查期间还能看到其它任务的源文件改动。本次数字用于机制判断和重复对照，不能作为某个发布版本的正式性能认证。下一轮验收应固定源文件、模板版本和样本，避免工作区变化混入基线。

## 判断与证据边界

当前更合适的定性是：**显示过程展开了大量工具内容，页面保留完整历史 DOM，又在滚动过程中管理内容可见性、折叠和阅读位置；这些工作与持续动画叠加，容易越过帧预算。** 内存占用与滚动计算是相关但不同的问题，不能把所有卡顿都称为“内存炸了”。

已经验证的是窗口分支里占位条动画的额外成本，以及“没有长任务”不等于“没有掉帧”。尚未闭环的是用户实际浏览器中当前最严重那次卡顿：提供的会话在当前全量布局分支的隔离回放中没有复现严重卡顿。因此不能宣布问题已经解决，也不能把单个因素说成所有场景的唯一根因。

没有必要先撤掉整体玻璃风格。当前 `45d4ef4` 已将工具块、表格、代码块、折叠按钮的重复 backdrop-filter 去除，并把环境光从 background-position 动画改为 transform。当前随流工具块仍有半透明背景，但已经没有每块实时背景模糊。仍需在实际客户端验证剩余合成成本，尤其不同 GPU、DPR 和 WebView 环境。

## 当前代码实际做了什么

1. `chat-renderer.js` 全量生成消息 HTML，并通过 `container.innerHTML = html` 插入所有历史消息。隐藏过程也会生成工具内容，再通过 CSS 隐藏。
2. `lazy-tool-content.js` 的窗口是在 DOM 中切换 `content-visibility:hidden`。屏外子树可以省布局/绘制，但元素和内容仍在 DOM 中；它不是历史内容节点的卸载机制。
3. 窗口大小是顶部行前 150 行、后 100 行。按行数控制的窗口，不能给单行很大的代码/工具结果提供稳定的节点和时间预算。普通助手正文也不在这套过程内容窗口的全面保护范围内。
4. 首次未布局的隐藏内容使用约 150px 的估算高度。恢复真实高度后，窗口逻辑测量高度、写 scrollTop 补偿；附近行又会进入自动折叠处理。这是一条会读写布局的滚动路径。
5. 当前 `.process-cv-hidden` **自身**仍运行 `cv-shimmer 1.2s linear infinite`，动画属性是背景位置。跳过其子树布局/绘制，不等于停止元素自身的动画处理。
6. 工作区修改在元素数量不超过 70,000 时关闭过程窗口、全量布局并一次性同步折叠状态。这个策略确实可以消除滚动期间的部分 reveal/折叠开销，但会增加首次布局和常驻渲染状态；超过门槛的会话继续走旧窗口路径。
7. 分级只在全量 render 时评估，位置在数学/表格增强之前；流式追加保持原来的模式。元素数量也不包括文本节点、伪元素、像素面积或层内存。因此 70,000 不是可靠的通用资源预算。

官方对 [content-visibility](https://web.dev/articles/content-visibility) 的说明也强调：它跳过渲染工作，但隐藏内容可以继续保留在 DOM；对跳过的子树调用需要布局的 DOM API 可能抵消收益。对 [布局读写交替](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing) 的优化，需要考虑 DOM 规模及同步布局的触发方式。

## 本次实验

诊断脚本位于 `.agentdev/temp/perf-investigation-20260927.mjs`；结果位于 `.agentdev/temp/perf-investigation-20260927/`，均为本地诊断产物。

实验采用独立 Edge 无头进程，1600×900，串行执行。阻止应用启动阶段加载其他会话，不发送写请求，不切换用户真实会话。真实样本取 `session-1790434680534-e22e98` 的持久化快照，共 1,580 条消息；从当前运行的对应 runtime 只读获取 52 个工具配置，并预加载 18 个渲染模板。合成样本为 901 条消息，包含较多长工具输出。

滚动协议：从底部开始，每个 rAF 向上移动 24px，名义累计 10,000px，共 418 帧采样。检查消息数、DOM 行数、模式和实际位移；记录帧间隔、长任务、折叠数和隐藏块数。窗口分支的实际像素位移受高度补偿影响，必须和折叠/窗口状态一起看，不能机械要求与名义位移完全一致。

以下是当前有效结果；不同分支的折叠状态不同，只对同分支内的单变量实验作直接因果比较。

| 场景 | 聊天元素数量 | 路径 | 帧间隔 p95 | >50ms 长任务 |
| --- | ---: | --- | ---: | ---: |
| 真实会话，当前工作区 | 52,509 | 全量布局 | 约 16.9ms | 0 |
| 同会话，关闭所有动画/过渡/背景模糊 | 52,509 | 全量布局 | 约 16.9ms | 0 |
| 同会话，强制恢复窗口 | 51,941 | 窗口 | 两次约 33.4–33.5ms | 0 |
| 同会话，强制窗口、仅关闭占位 shimmer | 51,941 | 窗口 | 约 16.8ms | 0 |
| 合成大 DOM，当前路径 | 122,120 | 窗口 | 重复约 33.3ms | 0 |
| 合成大 DOM，仅关闭占位 shimmer | 122,120 | 窗口 | 重复约 16.8ms | 0 |

合成样本的同分支对照保持了相同实际位移（约 9,496px）、10 个折叠内容及 998 个隐藏过程块。停掉 shimmer 不会减少工具内容或关闭窗口切换，这支持它是额外掉帧因素。**两组都没有长任务，却有明显帧间隔差异**：60Hz 下预算约 16.7ms，33ms 的顿挫不会触发 50ms 长任务门槛。

真实会话强制窗口后的同分支 shimmer 对照，也保持相同实际位移（约 10,721px）、14 个折叠内容、651 个隐藏过程块；p95 从约 33.4ms 降至约 16.8ms。它提供了真实内容上的机制验证，但强制窗口与当前自动选择的全量布局分支不同，仍不能替代用户实际卡顿页面的测量。

首轮较长协议曾出现约 100ms p95 和大量长任务，但后续同条件量级明显变化；同时诊断监听记录方式也做过收敛。它不能作为稳定的“100→17ms”收益数字，也没有单独证明变化原因。表中采用后续重复结果。历史输出不能与后续数字拼成一个已闭环结论。

早期不加载真实模板的真实样本只产生约 29,000 元素，不能代表完整产品渲染的负载；这些结果不用于表中的产品判断。另有一次特效对照的消息和 DOM 被异步路径清空，后置校验判为无效；调整隔离后重新测得有效结果。这里同样遵守对历史测试的证据标准。

### 内存观察

真实会话在当前分支连续全量重建 5 次，每次随后强制 GC，整个页面的 DOM 计数均为 136,933；JS heap 使用量从约 8.48MB 到 8.79MB，增长趋缓。这没有表现出每次重建叠留整棵聊天 DOM 的明显迹象。

这个小实验不能排除多会话缓存增长、长时间流式使用、浏览器原生内存、合成层或 GPU 内存问题，也不能用 JS heap 代表渲染器总内存。当前没有 OOM/crash 证据，不能将周期性滚动顿挫定性为内存泄漏。

### 历史 trace

原仓库根的 `window-trace.json`（收口时保存在 `.agentdev/temp/scroll-rescue-20260927/historical-window-trace.json`），来自先前代码/诊断插桩版本，不能当作当前工作区跑分。该 trace 中 834 次工作空间滚动监听器调用累计约 5,766ms；其查询是聊天容器里的 `.workspace-surface`，聊天页面没有这个目标，仍付出查找大树的成本。窗口 rAF 回调累计约 2,327ms，Layerize 约 2,654ms，UpdateLayoutTree 约 2,081ms。

这些总时长可能相互嵌套，不能直接相加。它们说明当时存在全树查询、样式和层处理成本，不能仅盯一处折叠函数。当前移除两个无关监听器的实验没有单独消除压力场景掉帧，真实全量布局样本本来就顺畅；因此“无关监听器是唯一原因”不成立。

## 前面为什么多次没有完成有效修复

读过指定会话的用户反馈、排查总结和末段实验。它不是完全没有找到问题，而是多次把局部热点、无效测试或成本迁移当成整体根因/验收结果。

1. **实验对象一度失真。** 之前记录自己承认：初始化替换了合成会话、跑到错误页面、工具块并未真正折叠、覆写没有拦截目标操作、诊断探针改变了任务时序。这些数字不能证明用户那条滚动路径得到改善。合成样本可以验证机制，但必须确认页面仍然活着，且渲染模板、模式和体量匹配。
2. **把“某处付费”混同“只有这里导致”。** 几何读取经常是浏览器结算之前 DOM/CSS 变化的地点；耗时记到某个 getter 或扫描函数，并不意味着单独减少扫描频率就能清除根因。先前每四帧扫描一次仍有接近的长任务数，就是反例。缓存折叠判断也没有阻止后续布局更新、节点插入和动画工作。
3. **单变量干预改变了显示语义。** 跳过按钮/折叠、停止窗口管理等，可能顺带改变高度、行数、位移和实际显示内容。若比较对象不同，“快了”不能直接转成产品修复。预建按钮、延后插入等末段实验也没有完成稳定的效果闭环。
4. **把位置正确性与流畅度混为同一个问题。** scrollTop 钳制修复、释放锚点和 reveal 补偿对跳动有价值，但同步读取和高度修正仍可能造成掉帧。锚点语义测试通过，不能证明每帧预算达标。冻结窗口到松手，还可能让到达位置先显示占位，再集中恢复；更多补偿会增加协调成本。
5. **主要成本仍随历史内容累积。** 幂等写入、批量读写、图标 mask 化和标点 span 瘦身都有价值，但整棵历史 DOM 仍保留。按元素门槛关闭窗口更是把滚动费用移到首布局和常驻状态，超过门槛后又回到旧路径。瘦身会改变会话落在哪个分支：同一套测试不能自动覆盖两者。
6. **验收指标不完整。** 只看平均 FPS 或 >50ms 长任务，会漏掉 33ms 的周期性停顿；只看滚动又会漏掉首次展开、内存、流式增长和会话切换。一次亮眼结果不等于不同规模与真实滚轮操作都达标。
7. **对话中的改动描述不等于当前代码。** 前次总结说移除了占位无限动画并做了批量扫描；当前 CSS 仍有无限 shimmer，窗口启用时 `_foldRowIfOutside` 也仍逐行“读高度→同步折叠→读高度→补偿”。不能只凭旧总结认定这些修复现在还生效。此次没有追定是哪次回退/后续修改造成了差异。

## 建议的下一轮顺序

### 先做可验证、保持外观的减负

- 从**屏外占位动画**入手：离屏元素不持续动画，只对有需要的屏内占位执行效果。保留玻璃底色、描边和环境光；别把关闭整个美术系统当作默认方案。
- 无关滚动监听器先根据页面状态退出；在对应表面挂载时缓存引用，避免每个聊天 scroll 都在整棵历史 DOM 里查一个不存在的 workspace/project/assembly 元素。
- 阅读锚点利用已有行缓存、邻近索引或有序高度索引，避免每次从第 0 行扫描到视口。明确窗口/折叠/跟随/阅读恢复的 scrollTop 所有权。
- 继续保留 DOM 瘦身方向，但独立验收文字、行号、复制、图标和无障碍语义。浏览器伪元素虽然不计 DOM 节点，仍会有样式/绘制成本。

### 再解决内容生命周期

- 先针对最重的工具结果实现**按需生成内部 DOM**：折叠态只挂摘要/预览，全文保留为数据，用户展开或接近视口才构建、高亮。
- 屏外工具体可卸载，只保留已测高度的轻量壳；高度需按内容版本及可用宽度缓存，改变宽度后重新测量。设有界缓存，不能把移出的全部 DOM 长期留在缓存里。
- 折叠判断和控件准备归入块的首次挂载/内容变化，滚动期间尽量只移动窗口，避免反复改变真实行高和补偿位置。
- 先做工具块内部生命周期，再决定是否整个消息列表虚拟化。全文搜索、复制、导航、选择、流式尾部和宽表行为要作为设计输入；直接换一套列表库会再次引入跳动和内容缺失风险。
- 重新评估 70,000 门槛。短期可作为有明确限制的折中，不能当成长期解决方案，也不建议继续简单抬高。

### 验收覆盖真实体验

同一批真实会话覆盖门槛两侧、长代码工具输出、宽表、富 Markdown。分别测试显示/隐藏过程、首次开过程、底部向上连续滚轮、长距离拖动、宽度拖动、流式更新和多会话切换。

记录帧间隔分布与最长停顿、输入到下一帧的延迟、首布局时间、DOM/原生内存/GPU 内存；记录相同内容锚点是否稳定。以实际客户端原生滚轮为最终依据，无头 rAF 回放用于机制对照。所有性能结果附带工作区版本、模板版本、会话样本和模式状态，另跑不带 trace 的基准，避免插桩影响判定。

下一轮最有价值的是：取得用户当前实际卡顿页面的原生滚轮 trace，并对照屏外动画及窗口/折叠路径，确认本次已经验证的因素在该页面中的占比。无需先牺牲整体视觉风格，也不应再从“把扫描节流一点”开始试运气。

## 后续修复：真实滚轮与折叠 Read 内容（2026-09-27）

用户授权快速修复，并在第一轮刷新后反馈：同一会话 `session-1790434680534-e22e98` 仍会滚动几次后极度卡顿、接近不可用。**第一轮不能判为修复成功；尚无浏览器 OOM/crash 证据。** 第二轮在减轻滚动监听器之外，降低默认折叠内容的实际 DOM 和高亮成本。用户的第二轮体验反馈仍需单独记录。

### 已实现

- 聊天阅读锚点的自动保存等待滚动停顿 150ms，避免每个 scroll 从第 0 行扫描到视口。会话/标签切换等边界仍同步捕获当前位置；延迟保存核对 context key，不能写错会话。
- 工作空间、sticky project bar、assembly side rail 按页面状态先退出，聊天滚动不再遍历大 DOM 查找这些不存在的目标。
- 普通 wheel 监听改为 passive。Chrome 页面恢复时临时附加一次可取消的补偿监听；嵌套滚动、缩放、横向滚动不消费恢复机会，首个合适的 wheel 后移除。Edge 不启用补偿监听。
- 全量渲染分级下，窗口滚动处理直接退出，不再安排空 rAF、停顿定时器及无意义的释放重锚定。
- 离屏过程占位保留静态渐变，去掉无限 background-position 动画。整体玻璃外观、环境光与已存在的 DOM 瘦身保留。
- 工具模板边界统一压缩 Read 的旧行号/content spans，并去掉无视觉贡献的 punctuation spans。原来的瘦身只覆盖内置 JSON 模板，动态 Feature 模板仍生成旧结构，配合新 counter 会画出重复行号。
- 行号使用固定 `data-line` 与 `::before { content:attr(data-line) }`，保留动态 Read 模板的真实源码行号/offset；去掉 CSS counter 依赖。已确认重复行号缺陷，**没有把 counter 单独认定为卡死根因**。
- 长 Read 文件结果默认仅构建前 8 行，沿用原工具模板和高亮；明确展开才构建全文，收起时重新释放全文节点。短结果、目录、失败结果和其他工具维持原行为。全量、追加、末条更新都使用同一个结果渲染函数；原始消息不修改，复制从原始消息取内容。

### 自动验证及数字边界

修复对照冻结了当时的 `public/src`、`public/styles` 为基线，不覆盖用户页面或会话。使用独立 Edge 无头进程、1600×900、相同 1580 条持久化消息、当前 runtime 的工具配置及 18 个真实动态模板。原生 `page.mouse.wheel` 连续 100 次向上 120px；消息数量、行数、模式及实际位移作为有效性检查。基准与结果位于 `.agentdev/temp/scroll-rescue-20260927/`。

- 全量分支旧锚点监听器的 100 次调用累计 333–919ms；第一轮自动测量的对应监听累计 2–7ms（不含停顿后的单次捕获）。这证明减少了逐事件扫描，不证明用户严重故障消失。
- 动态模板下基线有 52,509 个元素。统一行号/模板压缩后为 44,097，进一步延迟 Read 全文后为 33,933；同一会话有 65 个长 Read 预览。
- 真浏览器功能检查通过：8 行预览与完整结果的前 8 行文本/源码行号一致；展开后完整行数一致；再次收起后节点数与折叠行高恢复，原始消息字符串不变；不存在旧的重复行号 span。短结果、目录、错误、其他工具、显式展开/收起也有自动测试。
- 一对原生滚轮测量中，主要 renderer 进程工作集：基线渲染后约 380MB、滚动后 481MB；第二轮约 186MB、滚动后 240MB。第二轮复测为约 306MB→337MB，工作集存在明显波动；其 private memory 两轮滚动后约 279–286MB，基线约 421MB。原生内存由浏览器报告的 renderer PID 通过 Windows `Get-Process` 读取，**不是 JS heap**。这些隔离对照不包含用户客户端、多会话缓存或 GPU 进程；不能据此断言 OOM 被解决。
